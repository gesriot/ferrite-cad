# §22B-1e1: measured Unity asset identity across a reimport

Status: measurement only. The FBX writer, `ExportScene`, the document schema,
the shipped commands and the window are unchanged in this slice. What follows
is what Unity 6000.4.10f1 actually did, and the contract that measurement hands
to §22B-1e2. No production fix is made here, and none is chosen by guessing.

## The question, and why "not missing" is not the answer

§22B-1a to §22B-1d proved that the content arrives: geometry, hierarchy,
transforms, shared meshes, materials and custom properties all survive the trip
into the editor. §22B-1c also recorded, and left open, an editor warning:

```text
Identifier uniqueness violation: 'Name:<name>, Type:Mesh'. Multiple Objects
with the same name/type are generated by this Importer. There is no guarantee
that subsequent imports of this asset will properly re-link to these targets.
```

That warning is about relinking, so the only measurement that settles it is one
that holds a real reference across a real reimport. A reference that resolves to
*some* object is not a reference that survived: it may now denote a different
part, silently, with no warning and no missing pink asset. This slice separates
those cases and names them.

## Instruments

The editor is the installed native arm64 `6000.4.10f1`, run `-batchmode
-nographics`, once per measurement, in a **freshly created temporary project
outside the repository** that is deleted afterwards. Nothing imported is
committed: no `.fbx`, no `.meta`, no `Library`, no Unity project.

Every FBX comes from the production writer. The ten portable variants come from
the `fbx_identity_variants` example calling `write_fbx_ascii_7400`; the real
AP203 assembly comes from the shipped `export-fbx` route over the shared
`ferritecad-jobs`. The §22B-1a Python generator writes none of them.

Pinned `ufbx` 0.23.0 is the independent oracle: FBX object numbers read from
the retained DOM, object classes, names, hierarchy, geometry sharing and the
custom properties. The editor is never asked which FerriteCAD definition an
object is by name — §22B-1c already measured that several definitions of one
real assembly carry the same designation.

Both programs hash the whole file with the same 64-bit FNV-1a, and the join
verifier refuses a run in which they read different bytes. That is a content
check between two programs, not a security digest.

### What a reference means here

A real `ScriptableObject` asset is created in the project, given real references
to the tracked Mesh, Material and GameObject sub-assets, and saved. Unity writes
each one to disk as `{fileID, guid, type}` — the same pair a prefab, a scene or
a material writes. The measurement then reads that file back **as text** to
confirm the stored `fileID` really is the object's local file identifier, and
after the reimport resolves the reference twice by two independent routes: the
reloaded asset, and the stored identifier put back through `GlobalObjectId`. The
run is refused if the two disagree. They never did.

`GlobalObjectId` was examined for every sub-asset of every import — 764 of them
in the portable measurement, 3 384 in the AP203 one — and every single one is
exactly `GlobalObjectId_V1-1-<asset guid>-<local file identifier as unsigned 64
bits>-0`. Not one is anything else. Because that holds, the recorded tables
carry the two components rather than a third copy of them, and the verifier
refuses the run if a single row ever stops matching. The tracked references keep
theirs in full, because that is the string the measurement actually parses
back.

Meaning is compared on the pair a project file stores — asset GUID and local
file identifier — and never on a C# object reference. Reimporting hands back a
different managed instance for the same persisted object; the first version of
this probe compared instances and called every kept reference broken.

### One importer setting, measured rather than assumed

The probe sets `ModelImporter.sortHierarchyByName = false`.

Unity applies that sort **after** the custom-property callbacks have run, so the
durable keys the callback reports land on the wrong finished objects. The first
version of this probe did exactly that: it put `step.product_definition#50` — a
one-slot definition — on the object holding the two-slot `#100`, and the run
died asking for a material slot that was not there. That refusal is in the
failing-first log, with the whole mis-joined hierarchy it printed.

Because that is the probe changing what it measures, it is measured. The
`sort_control` block imports one file both ways and compares every sub-asset's
type, name and local file identifier:

| setting | hierarchy order |
| --- | --- |
| default (`sortHierarchyByName = true`) | `Alpha Part`, `Alpha Part 1`, `Alpha Part 2`, `Beta Part`, `Beta Part 1`, `Early Part` |
| probe (`false`) | `Early Part`, `Alpha Part`, `Alpha Part 2`, `Beta Part`, `Alpha Part 1`, `Beta Part 1` |

The order differs; the set of (type, name, local file identifier) triples is
**identical**.

The sort reorders the hierarchy and moves no identifier; even the numbered
disambiguation suffixes stay attached to the same objects. The same control runs
on the real AP203 assembly, where the reordering is much larger — the first
three children go from `ANY`, `ANY`, `ANY 1` to `ANY`, `ANY`, `ANY 4` — and the
identifiers are unchanged there too. If that ever stops being true, the verifier
refuses the whole run rather than reporting a result about the probe.

## The measured document

One base document, and each variant one change away from it. Its counts, read
by `ufbx` rather than assumed from the way it was built:

```text
base.fbx  10 273 bytes  fnv1a64 0886adebeb8088ba
models 7   geometries 4   materials 5
repeated_geometry_display_names 1     two definitions share a designation
repeated_sibling_names 4              siblings share a display name
placements_sharing_one_geometry 4     two geometries have two placements each
repeated_material_slot_names 2        two slots of one mesh share a name
```

Those four counts are the brief's scenarios 7, 8, 9 and 10. They are asserted by
the verifier, so a scenario cannot pass because the confusion it is about was
never in the file. Every definition has a vertex count no other one has — 3, 4,
5 and 6 in the base document, 7 for the one an insertion adds — so a silent
retarget is visible without trusting any name, key or position.

## Failing-first

Before anything was recorded, the gate was run with `--expect-stable`, which
asserts the optimistic contract: every tracked reference still means the same
FerriteCAD object. It failed on the real editor, on the first scenario:

```text
FCAD_FBX_IDENTITY_FAILURE System.InvalidOperationException: a saved reference
stopped meaning the same FerriteCAD object: s01-byte-identical-reimport
mesh:definition=step.product_definition#50 -> retargeted_to_another_definition
```

That first failure was the probe's, not Unity's — it is the instance-comparison
defect described above, and it is recorded here because the fix for it changed
what the measurement is allowed to conclude. The corrected probe answers
`same_semantic` for every reference in scenario 1. Both the failure and its
cause are kept in
[`../../tools/unity-fbx-identity/evidence/failing-first.log`](../../tools/unity-fbx-identity/evidence/failing-first.log)
rather than remembered.

## What Unity did

Ten scenarios; each tracks the same ten references — four meshes, three
materials and three placements — for a hundred rows. `same_semantic` means the
reference still denotes the same FerriteCAD definition, and for a placement the
same occurrence of it.

| | kept | retargeted | missing, object still exported | missing, object removed |
| --- | --- | --- | --- | --- |
| Mesh | 35 | 1 | 2 | 2 |
| Material | 23 | 2 | 5 | 0 |
| GameObject | 25 | 2 | 3 | 0 |

Per scenario, `.` is kept and a capital is a break:

| scenario | Mesh | Material | GameObject | warning |
| --- | --- | --- | --- | --- |
| 1 — the same bytes at the same path | . . . . | . . . | . . . | unchanged |
| 2 — an unchanged document exported again | . . . . | . . . | . . . | unchanged |
| 3 — one display name, keys unchanged | . **R** . **M** | . . . | **R** **M** **M** | disappeared |
| 4a — an unrelated earlier definition added | . . . . | **M** **R** **M** | . . . | unchanged |
| 4b — an unrelated earlier definition removed | *removed* . . . | **R** **M** **M** | . . . | unchanged |
| 5 — two unrelated definitions swapped | . . . . | . . **M** | . . . | **changed** |
| 6a — a sibling occurrence inserted | . . **M** . | . . . | . . . | unchanged |
| 6b — a sibling occurrence removed | . . . . | . . . | . . . | unchanged |
| 6c — two sibling occurrences swapped | . . . . | . . . | . . . | **changed** |
| 12 — one definition and its placement removed | . . . *removed* | . . . | . **M** **R** | disappeared |

`R` is a silent retarget: the reference resolves, nothing warns, and it now
denotes a different FerriteCAD definition. `M` is a null reference to an object
the document still exports.

### The mechanism, measured

Of the hundred rows, 83 are kept and 2 are honestly missing because the
document dropped the object. Fifteen are neither.

Fourteen of those fifteen are accompanied by exactly one thing: the object the
reference meant got a **new Unity name**, and therefore a new local file
identifier. No other row in the table has that flag set.

The fifteenth is different in kind. In scenario 12 the definition the reference
meant is gone, so there is no object left whose name could have changed —
instead its local file identifier was **inherited** by the surviving same-named
twin, and the reference now resolves to that twin. A project holding it would
show a part that still renders, in the right place, and is the wrong part.

* **Unity's local file identifier for an FBX sub-asset is a function of its
  Unity name and type**, plus a counter that resolves collisions. It is *not* a
  function of the FBX object number, and not of the project: the two
  clean-project runs produced byte-identical identifiers.
* **A Mesh takes its Unity name from a Model node, not from the FBX Geometry.**
  The writer names geometries `Alpha Part #2` with a position appended; Unity
  shows `Alpha Part`. This is why the uniqueness warning fires on meshes even
  though the writer's geometry names are unique — and why scenario 6a broke a
  mesh reference: inserting a placement before the existing ones changed which
  node the shared mesh is named after.
* **A Material keeps the writer's name in full, `Shell #1`.** That `#1` is the
  material's position in the file, so inserting or removing *any* earlier
  definition renumbers every later material, renames it, and moves its
  identifier. That is the whole of scenarios 4a, 4b and 5.
* **A GameObject's identifier follows the same name rule**, including the
  numbered suffix Unity appends to duplicate siblings. Removing one of two
  same-named twins promotes the other into the vacated identifier, which is
  scenario 12's silent retarget.
* Scenario 3 is the most alarming edit: **renaming one definition's display name,
  with every durable key unchanged, moved a Mesh reference from a four-vertex
  part onto a six-vertex part.** The warning *disappeared* in that scenario,
  because the rename removed the name collision — the warning went away exactly
  as the references broke.

### The warning is not the signal

The warning is present in every scenario where almost everything survives, and
**absent** in exactly the two — 3 and 12 — where the worst breaks happen. It
reports a name collision inside one import; it does not report a relink failure
between two.

Two scenarios produced a second warning Unity raised on its own:

```text
Importer(FBXImporter) generated inconsistent result for asset(<guid-6>)
"Assets/Identity/s05-reorder-definitions.fbx"
```

Reordering definitions and reordering siblings both made the editor's own
import-determinism guard fire. That is Unity saying it imported one asset twice
and got two different artefacts.

### `FerriteCADNodeKey` is not durable

The writer derives `FerriteCADNodeKey` from a node's position in the scene, so
it changes whenever anything earlier changes. It is reported beside every
verdict and deliberately kept out of the meaning being compared, because
folding it in would make every unrelated insertion look like a broken
reference. The measurement shows this directly: in scenarios 4a and 4b every
tracked placement kept its meaning while every one of their node keys changed.

The same is true of the FBX object numbers, which the writer derives from
position: they moved in 4a, 4b, 5, 6a, 6c and 12 without, on their own,
breaking anything. **Unity does not use the FBX object number as identity.**

## The real AP203 assembly

Scenario 11 is the assembly §22B-1c already exports: 46 definitions, 140 nodes,
34 geometries, 987 203 triangles, 233 343 529 bytes of ASCII FBX, written by the
shipped `export-fbx` route over the shared job. Each of the two scenarios
imports it on both sides of its change, in each of two freshly created
temporary projects, and the hierarchy-sort control imports it twice more: the
editor read those 233 megabytes ten times to produce this result. Every import
published 564 sub-assets.

This document's definitions carry **no display name at all**, so the writer
falls back to their source-local keys and every Geometry name in the file is
unique: `step.product_definition#68 #2`, and so on for all thirty-four. The
designations live on the *nodes*, and `ufbx` reads only three distinct ones
across the thirty-four definitions that have geometry:

| designation | definitions carrying it |
| --- | --- |
| `ANY` | 26 |
| `МГИФ.773754.239` | 4 |
| `УДШ-3 из ШД-БП` | 3 |

The editor warns thirty times, and the arithmetic is exact — one warning per
definition beyond the first in each group, 25 + 3 + 2:

```text
25 x  Identifier uniqueness violation: 'Name:ANY, Type:Mesh'
 3 x  Identifier uniqueness violation: 'Name:МГИФ.773754.239, Type:Mesh'
 2 x  Identifier uniqueness violation: 'Name:УДШ-3 из ШД-БП, Type:Mesh'
```

This is the single clearest proof in the measurement that **Unity names a Mesh
after a Model node and ignores the FBX Geometry name entirely**: every geometry
name in this file is unique, and every mesh collision Unity reports is a node
designation.

The anchors are chosen from the file by rule rather than by hand: the
definitions whose designations repeat, the one with the most placements —
twelve — and a spread over the rest. Six meshes, three materials and four
placements, twenty-six tracked references across the two scenarios.

Five of the six tracked meshes are ones Unity named `ANY` and the sixth is
`МГИФ.773754.239` — that is, the anchors are exactly the objects the warning
names, not bystanders.

**All twenty-six survive.** Both scenarios are byte-identical reimports, because
two independent exports of this document are byte-identical, which was checked
directly. So the real assembly reproduces the warning at full strength and
breaks nothing — and the portable measurement above shows why that is not
reassurance: the identity the warning points at is the Unity name, and this
document's names only stay put because its bytes do.

The editor also welds vertices on this assembly: 75 of its 108 placed meshes
arrive with fewer vertices than the file has, for example 47 626 against 50 710.
The join between a durable key and a finished object therefore cannot be checked
by vertex count here, and is checked by the geometry-sharing partition instead —
two definitions share one mesh in the editor exactly when they share one
geometry in the file. That check is exact in both documents and is what the
portable measurement uses as well; the vertex counts are additionally required
to match exactly on the portable document, where nothing is welded.

## Repeatability

* Two runs in two freshly created, separately deleted temporary projects
  produced byte-identical canonical reports — including every local file
  identifier. The only project-dependent values are the asset GUIDs, which are
  tokenised, and a GUID Unity prints inside one of its own warnings, tokenised
  the same way.
* The independent `ufbx` reader and the editor agree, per file, on byte count
  and FNV-1a: all twenty file-sides of the portable measurement and all four of
  the AP203 one.
* The recorded portable report carries 1 969 editor-side checks and the join
  verifier adds 1 396; the recorded AP203 report carries 5 328 and 1 491.

## Mutations

Nineteen semantic mutants are applied to copies of the recorded measurement and
fed to the real join verifier: a gate that only checks non-null; a local file
identifier taken for an FBX object number; a display name used as identity; a
hierarchy path used as identity; a Geometry result reported as a Material
result; a mandatory scenario skipped; shared placements turned into separate
meshes; two equal display names collapsed; a silent retarget counted as a kept
reference; the warning dropped from the report; a prewritten report the reader
never saw; the oracle reading a different file; the probe's importer setting
allowed to move identifiers; a run that tracked nothing; the two resolutions
allowed to disagree; the stored pair no longer being the object's identity; a
missing reference called resolved; the editor and the file disagreeing on how
many nodes there are; and a sub-asset's `GlobalObjectId` no longer being the
pair a project stores. All nineteen are killed.

Six more are applied to the C# probe itself, compiled and run against the real
editor: a verdict that only asks whether something resolved; a placement
identified by its display name; the importer left free to reorder the hierarchy
under the durable keys; a saved reference never reloaded from disk; a local file
identifier substituted for the vertex count; and the asset's own `m_Script` line
counted as a tracked reference. All six are killed.

The harness separately refuses an anchor that matches nothing, an anchor that
matches twice, a stale `.mutbak`, a prewritten Unity report with no execution
anchor, a zero-check run, an imported file left in the repository, and a probe
that does not compile. The last is explicitly not counted as a kill, and a
missing editor returns its own exit code that is neither a kill nor a survivor.

The half of this that needs no editor and no kernel — re-joining both recorded
measurements to the independent `ufbx` reading, rebuilding the transition tables
and running the nineteen semantic mutants — is
`tools/unity-fbx-identity/scripts/check_identity_record.sh`, and CI runs it on
every push. Unity itself stays local, on the one measured version, exactly as
§22B-1a decided. A recorded measurement no gate ever reads is a file, not a
result.

## Honest limits

* **The two "export again" scenarios are byte-identical to their base.** The
  writer is a function of the scene, which §22B-1b2 measured and §22B-1c
  repeated, so re-exporting an unchanged document cannot produce different
  bytes. Two independent exports of the real AP203 assembly were compared and
  are byte-identical. Scenario 2 therefore cannot differ from scenario 1, and
  it is reported as a confirmation rather than as an independent result.
* **The real assembly was not edited.** Editing a STEP source is not this
  slice, so scenarios 3 to 12 were measured only on the portable documents. What
  the AP203 assembly contributes is the warning at full strength on real
  repeated designations, and the fact that a reimport of unchanged bytes keeps
  every reference despite it. Whether a *changed* real assembly breaks the same
  way the portable one does is inferred from the shared mechanism, not measured.
* **The occurrence identity used here is an ordinal**, "the n-th placement of
  this definition in scene order". FerriteCAD has no persisted occurrence
  identity, so nothing more durable was available to compare against. Scenarios
  6a and 6c are read with that in mind: they say the ordinal survived, not that
  a persisted occurrence identity did.
* **The probe changes one importer setting**, and the control above shows it
  moves no identifier. It does not prove the setting is irrelevant to every
  other importer behaviour, only to the identifiers this slice measures.
* **Only sub-assets a placement reaches are tracked** — Mesh through
  `MeshFilter`, Material through `MeshRenderer`, and the GameObject itself.
  Avatars, animation clips and imported textures do not exist in these files
  and are not measured.
* **One editor version, one platform.** Everything here is `6000.4.10f1` on
  arm64 macOS. Nothing is claimed about another editor or another host.
* **No prefab or scene was authored.** The reference holder is a
  `ScriptableObject`, which stores references in exactly the same
  `{fileID, guid, type}` form; that is the mechanism a prefab uses, but a
  prefab's own additional remapping was not exercised.
* `tools/check-step-identity.sh` still needs ripgrep, which this machine does
  not have. This slice touches nothing that script looks at, and no workflow
  calls it. Recorded as an environment limit, not a green gate.

## Stop and report

Three of the conditions that require this slice to stop before designing
§22B-1e2 are met, so it stops.

| condition | met | what was measured |
| --- | --- | --- |
| Unity cannot be matched to a durable FerriteCAD identity | **no** | the editor's own custom-property callback delivers `FerriteCADDefinitionKey`, and the join is verified against the geometry sharing `ufbx` read from the same bytes |
| keeping references would need the visible names changed | **open** | identity *is* the visible name today; whether it can stop being that without changing what a user sees is precisely the §22B-1e2 question, and this slice does not answer it |
| Unity ignores or unstably treats FBX object IDs | **yes** | it ignores them entirely; the numbers moved in six scenarios without, on their own, breaking anything |
| Model, Mesh and Material need incompatible identity schemes | **no** | all three are name plus type plus a collision counter — but the *name* comes from three different places, which is a real complication rather than an incompatibility |
| a new persisted occurrence identity or a schema change would be needed | **yes**, for Model | a placement's durable identity is (definition, occurrence) and FerriteCAD persists only the first half |
| the warning reproduces but no gate shows a broken reference | **yes**, on the real assembly alone | the AP203 assembly warns thirty times and keeps all twenty-six references, because its bytes do not change; the portable document shows the same mechanism breaking references as soon as they do |
| results differ between clean projects or independent runs | **no** | two clean projects, byte-identical reports, every local file identifier included |

So no production change is chosen here. What follows is the contract the
measurement supports and the questions it deliberately leaves open.

## The contract for §22B-1e2

This is what the measurement supports. It is not implemented here.

**What identity is, per kind.**

* *Geometry (Unity `Mesh`)* — Unity's identity is the Unity name plus type plus
  a collision counter. The Unity name comes from a Model node, so a definition's
  geometry is only stably identified if **some** node naming it has a name that
  is stable and unique in the file. The durable FerriteCAD identity available to
  put there is the definition's source-qualified key: `ImportedSourceId` plus
  source-local key for an imported definition, `ObjectId` for a body.

  One thing this measurement found that a design would otherwise have assumed:
  an imported STEP definition in this corpus has **no display name at all**. The
  designation a user recognises sits on the occurrence, not on the definition,
  which is why the real assembly's Geometry names are already unique source keys
  and its Model names are already ambiguous. Anything §22B-1e2 does about Mesh
  identity has to work through a node name, because that is the only name Unity
  reads and the only place the designation exists.
* *Model (Unity `GameObject`)* — same rule, on the node's own name. The durable
  FerriteCAD identity of a placement is (definition identity, occurrence). Only
  the first half is persisted today.
* *Material* — same rule, on the FBX material name. The durable identity is
  (definition identity, slot index), plus the placement identity when a node
  overrides the colour, because such an override is a separate binding and must
  not merge with the definition's own slot.

**What must keep a reference.** A byte-identical reimport; re-exporting an
unchanged document; changing a display name while the durable key is unchanged;
inserting, removing or reordering any unrelated definition; inserting, removing
or reordering an unrelated sibling occurrence; adding or removing a placement of
another definition.

**What must honestly make a new object.** Removing a definition from the
document; removing an occurrence; a definition genuinely replaced by a different
source identity. These must produce a *missing* reference, never a resolved one
that denotes something else.

**Can a display name change independently of identity?** It must be able to.
That is the whole of scenario 3, and today it is the single most destructive
edit. Whatever §22B-1e2 does, the visible `GameObject` name must remain the
source designation the user recognises, and identity must stop being that
string. Renaming objects to make them unique is not an acceptable answer, and
neither is a cosmetic suffix that hides the warning without changing what Unity
hashes.

**May FBX object numbers be derived from durable keys?** They may, but it would
not fix anything on its own: this measurement shows Unity ignores them.
Deriving them from durable keys is still worth doing for readers that do use
them, and it would remove one thing that changes for no reason on reorder.

**Collision resolution.** If §22B-1e2 hashes a durable key into a name, the
collision policy has to be stated, because Unity's own collision counter is
order-dependent and is exactly what produced scenario 12's silent retarget. Two
distinct durable keys must not be allowed to produce one Unity name; the
refusal must be typed and must happen before any byte is written, in the same
way the writer already refuses an unrepresentable transform and an out-of-range
colour.

**Why order is not identity.** Definition order, node order and material order
all changed references in this measurement while the documents meant the same
thing. Both `FerriteCADNodeKey` and the FBX object numbers are positional today,
and both moved without meaning to.

**Shared meshes.** A geometry with several placements takes its Unity name from
one of them, and which one depends on order — that is scenario 6a. A stable
geometry identity therefore cannot come from a placement at all; it has to come
from the definition. Whatever is done must keep `sharedMesh` reference-equal
across placements, which §22B-1a and §22B-1b2 already require.

**Structural and omitted nodes.** An assembly frame has no geometry and no
material and needs only a stable Model identity. An omitted definition is a node
with no geometry that carries `FerriteCADGeometryOmission`; it must keep a
stable Model identity too, and it must not acquire a Mesh identity, because a
partial export that starts looking complete is the one failure §22B-1c's
boundary exists to prevent.

**What is still unknown and must be measured in §22B-1e2, not assumed.**
Whether Unity's identifier derivation is stable across editor versions; whether
a name long enough to hold a hash is truncated before hashing; and whether the
`GameObject`, `Transform`, `MeshFilter` and `MeshRenderer` of one node all
follow the same rule, which this slice observed but did not vary independently.
