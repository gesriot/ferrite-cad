# План реализации локального параметрического MCAD

**Статус:** рабочий план первой версии

**Горизонт:** от первого коммита до публичной beta параметрического part-моделлера

**Базовый документ:** [архитектурные решения](architecture-decisions.md)

## 1. Результат первой версии

Beta должна позволять пользователю:

1. создать эскиз на базовой плоскости;
2. задать базовые геометрические и размерные ограничения;
3. создать и изменить Extrude, Revolve, Cut, Fillet, Chamfer, Shell, Mirror и Pattern;
4. сохранить модель в нативный документ, открыть его на другой машине и перестроить без кэшей;
5. получить честную диагностическую ошибку при потерянной топологической ссылке;
6. импортировать и экспортировать STEP, экспортировать STL;
7. работать без заморозки интерфейса во время долгого перестроения.

Сборки, чертежи, ЕСКД, DXF и скриптинг не входят в этот результат. Нельзя называть beta «заменой SolidWorks»; корректное обещание – быстрый локальный параметрический моделлер деталей.

## 2. Принципы исполнения

- Каждый этап заканчивается работающим вертикальным срезом, а не набором библиотек.
- Ни одна фича не считается готовой без persistence, undo, тестов топологического именования и измерения производительности.
- Кэш ускоряет работу, но тесты регулярно запускают полное перестроение без него.
- Все ошибки ядра и потерянные ссылки видимы пользователю; неверный успешный результат хуже отказа.
- Внешние форматы являются входом/выходом, но не моделью редактирования.
- Новая зависимость добавляется только с лицензией, владельцем и причиной появления.

## 3. Рабочая структура репозитория

Предлагаемая структура Rust workspace:

```text
crates/
  ferritecad-types/          UUID, единицы, допуски, ошибки, канонические хэши   [есть]
  ferritecad-document/       IR, CBOR envelopes, SQLite, миграции, кэш-спутник   [есть]
  ferritecad-eval/           планирование и последовательный cold evaluator       [есть]
  ferritecad-kernel/         GeometryKernel trait и kernel-agnostic типы          [есть]
  ferritecad-occt/           Rust часть адаптера OCCT                            [есть]
  ferritecad-occt-bridge/    C++17 `extern "C"` шим и CMake-сборка               [есть]
  ferritecad-topology/       именование, разрешение ссылок, history mapping        [есть]
  ferritecad-sketch/         геометрия эскизов, ограничения и solver API
  ferritecad-tessellation/   LOD и перенос данных для GPU
  ferritecad-render/         wgpu, камера, ID picking, выделение
  ferritecad-exchange/       STEP/XDE и STL
  ferritecad-ui/             egui, команды, панели и взаимодействия
  ferritecad-app/            composition root, окно, настройки, telemetry opt-in
  ferritecad-cli/            create, inspect, validate, dump-graph, clear-cache   [есть]
  ferritecad-testkit/        тестовые модели, сравнения, профилирование
tests/
  corpus/             лицензированно чистые STEP и native fixtures
  topology/           сценарии сохранения/потери ссылок
  snapshots/          изображения и сериализованные результаты
docs/
```

Отметка `[есть]` означает crate, существующий в репозитории; остальные появляются в своём этапе.

Топологическая сортировка намеренно осталась в `ferritecad-document`: документ обязан уметь ответить на «в каком порядке это перестраивать» сам по себе, и `evaluation_order` уже покрыт тестами там. `ferritecad-eval` её переиспользует, а не дублирует, поэтому частичный план по построению является подпоследовательностью полного, а не вторым мнением о порядке. Хэши входов фич живут в `ferritecad-types` и `ferritecad-document` по той же причине – они часть определения объекта, а не планировщика. Последовательный cold evaluator уже исполняет полный план через `GeometryKernel`; отменяемый job scheduler остаётся отдельной работой после появления реального адаптера и модели владения kernel-сессиями у worker'ов.

Прямые зависимости допустимы только вниз: UI не знает OCCT, а document не знает UI и `TopoDS_Shape`. `ferritecad-occt-bridge` – единственное место, где используются заголовки OCCT.

## 4. Сквозные технические правила

### 4.1. Документ и миграции

- Применять `PRAGMA foreign_keys = ON` для каждого соединения: в SQLite это настройка соединения, выключенная по умолчанию, а не свойство файла.
- Любое изменение схемы – отдельная миграция с тестами upgrade и downgrade/readonly fallback. Миграция и запись её номера в `user_version` идут одной транзакцией.
- В `meta` хранить `format_version`, `minimum_reader_version`, UUID документа и единицы отображения; `capabilities` – денормализованный индекс обязательных возможностей. Перед предоставлением write-доступа сверять его с envelope-объявлениями: повреждённый индекс не имеет права сделать документ небезопасно записываемым.
- Payload фичи – CBOR envelope с вложенной byte string; неизвестные payload сохраняются как исходные байты и никогда не перекодируются.
- Сохранять обязательные данные и кэш в **разных файлах**: документ `.fcad`, спутник `.fcad-cache`. Удаление спутника не должно менять результат перестроения, и это проверяется тестом, который просто удаляет файл.
- Документ использует `journal_mode=DELETE` и `synchronous=FULL`, поэтому закрытый документ – один самодостаточный файл. WAL применяется только к спутнику кэша.
- `PRAGMA application_id` содержит `FCAD` для документа и `FCAC` для спутника; чужая SQLite-база отвергается до любой попытки её прочитать.

### 4.2. Хэширование и детерминизм

- Идентификаторы: UUIDv7 в 16-байтовом каноническом представлении.
- Хэши: BLAKE3 от канонической сериализации входов, версии алгоритма и допусков.
- Запретить NaN/Infinity, нормализовать отрицательный ноль и порядок неупорядоченных коллекций.
- Не сравнивать B-Rep по байтам между разными платформами; сравнивать семантический результат, число сущностей, допуски, объём, площадь, bbox и ожидаемые ссылки.

### 4.3. Ошибки и отмена

- Все публичные операции возвращают `Result<T, CadError>` с классификацией: input, constraint, topology, kernel, rendering, IO, cancellation, unsupported.
- FFI не допускает C++ исключений за границу вызова.
- Отмена не сохраняет частичный результат в документ или кэш.
- Неуспешное перестроение сохраняет последний корректный результат только для отображения, но помечает дерево фич ошибкой.

### 4.4. Лицензии и supply chain

- В первом коммите создать `LICENSE`, `THIRD_PARTY_LICENSES.md`, `deny.toml`, `SECURITY.md` и CI-проверку `cargo deny check`.
- Зафиксировать версии и checksums сторонних C/C++ архивов.
- Не добавлять GPL/AGPL-код в процесс приложения без отдельного решения по лицензии.
- Перед распространением включить notices OCCT, LGPL и инструкции по замене динамической библиотеки.

## 5. Этап 0 – подготовка и проверка рисков

**Оценка:** 2–4 недели для одного разработчика.

**Цель:** убрать неверные предположения до появления пользовательского UI.

### Работы

1. **[сделано]** Создать workspace, CI для Windows/Linux/macOS, форматирование, clippy, unit tests и проверку лицензий.
2. **[частично]** Собрать OCCT как динамические библиотеки на всех трёх платформах; зафиксировать тег, контрольную сумму, toolchain, CMake и способ упаковки DLL/SO/dylib. Сделано: OCCT `V8_0_1` собирается shared и проходит smoke-test 8/8 на Linux, Windows и macOS; тег, коммит, SHA-256, размер архива и тулчейн каждой платформы записаны в [build-occt.md](build-occt.md) по прогону [31254884697](https://github.com/gesriot/ferrite-cad/actions/runs/31254884697). Предыдущий кандидат `V8_0_0` прошёл те же три платформы в прогоне [31227437597](https://github.com/gesriot/ferrite-cad/actions/runs/31227437597). Осталось: способ упаковки библиотек в поставку, а для macOS – install name `@rpath`, выбор между universal binary и `lipo`, подпись и нотаризация. Ничего из этого прогоном не проверялось: он собирает и запускает, но не пакует.
3. **[сделано]** Собрать чистый C++ smoke-test: box, extrude, boolean, fillet, сериализация B-Rep, чтение/запись STEP через XDE, тесселяция. Реализация – [`tools/occt-smoke`](../tools/occt-smoke); 8/8 PASS на трёх платформах. Текущий STEP-вход – собственная синтетическая сборка `fixtures/step/canonical/02-flat-assembly.step`: имена, два цвета и миллиметры переживают чтение и круг записи/чтения через XDE.
4. **[сделано]** Сформировать легально доступный тестовый корпус: 20 деталей с агрессивными fillet/shell, 5–10 STEP-сборок, несколько повреждённых файлов. Геометрическая часть – 20 процедурных деталей, описанных параметрами прямо в `fillet_shell_corpus.rs`. STEP-часть – семь собственных AP242-моделей и пять детерминированно повреждённых вариантов в `fixtures/step`; для каждого из 14 артефактов записаны происхождение, размер и SHA-256 в [`PROVENANCE.md`](../fixtures/step/PROVENANCE.md), а обычный CI проверяет и суммы, и полноту списка. `tools/build-step-corpus` после чтения проверяет схему, исходные единицы, дерево definitions/instances, UTF-8-имена, placements, definition/instance colours и непустую валидную геометрию; pin-workflow требует одинаковый семантический манифест на OCCT 8.0.1 трёх ОС. STEP-байты не обязаны совпадать из-за недетерминированного порядка независимых цветовых сущностей writer'а. Старый Pro/ENGINEER fixture без записанного происхождения удалён и заменён синтетической сборкой. Корпус реальных файлов SolidWorks/NX/Creo с проверенными лицензиями остаётся отдельной interoperability-работой и этим пунктом не считается выполненным.
5. Создать бенчмарк-проект для OCCT: время, память, процент ошибок и валидность результата для каждой операции.
6. **[сделано]** Быстро прототипировать solver API на 200 ограничениях: собственный минимальный LM/Dogleg против planegcs. Изолированный стенд и общий корпус до 208 уравнений готовы; оба кандидата проходят общий предел невязки, отвергают три заведомо неразрешимых системы и называют ограничения в простом конфликте. Drag измеряется на 50 обновлениях одного target без перестройки constraint graph planegcs; setup, diagnose и шаги разделены. Planegcs начинает каждый шаг от gesture-start reference, LM – от предыдущего решения; это реальные семантики кандидатов, а не скрытая эквивалентность. Baseline – planegcs, решение и его обратимость записаны в [ADR 0001](decisions/0001-sketch-solver.md). Точные времена не считаются стабильным benchmark до появления hardware profile и повторного cold/warm протокола.
7. Записать hardware profile для бенчмарков: CPU, RAM, ОС, OCCT build flags, версия драйвера.

### Артефакты

- воспроизводимый build guide;
- `ferritecad benchmark-kernel`;
- CSV/JSON результатов и список непроходимых геометрических случаев;
- решение о baseline solver, подтверждённое измерениями;
- перечень обязательных внешних notices.

### Gate выхода

- **[пройден]** OCCT стабильно собирается и динамически грузится на Windows, Linux и macOS;
- **[пройден]** smoke-test читает и экспортирует минимум один STEP с именем и цветом;
- **[пройден]** известны пределы fillet/shell на воспроизводимом процедурном корпусе;
- **[пройден]** есть решение, которое не блокирует MVP: baseline solver – planegcs, собственный LM остаётся независимым reference-кандидатом.

Все четыре критерия gate этапа 0 пройдены. При этом список работ этапа ещё не исчерпан: не записан hardware profile; vendor-interoperability корпус требует реальных файлов и проверки лицензий; packaging planegcs на Linux/Windows и лицензионный комплект поставки остаются отдельной обязательной работой. Gate снимает архитектурные блокеры, но не превращает эти пункты в выполненные.

## 6. Этап 1 – фундамент модели и формата

**Оценка:** 3–5 недель.

**Цель:** получить маленький, но долговечный документ без UI.

### Работы

1. Реализовать базовые типы: `DocumentId`, `ObjectId`, `FeatureId`, `StableEntityId`, Quantity, Unit, Tolerance, Transform, `CadError`.
2. Реализовать SQLite schema v1 и транзакционный repository API.
3. Реализовать envelope CBOR и raw-preservation неизвестных объектов.
4. Реализовать объекты `Document`, `Body`, `Sketch`, `ExtrudeFeature`, `Parameter`, `TopologyRef` и таблицу зависимостей.
5. Реализовать загрузку, сохранение, миграцию и read-only режим для неподдерживаемых capability.
6. Реализовать канонический хэш параметров и входов фич.
7. Реализовать CLI: `inspect`, `validate`, `dump-graph`, `clear-cache`.

### Тесты

- создание → сохранение → загрузка → повторное сохранение;
- сохранение неизвестного CBOR payload без изменения байтов;
- невалидный UUID, цикл в DAG, отсутствующая зависимость, неверная единица;
- crash-safe тесты на искусственном прерывании записи;
- открытие документа после удаления всех кэш-таблиц.

### Gate выхода

CLI создаёт документ с эскизом и Extrude, валидирует его, сохраняет и открывает его с той же семантической IR. Старый reader открывает документ с неизвестной capability только read-only.

## 7. Этап 2 – ядро, DAG и первый вертикальный срез

**Оценка:** 5–8 недель.

**Цель:** `Sketch → Extrude → save → cold rebuild` без пользовательского UI.

### Работы

1. **[сделано]** Описать `GeometryKernel` и DTO, не содержащие OCCT-типов. Crate `ferritecad-kernel` зависит только от `ferritecad-types`: ни OCCT, ни C/C++, ни `build.rs`, ни FFI, ни document/eval. Определены identity ядра для cache key, плоский профиль с помеченными сегментами, extrude и transform, B-Rep blob, параметры тесселяции и mesh, история generated/modified/deleted, явные tolerance, отмена и progress. Handles ядра не сериализуются и привязаны к сессии. Mock-ядро на арифметике позволяет тестировать вышележащие слои без установленного OCCT.
2. **[частично]** Реализовать C++ bridge: создание профиля из 2D-контура, extrude, transform, тесселяция, B-Rep encode/decode и запрос history. Сделано: плоский `extern "C"` ABI с opaque-сессией, кодами состояния и caller-owned буферами; фиксированная ширина ABI-кодов, фактический `noexcept` на всех экспортируемых функциях и перехват `Standard_Failure`, `std::exception` и неизвестных исключений во всех fallible entry points. Реальный путь `Line/Arc профиль → Extrude → release` собирает солид, возвращает историю сторон через `BRepTools_History` и крышки через `FirstShape`/`LastShape`; повторное появление одного OCCT sub-shape получает тот же session-local id. `KernelIdentity` читает версию OCCT из библиотеки, а build-часть содержит полный BLAKE3-256 digest исходников моста, target и C++ toolchain. Проверено на пиннутой OCCT `V8_0_1` на всех трёх платформах прогоном [31275991427](https://github.com/gesriot/ferrite-cad/actions/runs/31275991427): 25 тестов адаптера против настоящей геометрии, а динамическая линковка подтверждена по самому тестовому бинарю – `libTKernel.so.8.0` на Linux, `TKernel.dll` на Windows, `@rpath/libTKernel.8.0.dylib` на macOS. Windows-имя DLL не содержит версии; там именно `8.0.1` подтверждают разрешённый pin с checksum и строка `OCC_VERSION_COMPLETE=8.0.1` запущенного smoke-test, а не вывод `dumpbin`. B-Rep encode/decode работает: бинарный формат OCCT через `BinTools`, обёрнутый собственным заголовком v2 с длиной и BLAKE3-256 checksum payload'а; проверка `KernelIdentity` перед декодированием, отказ на повреждённом, чужом, старом и более новом blob'е, cross-session roundtrip. Тесселяция возвращает positions/normals/indices и диапазоны треугольников на тех же face handles; location и orientation применяются в мосте. Каждый вызов очищает transient mesh до и после работы, поэтому результат зависит от своих deflection-параметров, а не от предыдущей сетки, и рисование не меняет сериализуемый B-Rep. Остался `transform` – сейчас он явно возвращает `Unsupported`.

   Важно: **декодированная форма несёт геометрию и ничего больше.** Формат B-Rep хранит форму, а не историю операций, которые её построили, поэтому у восстановленной формы нет ни боковых граней, ни крышек – мост отказывает на этих запросах, а не отвечает пустым списком, который слой именования прочитал бы как «фича ничего не произвела». Подключать warm cache к evaluator нельзя до задачи №14: только вместе с сохранённым mapping'ом топологии cache hit становится безопасным.
3. **[частично]** В `ferritecad-eval` реализовать dirty propagation и планирование перестроения. Сделано: обратный индекс зависимостей, транзитивный dirty set от нескольких корней, `RebuildPlan` с порядком и детерминированными уровнями параллелизма, facade `DocumentGraph` над `&Document`, честный отказ на цикле и висячем ребре. Осталось: отменяемый job scheduler. Cold evaluator из пункта 4 исполняет план последовательно; уровни параллелизма `RebuildPlan` вычисляются, но пока никем не исполняются, потому что сессия ядра не разделяема между потоками.
4. **[частично]** Реализовать feature evaluator для эскиза и extrude. Сделано: последовательный cold evaluator `rebuild_cold` в `ferritecad-eval`, работающий против `dyn GeometryKernel` и проверенный как на `MockKernel` без OCCT, так и на настоящем `OcctKernel` с сохранением/повторным открытием `.fcad`. Срез – `DatumPlane → Sketch → Extrude → Body`, один замкнутый внешний контур из Line/Arc, только `NewBody` и `Blind`/`Symmetric`. Сегменты эскиза упорядочиваются обходом цепочки, а не берутся в порядке хранения. Всё за пределами среза – `Circle`, точки, отверстия, несколько контуров, booleans, `ThroughAll`, неизвестные типы объектов – возвращает `Unsupported`, а не приближение. Перед обращением к ядру документ проходит semantic validation. Проверены детерминизм повторного и после переоткрытия документа перестроения, отмена до, посреди и на последнем progress-событии, а также освобождение всех shape handles, включая путь через ошибку. Осталось: инкрементальное перестроение по dirty set и отменяемый job scheduler. `rebuild_cached` перестраивает документ целиком и лишь пропускает вычисление тех фич, чей архив нашёлся, – это не инкрементальное перестроение.
5. **[частично]** Реализовать `ferritecad-topology`: выпуск семантических имён для эскиза и ExtrudeCap/ExtrudeSide, mapping истории и resolver. ### Критические тесты топологического именования

Для каждой из последовательностей ниже тест меняет параметр предшественника, очищает кэш и проверяет ожидаемый результат:

- высота Extrude меняется, ссылки на cap и стороны живы;
- профиль получает/теряет сегмент – ссылка либо остаётся семантически корректной, либо даёт явную ошибку;
- порядок обхода граней искусственно изменён в adapter fixture – результат не меняется;
- закоммиченная фикстура плиты даёт тот же манифест cardinality/uniqueness на mock и на OCCT;
- восстановление из документа не опирается на прежний `TopoDS_Shape`;
- нерешаемая ссылка не выбирает другую грань.

### Gate выхода

Одна модель с эскизом и extrude после полной очистки кэша воспроизводится из SQLite. Ссылка на грань extrude остаётся валидной после изменения высоты, а потерянная ссылка диагностируется явно.

## 10. Этап 5 – параметрические фичи и naming

**Оценка:** 6–12 месяцев; выпускать инкрементально.

**Цель:** реальная деталь, а не демонстрация.

Каждая фича проходит один и тот же lifecycle: typed data model → evaluator → семантические outputs → persistent naming → UI command → persistence/migration → unit/property/topology/performance tests → документация и sample.

| Волна | Фичи | Обязательные проверочные сценарии |
| --- | --- | --- |
| 5A | Extrude, Revolve, базовые datum planes, transform | изменение размеров профиля, смена направления, ссылки на caps/side faces |
| 5B | Boolean Cut/Fuse/Common, multi-body | split/merge, удаление входной грани, ссылки между телами |
| 5C | Fillet и Chamfer | цепочка рёбер, изменение радиуса, исчезновение ребра, корректная ошибка |
| 5D | Shell, Draft, Mirror, Linear/Circular Pattern | удалённая грань, инстансы, симметричные случаи, изменение количества |
| 5E | параметры, expressions, suppression, rollback, UI дерева | грязное распространение только на зависимые узлы, повторное включение фич |

Для boolean, fillet, chamfer и shell негативные тесты равноправны позитивным: операция может законно не строиться. Ошибка должна содержать feature ID, пользовательское имя, классификацию и, если возможно, подсказку, что изменить.

### Gate выхода

На тестовом наборе реальных деталей можно менять ранние параметры, получать корректное инкрементальное перестроение, экспортировать STEP/STL и не иметь молчаливого retargeting топологических ссылок.

## 13. Регистр рисков и реакция

| Риск | Ранний индикатор | Действие |
| --- | --- | --- |
| OCCT fillet/shell нестабилен | высокий процент ошибок на corpus | честные ограничения UI, минимальные reproducer, fallback/repair только после измерений |
| Naming даёт неверную грань | хотя бы один silent retargeting | блокировать фичу, добавить fixture; предпочесть явную ошибку |
| Собственный solver затягивается | не хватает базовых ограничений после оговорённого прототипа | зафиксировать временный solver за абстракцией, не тормозить viewer/format |
| Кэш-спутник разрастается | размер `.fcad-cache` растёт непропорционально модели | chunking есть с самого начала; далее eviction и GC по ключу, benchmark до оптимизации. Документ при этом не страдает: кэш – отдельный файл |
| UI блокируется ядром | P95 input latency растёт во время rebuild | обязательные worker jobs, отмена, immutable snapshots |
| FFI или OCCT рушит приложение | crash на импортируемом файле | minimal reproducer, exception boundary, затем worker process для рискованных путей |
| Scope creep | новая крупная подсистема до завершения P0/P1 | вести backlog отдельно; вход только через утверждённый gate |
| Лицензионный конфликт | зависимость без разрешённой лицензии | CI блокирует merge, разрешение документируется до добавления |

Важно не приписывать capability обратную совместимость, которой нет: бинарь с SQL schema target v2 отвергает v3 ещё до чтения envelope. `exchange.step.imported.v1` – более точный инструмент для читателя, который уже понимает schema v3, но не смысл конкретного imported-объекта: он сохраняет envelope байт в байт и открывает документ read-only. Многомегабайтные байты в CBOR `objects.payload` не кладутся; payload держит `source_id`, `content_hash`, `byte_len`, переносимую сцену, identity импортёра и его диагностику.
   **Достижимость – строка, а не поле в payload.** `imported_source_refs` связывает объект и источник с `ON DELETE CASCADE` со стороны объекта и `RESTRICT` со стороны байтов, поэтому SQLite снимает притязание даже с объекта, который этот build декодировать не умеет. Каждая успешная правка добирает источники, на которые никто не ссылается, но перед транзакцией проверяется согласованность известных imported payload'ов и reachability rows: повреждённая таблица ссылок блокирует запись, а не превращает потенциально восстанавливаемый orphan в окончательную потерю. Замена imported-объекта обычным снимает старое притязание; повторное использование content-addressed строки сравнивает не только записанный hash, но и фактические bytes/length. Документ с непонятым объектом открыт read-only и до сборки мусора не доходит. Источник неизменяем: другие байты – новый `source_id` и новый hash, а не правка под старой идентичностью; одинаковое содержимое хранится один раз.
   **Контракт связывания.** `Scene::persist()` даёт handle-free проекцию (`PersistedScene`), `PersistedScene::bind(current)` возвращает **только** переданную свежую сцену и только после позиционного сравнения всей проекции: unit, schema, количество и порядок definitions, name и solids каждой, всё дерево instances, definition/parent, имена, row-major 3x4 placement, colour source и linear RGB. Сравнение точное, без допуска: это проверка тождества повторного чтения уже проверенных байтов, а допуск разрешил бы связать реально сдвинувшийся placement. Имена не являются идентичностью – одинаковые имена законны, поэтому поиска «похожего» definition нет, а любая перестановка, изменившая переносимую проекцию, отвергается с указанием расхождения. Граница записана явно: две definitions с одинаковыми persisted-полями и полностью симметричными occurrences эта проекция различить не может. Durable-ссылок внутрь imported assembly пока нет; до их появления обязателен source-stable definition key из STEP/XDE, а не геометрический fallback. `ShapeHandle` не реализует `Serialize`; это проверено `const`-утверждением, а не обзором. Non-finite значения не проходят ни при decode, ни при persistence, `-0.0` канонизируется.
   **Порядок и транзакция.** Всё, что может отказать – чтение файла, проверка длины и BLAKE3, импорт, построение проекции, строгая сверка – заканчивается до `Document::write`. Rejected import не открывает транзакцию вовсе: у него нет сцены. Успешный импорт пишется одной транзакцией: байты, объект, притязание на байты, capability и метаданные. Отказ не меняет `.fcad` ни на байт и не двигает `modified_at`; байтовые ворота снимаются после того, как документ уже создан и открыт, потому что `Document::open` сам мигрирует и ставит persistent pragmas.
   **Две диагностики, а не одна.** `diagnostics_at_import` – историческое наблюдение, оно не перезаписывается; `diagnostics_now` – то, что сказало текущее чтение. Им соответствуют отдельные `imported_by` и `reopened_by`, поэтому текущий отчёт и свежие handles не остаются без provenance. Другая `KernelIdentity` сама по себе не запрещает открыть документ: `build` содержит target triple, и одна и та же версия на другой ОС отличается по построению. Identity – provenance; сверяется сцена. Отказ связывания освобождает все shapes, которые это чтение построило: иначе документ, который не открывается, тёк бы при каждой попытке.
   **Ворота.** Без OCCT: невозможность сериализовать handle, полнота проекции, связывание в другой session, отказ на перестановке/переименовании/solids/unit/schema/иерархии/placement/цвете, одинаковые имена без выбора «первого», миграция v2→v3 без потери объектов и topology refs, проверка hash/byte_len/BLOB, обнаружение порчи до вызова ядра, неизменность файла при отказе, отсутствие недостижимых байтов после удаления объекта, сохранение непонятого imported-объекта. Против настоящего OCCT: семь канонических файлов проходят import → save → close документа и session → open → новая session → reimport, handles заведомо другие, а имена, дерево, placements, цвета, единицы и solids совпадают; повреждённые, но импортируемые файлы сохраняют историческую диагностику и отдельно дают текущую; отвергнутые файлы не пишут ничего; несоответствие сохранённой сцены отказывается, а не привязывает похожее; на всех путях `live_shape_count` равен нулю. Закоммиченная фикстура плиты мигрирована в schema v3 на месте – все идентификаторы, payload'ы и хэши прежние, – потому что read-only путь отказывает немигрированному документу вместо чтения его как будто новые таблицы уже есть.
   **Срез 18C сделан.** `ferritecad import-step <файл.step> -o <документ.fcad>` – первый путь, на котором пользователь приносит чужой файл. Входной файл открывается один раз и только на чтение: он не переписывается, не нормализуется и не перемещается, что проверяется по байтам и по mtime после прогона. Документ строится в атомарно созданной приватной scratch-директории рядом с назначением и публикуется одним шагом – `hard_link` без `--force` даёт атомарный no-clobber, `rename` с `--force` – обычную замену old-or-new; ни один путь выхода не оставляет `.partial`. Директория резервирует namespace до того, как SQLite получает путь: одной проверки отсутствующего имени было бы недостаточно, потому что между ней и открытием можно подставить symlink. Логика публикации вынесена в общий `publish` и используется и экспортом STL, и импортом: детали здесь тонкие, а вторая копия – это второе место, где они разойдутся.
   **Три исхода, а не два.** Код 0 – документ записан и чтение ничего не сообщило; код 4 – документ записан целиком и чтение что-то сообщило; код 5 – не записано ничего. Скрипт различает их без разбора текста, и ни один из трёх не означает, что файл корректен. При коде 0 отчёт прямо говорит, что молчание описывает читателя, а не файл: на 8.0.1 один из повреждённых файлов переносится и не вызывает ни одной диагностики, оставаясь с испорченной координатой. Слов «корректен», «валиден» и «без проблем» в выводе нет, и это закреплено тестом. Исходные байты попадают в документ целиком, поэтому после импорта исходный файл можно удалить – тест это и делает, а затем читает документ. В `inspect` у импортированного объекта видно число definitions и placements, размер и имя источника, ядро-импортёр и сколько всего было сказано при импорте. Имя объекта по умолчанию берётся из имени файла и меняется `--name`; имена, которые файл дал своим частям, при этом не трогаются. В provenance пишется имя файла, а не путь: путь положил бы раскладку одной машины в документ, который должен переезжать, и всё равно никогда не открывается.

   **Результат: `PRODUCT_DEFINITION` присутствует, уникален и стабилен на десяти из одиннадцати файлов, дающих сцену.** Исключение – специально повреждённый файл со столкнувшимся идентификатором, описанный ниже; два файла, которые OCCT отвергает, сцены не дают, и ключа им не нужно. Идентификаторы совпадают на Linux, Windows и macOS и совпадают при повторном чтении тех же байтов вторым reader'ом. Путь до него типизированный, а не обход графа: вверх строго через `ADVANCED_BREP_SHAPE_REPRESENTATION` и `SHAPE_DEFINITION_REPRESENTATION`, затем вниз через проверенные поля и `PRODUCT_DEFINITION_SHAPE` до `PRODUCT_DEFINITION`; сборочная половина принимает только `NEXT_ASSEMBLY_USAGE_OCCURRENCE`, а не его общий базовый тип. Ограничить произвольный обход числом шагов было бы недостаточно: он всё ещё мог бы прийти в соседнюю деталь.
   **У сборки нет собственной геометрии, а значит нет и собственной сущности.** `shape entity` пригоден для всех definitions только в 4 файлах из 11 – то есть отсутствует именно на узлах, которые пользователь скорее всего и выберет. Сборка именуется через `NEXT_ASSEMBLY_USAGE_OCCURRENCE`: родитель, на котором сходятся все её компоненты. Две находки записаны как форма риска, а не как происшествия: одна сборка может содержать одну деталь несколько раз, и каждое размещение – своё occurrence (без схлопывания дубликатов корректная вложенная сборка выглядела неопознаваемой); две сборки с одинаковым набором компонентов по компонентам неразличимы, и probe в этом случае не выдаёт ключ, а не выбирает.
   **Что делает столкнувшийся идентификатор – измерено.** Добавлен воспроизводимый fixture `06-duplicate-product-definition.step`: `#31` записан дважды с разным содержимым (второй несёт formation и context другой детали), при этом все ссылки в файле по-прежнему разрешаются. Прежний `05-duplicate-entity-id.step` этот вопрос не задавал – он дублирует shape representation и дублирует идентично, так что неоднозначности нет. OCCT читает новый файл (`RetDone`), сообщает на загрузке `F: Ident defined SEVERAL TIMES : #31`, успешно переносит и выдаёт те же три узла с теми же объёмами, что и неповреждённая сборка. **Геометрия цела; потеряна идентичность.** Обе детали ключи сохраняют, а собственный ключ теряет сборка: occurrences её компонентов ссылаются на другой `#31`, поэтому родитель, на котором сходятся все компоненты, пуст, и probe не выдаёт ключ, а не выбирает между ними.
   **Это и есть режим отказа, под который надо проектировать, и он не тот, которого ждёшь.** Столкнувшийся идентификатор не даёт двух definitions с одним ключом – такое поймала бы проверка уникальности. Он даёт узел **без** ключа в файле, который импортируется и выглядит совершенно нормально. Значит §18D-2 обязан проверять полноту («у каждой definition есть ключ»), а не только уникальность; load-диагностика при этом доступна и объясняет причину, чего `04-corrupted-number.step` не даёт. Уникальность на произвольных vendor-файлах остаётся измерением на этом корпусе, а не свойством формата, поэтому обе проверки – на чтении.

Rust-сторона декодера проверяет то же самое повторно – она не может освободить shapes и потому слабее, но не даёт повреждённому буферу стать сценой.
   **Маршрут идентичности вынесен в общий заголовок** `crates/ferritecad-occt-bridge/src/step_identity.hpp` и включается и мостом, и `tools/step-key-probe`. Две копии сделали бы измерение утверждением о probe: при первом же расхождении ворота продолжали бы проходить, пока импортёр делает другое. Матрица ключей после выноса не изменилась ни на байт.
   **`06-duplicate-product-definition.step` больше не создаёт документ.** CLI `import-step` даёт код 5, ничего не пишет и говорит `identifying` – это отказ FerriteCAD, а не ядра. Ворота: ключи присутствуют, уникальны и совпадают при двух чтениях на семи канонических файлах; столкновение отвергается, диагностика ровно одна и со стадией identity, `live_shape_count` после отказа равен нулю; процессный тест CLI подтверждает, что каталог не изменился.
   **Срез 18D-2B-1 сделан.** Persisted scene **v2**: у definition появился `key`, а instance называет свой definition ключом, а не индексом. Индекс остался только у `parent` – и по праву: instance не то, что файл именует, это место, а порядок мест и есть дерево.
   **Связывание идёт по идентичности.** Множества ключей обязаны совпасть точно: перестановка проходит, исчезнувший, появившийся, переименованный и дублированный ключ – отказ с освобождением всех shapes. Проверено и на mock, и против настоящего OCCT: файл, прочитанный и затем описанный в обратном порядке, связывается, и каждое размещение получает именно ту деталь, которую называет.
   **v1 и v2 сравниваются одним кодом**, и вся разница между ними – что именно считается идентичностью definition: у v2 это ключ, у v1 позиция, потому что позиция – всё, что v1 когда-либо о них знал. Отсюда без отдельного правила следует, что перестановка отвергается в v1 и принимается в v2: переставленная v1-сцена действительно изменила единственное, что записала.
   **Legacy v1 продолжает открываться read-write**, связывается по позиции и записывается обратно тем же layout'ом: `StoredScene::keys()` возвращает `None`, а синтез ключа из позиции запрещён – получилось бы нечто, выглядящее идентичностью и ведущее себя как индекс. Payload-версия объекта берётся из самой сцены, а не из билда, поэтому v1-объект под v2-заголовком невозможен. Capability не менялась: старый билд видит незнакомый layout знакомого типа, сохраняет envelope дословно и ничего не теряет.
   **Срез 18D-2B-2 сделан.** `ImportedDefinitionRef { source_id, definition_key }` – один валидируемый тип, а не два поля, которые вызывающий обязан помнить сверить. Пустой ключ отвергается конструктором, и сохранённая ссылка проверяется при десериализации, а не считается верной за то, что раскодировалась.
   **Разрешение идёт внутри названного source и больше нигде.** Ссылка называет байты, к которым относится; чтение знает, из каких байтов оно получено; расхождение – отказ, а не поиск вокруг. Fallback по имени, позиции или ближайшему совпадению отсутствует как операция: ссылка, разрешившаяся во что-то правдоподобное, хуже неразрешившейся. Source и версия сохранённой сцены внутри `ReopenedStepImport` доступны только для чтения: вызывающий не может подменить source перед проверкой или объявить legacy v1-сцену версией v2 и разрешить ссылку по ключам, которые появились только при текущем чтении.
   **Три отказа – три разных факта, и они различаются по `ErrorKind`,** так что вызывающему не нужно разбирать текст: `Input` – ссылка про другой source (она не потеряна, она никогда не была про этот импорт); `Unsupported` – сцена v1, ключ не утрачен, его никогда не существовало, и синтез из позиции ответил бы на вопрос, на который документ не соглашался; `Topology` – тот самый source, и ничто в нём больше не несёт эту идентичность, то есть потерянная ссылка. Это ровно та классификация, которую §16C уже печатает как `invalid`/`unsupported`/`lost` с кодами 1/2/3.
   **Столкновение ключей взято из корпуса, а не придумано:** `01-single-part.step` и `02-flat-assembly.step` оба описывают `step.product_definition#5` – плиту и кронштейн. Ворота против настоящего OCCT: оба файла импортируются в один документ, документ и сессия закрываются, в новой сессии сборка переоткрывается, ссылка в свой source разрешается в свежий handle (заведомо не в прежний), ссылка с тем же ключом в чужой source отвергается, хотя definition с этим самым текстом лежит рядом, а неизвестный ключ даёт `Topology`. На всех путях `live_shape_count` равен нулю.
   **Occurrence path намеренно не включён.** У definition есть идентичность, записанная источником; у occurrence – только положение в дереве, и ссылка, смешавшая эти два уровня, выглядела бы durable, опираясь на индекс. Дальше viewport и vendor-interoperability корпус.
19. **[частично]** Поднять `wgpu` viewport с камерой и immutable mesh snapshot.
   **Срез 19A сделан (view-only, без GPU).** `ferritecad-viewport` превращает меши и размещения в то, что может нарисовать GPU: упакованный неизменяемый `RenderSnapshot`, `Camera`, переживающая resize, и draw list в определённом порядке. Крейт не зависит ни от документа, ни от OCCT и не имеет зависимости, которая позволила бы: только `ferritecad-kernel` (словарь `Mesh`) и `ferritecad-types`.
   **Pick называет definition, а не размещение.** Четыре болта в плите – это одна definition и четыре draw'а, и клик по любому даёт один и тот же `PickId`. Информация, позволяющая различить размещения, до результата pick'а просто не доходит – не отфильтрована в конце, а не переносится вовсе, поэтому никакая последующая правка не начнёт её ронять случайно. Причина та же, что и в §18D-2B: у definition есть идентичность, записанная исходным файлом, а у occurrence – только позиция в дереве, которую следующий импорт волен перенумеровать. Occurrence path намеренно не создан, поэтому viewport не может превратить instance index в сохраняемую ссылку.
   **Pick не является форматом хранения:** у крейта нет прямой зависимости для сериализации, и `PickId` не реализует соответствующий трейт. При этом его raw `u32` намеренно доступен для GPU pick-буфера, поэтому вызывающий технически может записать число сам; такое число имеет смысл только вместе с тем snapshot, который его отрисовал. Readback обязан удерживать именно этот snapshot, а durable selection начинается с identity definition в документе, не с `PickId`.
   **Ворота (headless, без графики):** упаковка в interleaved position+normal с проверкой смещений и bounds; отказ на меше, который GPU не смог бы нарисовать (индекс за пределами, не-конечные позиция или нормаль, переполнение при сужении `f64` в `f32` или при vertex transform); композиция размещений на три уровня вглубь и мировые bounds по всем восьми углам, а не по двум; пустой размещённый mesh не создаёт extent; отказ на forward reference родителя; детерминированный порядок draw'ов – два построения одной модели дают побайтово равный список, и порядок не сортируется по мешу; pick называет definition и никогда размещение, а уже декодированный `PickId` не может молча перенацелиться в другом snapshot; значение pick-буфера вне диапазона попадает в фон; viewport нулевого размера даёт конечные матрицы (aspect = 1, `is_drawable()` = false) для трёх вырожденных размеров; framing одной точки и отказ на бессмысленном боксе; все восемь углов модели остаются внутри wgpu clip volume, в том числе в портретном viewport; пустой snapshot не выдумывает extent.
   **Первый wgpu smoke не вошёл в 19A, но прежний supply-chain блокер уже снят upstream.** Проверенный тогда `wgpu 27` тянул `paste` с RUSTSEC-2024-0436 (unmaintained), поэтому исключение в `deny.toml` намеренно не добавлялось. На 2026-08-12 актуальный `wgpu 30.0.0` больше не содержит `paste`; его полный трёхплатформенный graph отдельно проходит фактический `deny.toml` проекта (`advisories`, `bans`, `licenses`, `sources`), а MSRV крейта 1.87 ниже MSRV проекта 1.90.
   **Срез 19B сделан.** `ferritecad-viewport-gpu` рисует snapshot на настоящем устройстве, off screen: цветовой, глубинный и pick target'ы, минимальный WGSL и readback. Ни окна, ни `egui` – их отсутствие и есть то, что делает срез проверяемым: всё, что здесь утверждается, утверждается о кадре, а не о том, как он попал на экран.
   **`wgpu 30.0.0` проходит проектный `deny.toml` без исключений:** `paste` (RUSTSEC-2024-0436) в графе больше нет, все четыре проверки cargo-deny чистые; граф вырос с 89 до 179 крейтов. Это ровно тот случай, ради которого §19A остановился и не стал добавлять исключение – версия решила вопрос сама.
   **Кадр держит именно тот snapshot, которым отрисован.** `Frame::pick_at` разрешает pick против него, а не против «текущего», поэтому чтение pick-буфера чужим snapshot'ом невозможно не по договорённости, а потому, что кадр и его snapshot нельзя разделить. Это тот же класс ошибки, который §19A закрыл на уровне `PickId`, и здесь он закрыт на уровне владения.
   **Ворота (9 smoke-тестов; пропуск разрешён только когда adapter отсутствует, а не когда найденный adapter отказал в device):** snapshot доходит до цветового target'а в том канале, в котором был задан; pick-буфер возвращает те же идентичности, что были в него положены, а фон читается как `NOTHING`, а не как definition ноль; оба размещения одной definition рисуются в разных половинах кадра и дают один и тот же pick – проверка сканированием, а не по угаданным координатам; кадр не разрешается против другого snapshot'а; viewport нулевого размера даёт пустой кадр, а размер больше device limits отвергается до GPU allocation; пустой snapshot даёт очищенный кадр, а не отказ; normal под non-uniform scale освещается так же, как эквивалентная геометрия с запечённым transform; два кадра одного snapshot'а побайтово равны – утверждение не о GPU вообще, а о том, что в этом рендерере нет ни времени, ни счётчика кадров, ни обхода чего-либо неупорядоченного.
   **Две находки при сборке записаны там, где их встретят:** layout uniform'а в WGSL и в Rust обязан совпадать точно – `vec3<u32>` выравнивается на 16 и растянул бы структуру со 96 до 112 байт, поэтому padding – три скаляра; а квадрат в плоскости XY при камере, смотрящей вдоль +Y, виден с ребра и неотличим от «ничего не нарисовалось», что стоило одного ложного диагноза. `.wgsl` добавлен в проверку лицензионных заголовков: шейдер, вынесенный из репозитория, иначе не несёт лицензии вовсе.
   **Срез 19C сделан.** `PreparedSnapshot` держит резидентные GPU-буферы: `Renderer::prepare` загружает геометрию один раз, а повторные кадры пишут матрицу и гоняют pass, не трогая вершины. Проверяется не на слово: `Renderer::geometry_uploads()` открыт наружу ровно затем, чтобы «загружено один раз» можно было утверждать снаружи, как `live_shape_count` у адаптера ядра, и тест рисует десять кадров с десяти разных камер, требуя, чтобы счётчик не сдвинулся и чтобы картинки при этом различались – иначе тест прошёл бы, ничего не доказав.
   **Три вещи viewport'а теперь принадлежат тому, чем они на самом деле являются:** смысл модели – `RenderSnapshot`, её буферы – `PreparedSnapshot`, одно её прочтение – `Frame`. `PreparedSnapshot` принадлежит подготовившему его `Renderer` (`RendererId` устроен как `SessionId` ядра и по той же причине), и чужой renderer отказывается его рисовать вместо того, чтобы лезть в память другого устройства; отказ – по имени, а не как ошибка драйвера вдали от причины. Старый `Frame` продолжает разрешать picks против своего snapshot'а: тест рисует две модели, у которых raw pick равен 1 в обеих, и требует, чтобы каждый кадр отвечал про свою.
   **Срез 19D сделан.** Интерактивная камера – чистые операции над `Camera` в `ferritecad-viewport`, без `winit` и `egui`: `orbit`, `pan`, `zoom`, `look_from` со стандартными видами и изометрией. Что означает перетаскивание, решено и проверено до того, как что-либо начнёт эти события доставлять, поэтому §19E останется тонким.
   **Что закреплено.** Orbit сохраняет расстояние и точку интереса, применяет yaw и pitch по отдельности и упирается чуть ниже полюса: ровно на вертикали ось up и направление взгляда параллельны, бокового вектора нет, и вид перевернулся бы вокруг оси, которой пользователь не касался. Pan двигает eye и target вместе и ровно на те пиксели, которые ему дали, – измерено по экрану в NDC, а не через `world_per_pixel`, иначе тест соглашался бы с любым ответом функции, которую проверяет. Zoom экспоненциальный и обратимый, никогда не доходит до цели и тянет за собой near/far: камера, приблизившаяся в сто раз с плоскостью отсечения там, где её оставил framing, обрезала бы ровно то, к чему приблизилась. `frame` теперь сохраняет направление: «покажи целиком» – это не «и спереди».
   **Плановый вид имеет сторону.** Сверху и снизу мировая ось up совпадает с направлением взгляда и как up не годится, поэтому эти виды несут свою: север вверх, а низ – зеркало верха, а не его поворот. Проверяется по картинке: точка севернее центра обязана оказаться выше центра экрана и не сместиться вбок. Orbit определён вокруг мировой оси up и восстанавливает её, иначе каждый drag докручивал бы крен.
   **Ворота проверены мутациями.** 28 headless-тестов; каждая из четырнадцати внесённых поломок – снятый clamp, проигнорированный yaw, перепутанные оси pan, инвертированный zoom, потерянный множитель в `world_per_pixel`, framing, возвращающий вид спереди, – роняет ворота. Три первые редакции тестов проходили при снятом clamp, при проигнорированном yaw и при `world_per_pixel` без расстояния; они переписаны так, чтобы измерять угол и экран, а не знак и не самих себя. Ревью добавило ещё две численные границы: недоступен весь viewport, если нулевое любое измерение, а не только высота; длина направления считается устойчивым `hypot`, поэтому большая, но представимая в `f32` модель не превращает расстояние в бесконечность. Жест, чей следующий pose или GPU matrix переполнился бы, не применяется частично.
   **Срез 19E-1 сделан.** Выделена граница surface. `Renderer::for_surface` просит адаптер, умеющий выводить именно в эту поверхность, а `Renderer::new` – любой, умеющий считать: на машине может быть несколько адаптеров, и первый считающий не всегда связан с дисплеем, на котором окно. Раньше оконный путь взял бы headless-адаптер и упал бы позже, внутри драйвера, с сообщением ни о том, ни о другом.
   **`WindowSurface` владеет жизненным циклом:** формат и alpha-режим берутся из возможностей самой поверхности, `resize` переконфигурирует, нулевой размер деконфигурирует (окно свёрнуто – это обычное состояние, а не ошибка), а размер больше предела устройства обрезается, а не отвергается: окно такое, какое есть, и отказ рисовать оставил бы его пустым.
   **Решения вынесены в функции над значениями и проверены без окна.** `recovery_for` отвечает на каждый ответ поверхности: `Lost`/`Outdated` – переконфигурировать и повторить ровно один раз (второй повтор не помог бы, а цикл повесил бы event loop); `Timeout`/`Occluded` – пропустить кадр, оба состояния проходят сами; `Validation` – ошибка самой программы, которую повтор только спрятал бы. `Suboptimal` рисуется, а не выбрасывается, и переконфигурируется после показа: картинка верна, разошлась конфигурация, и выброшенный кадр показал бы пользователю рывок ради того, чего он не видит.
   **Идентичности в окно не пишутся.** Кадр окна рисуется десятки раз в секунду, а pick запрашивают по клику, поэтому платить за второе на каждом первом – платить постоянно за то, что нужно изредка; picking идёт через offscreen-путь с той же камерой. Пайплайн собирается по формату, в который рисуют, но из одного определения: вторая копия стала бы вторым местом, где разъедутся vertex layout, depth state и правило отсечения. Проверка «чужой `PreparedSnapshot`» тоже одна на оба пути.
   **Ворота:** 6 headless-тестов решений (нулевой и запредельный размер, все пять ответов поверхности, две последовательности после единственного retry и ownership устройства) плюс прежние 12 GPU smoke; семь исходных мутаций – разрешённый нулевой размер, необрезанный размер, `Lost`/`Timeout`/`Occluded` как фатальные, `Validation` как повторяемая – все роняют ворота. Ревью добавило восьмую: `Lost -> Suboptimal` обязан нарисовать полученный кадр и переконфигурировать после него; прежняя проверка отдельных ответов этого нарушения state machine не видела. `WindowSurface` также хранит `RendererId`: resize и present с другим устройством отказывают до изменения состояния или получения texture, а не падают позже в драйвере. Самого окна здесь нет намеренно: ни одна платформа CI не может открыть его в тесте (на Linux нет дисплея, на macOS event loop только в главном потоке), поэтому `winit` приходит в **19E-2** вместе с event loop и `egui`. Замерено заранее: `winit 0.30` без `wayland-csd-adwaita` проходит `deny.toml` без исключений (иначе тянет `ttf-parser`, RUSTSEC-2026-0192) и добавляет 113 крейтов.
   **Срез 19E-2 начат: frame-composition seam.** Поверхность выдаёт одну текстуру на кадр, поэтому окно с моделью и интерфейсом поверх обязано делить именно её: сначала модель, затем интерфейс, и только потом публикация. `WindowSurface::begin` – этот шов; overlay, взявший свою текстуру, просил бы второй кадр, а отработавший после `present` рисовал бы в то, что уже на экране. `WindowSurface::present` остался целым кадром там, где над моделью ничего нет, и собран из того же шва, поэтому оба пути приобретают и переконфигурируют одинаково.
   **Заимствование делает работу, а не украшает.** `SurfaceFrame` держит `&mut WindowSurface`, пока жив, поэтому окно нельзя переконфигурировать при незакрытой текстуре – а wgpu документирует `configure` в этот момент как панику, то есть заимствование превращает падение в ошибку компиляции. Ворота – два `compile_fail` doctest: незакрытый frame не даёт resize, а неочищенный frame не открывает texture view; рядом `no_run`-двойник правильной последовательности. Оба негативных теста проверены обратными мутациями, при которых запрещённая программа начинает собираться и ворота краснеют. Ревью сделало порядок структурным: только `SurfaceFrame::draw_scene(self)` выдаёт `ComposedSurfaceFrame`, и только второй открывает `view` overlay и позволяет `present`; поэтому интерфейс нельзя нарисовать до очищающей сцены, а сцену нельзя вызвать повторно и стереть интерфейс. `begin` заимствует вместе с surface и её `Renderer`, а следующие состояния больше не принимают renderer параметром: texture устройства A нельзя нарисовать или опубликовать через устройство B даже теоретически; overlay получает ссылки на правильные device/queue/view из одного состояния. `present` потребляет кадр, потому что текстура публикуется ровно один раз, а переконфигурация после `Suboptimal` происходит уже после того, как texture ушла.
   **Срез 19E-2 сделан.** `ferritecad-ui` – чистый reducer ввода: события идут внутрь, `Camera` двигается, кадр запрашивается. Ни окна, ни surface, ни renderer, ни event loop в сигнатурах нет, поэтому каждое правило – тест, а не «попробуй руками». `ferritecad-app` владеет окном, event loop'ом и surface, и в нём остаётся только проводка.
   **Интерфейсу дано право первого отказа.** Каждое событие приходит с флагом «интерфейс уже хочет это»; флаг соблюдается в reducer'е, потому что «был ли этот клик для панели» – правило о смысле приложения, а не о том, как toolkit докладывает события. Захваченное событие не двигает камеру и не начинает жест, но **позицию указателя всё равно обновляет**: иначе после прохода курсора над панелью первый же drag прыгнул бы на её ширину. Начатый в viewport'е жест интерфейс не отбирает – модель не должна замирать, когда курсор пересёк панель, и это отдельные ворота.
   **Один размер на обе стороны:** `resize` задаёт камеру и возвращает то, чем настраивать surface, поэтому разойтись они не могут; камера с одним соотношением сторон в surface с другим растянула бы модель. **Redraw схлопывается на обеих границах:** reducer объединяет смысловые причины, а `FrameScheduler` отдельно гарантирует один фактический `Window::request_redraw` до начала кадра. Первая проводка снимала флаг и тут же ставила его обратно после каждого события, поэтому полагалась только на необязательное coalescing самой платформы; четыре headless-ворота планировщика ловят эту щель, выбор самого раннего срока и отмену таймера немедленным кадром. `egui::request_repaint_after` будит `ControlFlow::WaitUntil` через user event, поэтому анимация не застывает в спящем loop и не требует polling; первый кадр запрашивается явно после `resumed`. Потеря фокуса завершает жест и забывает прежнюю позицию: ОС не обязана прислать отпускание кнопки окну, которое уже потеряло фокус.
   **Кадр композируется в порядке, который держит тип, а не комментарий:** `begin → draw_scene → egui в загруженный view → present`, одна текстура на кадр. Ручной smoke: окно открывается, показывает фиксированную сцену из двух коробок, переживает resize и закрытие. Документ и OCCT – следующим срезом, после доказанного event loop.
   **Решение по шрифту принято: встроенный набор `egui`.** Системный шрифт дал бы разный интерфейс и покрытие символов на трёх ОС, а свой vendored-файл повторил бы ту же лицензионную обязанность отдельным asset'ом. Следующий срез включает `default_fonts`, разрешает OFL-1.1 и Ubuntu-font-1.0 в `deny.toml`, записывает конкретные шрифты и право их распространения в `THIRD_PARTY_LICENSES.md` и кладёт оба полных текста лицензий в поставку. Одного прохождения `cargo deny` недостаточно: приложение встраивает font software в бинарь, а обе лицензии требуют сохранить свои условия при распространении. До этого прямоугольник-маркер остаётся честным доказательством композиции без текста.
   **Срез 19E-3 сделан: решение исполнено.** Встроенные шрифты `egui` включены, `deny.toml` разрешает `OFL-1.1` и `Ubuntu-font-1.0` только как exception для проверенного `epaint_default_fonts` 0.36.1, а не глобально: иной крейт и даже обновление набора обязаны пройти новое ревью. Обе – шрифтовые лицензии: они разрешают встраивать шрифт в приложение и распространять вместе с ним, ничего не требуют от самого кода, но требуют, чтобы условия сопровождали шрифт. Поэтому полные тексты скопированы дословно в `licences/fonts/` из того самого крейта, что несёт файлы, а не заменены ссылкой, которая может переехать.
   **Что именно встроено:** Hack Regular (MIT, с вкладом DejaVu в public domain и уведомлением Bitstream Vera), Ubuntu Light (Ubuntu Font Licence 1.0), Noto Emoji Regular (SIL OFL 1.1) и emoji-icon-font (MIT) – перечислены в `THIRD_PARTY_LICENSES.md` с указанием, что где используется. Шрифты не изменяются: и условие reserved font name в OFL, и правило переименования в UFL срабатывают именно на модификацию, а здесь файлы встраиваются как опубликованы. Разрешение в `deny.toml` расширяет только типографику – обе лицензии не касаются кода, который их рисует.
   **Ворота на текст, а не на веру.** `this_build_can_draw_words` меряет ширину разложенной строки: без шрифта она равна нулю, и это тихий отказ – ни ошибки, ни паники, просто интерфейс без слов; там же проверяется, что длинное слово шире короткого, иначе измерялась бы константа. Рядом сквозной тест: подпись обязана дать больше геометрии после тесселяции, чем пустой кадр, потому что шрифт, который разложился, но не дал глифов, прошёл бы первую проверку и всё равно ничего не нарисовал. Оба теста headless. Попутно выяснено, что epaint паникует, если уронить `TexturesDelta` неприменённым – это ровно атлас шрифта, который обязан доехать до рендерера. Первый pixel-smoke показал, что app загружал и освобождал команды, но оставлял их записанными в delta, поэтому объект всё равно паниковал при уничтожении; теперь обе коллекции применяются через `drain`, а ворота требуют и вызова upload/free, и пустого остатка.
   **Панель видов заменила маркер:** семь кнопок с теми же горячими клавишами, из одного списка `VIEWS`, который теперь читает и keyboard binding, чтобы подпись на кнопке не разошлась с тем, что делает клавиша. Ревью нашло, что первая проводка оставила рядом отдельный `match 1..7`; он удалён, а отдельные ворота требуют, чтобы каждая напечатанная клавиша вернула именно свой вид. Панель возвращает выбранное и ничего не применяет – нажатие идёт через тот же reducer, что и клавиша, иначе камера двигалась бы из двух мест. Ручной smoke: окно, две коробки, панель с читаемыми подписями, resize и закрытие.
   **Срез 19F-1 сделан: headless loader.** `ferritecad-scene` – единственное место, знающее одновременно документ и viewport: read-only open, холодная перестройка, тесселяция, упаковка в `RenderSnapshot`. Ни окна, ни event loop, ни жёсткой связи с OCCT: ядро передаётся аргументом, поэтому весь путь проверяется против mock'а на трёх ОС без Open CASCADE, а сессию выбирает вызывающий. Кэш не читается намеренно – он экономит время, и картинка не должна зависеть от состояния файла-спутника.
   **Смотреть на документ – значит не трогать его.** Открытие идёт через `Document::open_read_only`: ни миграции схемы, ни изменения persistent pragma. Побайтового сравнения после загрузки для этого мало – на актуальной схеме `Document::open` тоже ничего не пишет, и мутация «заменить на `open`» первую версию ворот пережила. Настоящая разница видна на документе, который другая программа оставила в режиме WAL: read-only путь отказывает с внятным сообщением, а `open` переписал бы журнальный режим чужого файла и мог бы оставить рядом `-wal` и `-shm`. Ворота ставят копию плиты в WAL и требуют отказа при неизменных байтах и отсутствии спутников.
   **Shapes возвращаются на каждом пути.** Всё, что может отказать, выполняется внутри одного замыкания, после которого стоит единственный `release_all`. Ворота на отмену специально устроены так, чтобы утечка была возможна: ядро сначала успешно строит модель, и только потом отказывает – загрузчик, освобождавший shapes лишь на успешном выходе, прошёл бы все остальные тесты. Отдельно проверяется отмена **между телами**: ядро отвечает корректно и возвращает готовый меш, потому что контракт разрешает алгоритму доработать начатую единицу работы; заметить смену намерения обязан загрузчик, иначе он дотесселирует модель, которую уже никто не ждёт. Обе мутации – убрать `release_all`, убрать проверку отмены в цикле – роняют ворота.

Проверка настоящей геометрии OCCT 8.0.1 идёт третьим срезом, вместе с воротами на само окно.
   **Срез 19F-2 сделан: `ferritecad-viewer <file.fcad>`.** Документ читается в отдельном потоке, ответ приходит одним user event'ом, а `Renderer::prepare` и замена текущего snapshot'а происходят на UI-потоке. Окно открывается пустым и получает модель, когда модель готова: перестройка и тесселяция – секунды работы, и выполненные между двумя событиями они заморозили бы интерфейс ровно на это время. Ядро создаётся и уничтожается внутри worker'а – сессия принадлежит своему потоку, и брошенная загрузка не переживает свои shapes. Закрытие окна отменяет загрузку и **дожидается** worker'а: оставить его умирать вместе с процессом значило бы, что единственный путь, освобождающий геометрию, никем не проходится.
   **Замена атомарна, а ошибка сохраняет кадр.** Кандидаты камеры и GPU-сцены готовятся отдельно от текущих и присваиваются лишь после успеха обоих. Ревью нашло щель в первой версии: камера наводилась на новые габариты до `Renderer::prepare`, поэтому отказ upload оставлял старую геометрию с камерой, смотрящей на модель, которой на GPU нет. Отдельные ворота теперь отказывают upload после успешного framing и требуют, чтобы ни камера, ни долг кадра не изменились. Что ошибка значит для камеры – правило reducer'а и проверено там: успешная загрузка наводит камеру на новые габариты и требует кадр, неудачная не двигает ничего и не требует ничего, поэтому на экране остаётся то, что там было. Пустой документ камеру тоже не двигает – наводиться не на что, а придуманное расстояние до пустоты хуже прежнего положения.
   **Первый pixel-smoke нашёл непроверенный оконный pass.** Окно жило до прихода модели, но первый кадр с реальной геометрией падал валидацией wgpu: surface pipeline объявлял `[colour, None]`, что означает два attachment-slot'а, тогда как оконный render pass передаёт ровно один. Оконный pipeline теперь строит список длины один, а отдельный GPU-тест исполняет именно одноцветовой `draw_into` без pick-target; offscreen-путь с двумя target'ами остаётся прежним.
   **Ворота:** «окно не блокируется» проверено порядком, а не таймингом – загрузка удерживается на канале, и вызывающий поток обязан дойти до проверки раньше, чем она ответит; мутация «выполнить загрузку на месте» роняет тест за 5 секунд вместо того, чтобы его повесить. Плюс аргумент командной строки (один документ, ни ноля, ни двух), доставка ошибки наружу вместо проглатывания и три ворот reducer'а.    **Срез 19F-3 сделан: сохранённые STEP-импорты видны.** Импорт переоткрывается через `reopen_step_import`, каждое нарисованное definition тесселируется один раз, а размещения складываются в мировые до попадания в snapshot. Обе половины геометрии документа – перестроенные тела и импортированная сцена – живут в одной kernel-сессии и освобождаются в одном месте: на успехе, на ошибке и на отмене.
   **Ключевое измерение: рисуются только листья.** Сборка приходит и как definition, чей shape – весь compound, и как отдельные instance'ы того, что внутри. Замерено на настоящем OCCT: `BoltPattern` даёт 864 треугольника, ровно четыре `Bolt` по 216, а `OuterGroup` – 48 при 12 у `Cube`. Поэтому instance с детьми – структура, а не геометрия: он не рисуется, но его placement остаётся тем, в чём сидят дети. Обратный вариант нарисовал бы каждую сборку дважды, и заметить это по картинке почти невозможно.
   **Cold evaluator больше не отвергает документ с импортом, но и не молчит о нём.** У импортированного объекта нечего пересчитывать: его геометрия – байты, а чтение байтов требует importer'а, а не kernel'а, и заводить его в eval значило бы развернуть зависимость, которую проект держит однонаправленной. `RebuildResult::imports()` называет такие объекты, и `rebuild` печатает про них строку: отчёт, упомянувший только построенное, читался бы как «это всё, что в файле есть».
   **Чтение STEP приходит функцией, а не вторым объектом.** `GeometryKernel` – контракт ядра, `StepImporter` – контракт документа, и ни один shipped-крейт не смотрит из адаптера ядра обратно на документ. Передача ядра *в* функцию вместо захвата – то, что позволяет одному `&mut` удовлетворить оба контракта; документ без импортов её не вызывает вовсе.

Четыре мутации – рисовать контейнеры, игнорировать дерево, не отдавать импортированные shapes, красить всё одним цветом – роняют их. Вертикаль закрыта против OCCT 8.0.1: `import-step` шипнутой командой, загрузка как во viewer'е, кадр на GPU и подсчёт пикселей, откалиброванный пустой сценой в том же кадре, плюс pick, попадающий в куб. В pin-workflow GPU обязателен через `FERRITECAD_REQUIRE_GPU=1`: отсутствие адаптера роняет прогон, а не оставляет зелёный skip, который можно заметить только ручным чтением лога. Ревью также вернуло прежнюю границу loader'а через `dyn GeometryKernel`: функция чтения STEP остаётся передаваемой отдельно, но вызывающий не обязан знать конкретный тип ядра.
   **Срез 19F-4 сделан: повторное Open с поколениями.** Каждый запрос получает монотонный `LoadGeneration`, новый запрос отменяет предыдущий и **не ждёт** его: отмена – это просьба, ядро замечает её на следующей фиче, и всё это время окно иначе стояло бы замороженным. Ответ принимается только от текущего поколения; запоздалый кадр и запоздалая ошибка отбрасываются молча – жалоба «этот документ не открылся» про файл, который пользователь уже сменил, была бы жалобой не про тот файл. Брошенный worker не выбрасывается, а сохраняется: `drop` у `JoinHandle` отвязывает поток, а отвязанный worker владеет kernel-сессией, которую никто не дождётся. Завершённые присоединяются по `is_finished`, все оставшиеся – на выходе.
   **Ворота на гонки:** `A → B → ответ B → ответ A` и `A → B → ошибка A` – на экране остаётся B, и отброшенный ответ не просит кадр. Плюс монотонность поколений, отмена предыдущего без ожидания, присоединение завершённого без ожидания незавершённого и полная остановка на выходе. Пять мутаций роняют ворота; шестая – «отменять и ждать по одному вместо всех сразу» – не роняет, потому что это свойство времени, а не результата, и таймингового утверждения здесь не ставится. Ворота на выход считает сам worker, уже после того как заметил отмену: `stop_all`, который бы просто забыл потоки, добежал бы до проверки раньше них.
   **Диалог выбора файла: сначала замер, потом код.** `rfd 0.15` добирается до XDG-портала через `ashpd` и `zbus` – 72 крейта, включая целый async-рантайм и ICU. `rfd 0.17` говорит по протоколу портала сам: **два** крейта, `rfd` и `objc2-app-kit` на macOS, всё остальное уже есть через `wgpu` и `winit`. `cargo deny check` – advisories, bans, licenses, sources – зелёный. Фичи названы явно, как у `winit`: default, который однажды поменяется, – это дерево зависимостей, которое поменялось без чьего-либо решения. Диалог вызывается **после** публикации кадра: модальное окно крутит свой event loop, и открыть его, держа взятую texture поверхности, значило бы держать её всё время, пока пользователь ходит по папкам. Ревью нашло, что включённая ради parent identifier фича `wayland` не использовалась: без `set_parent` портал получал пустой идентификатор, а диалог жил отдельно от viewer'а и мог уйти за него. Теперь диалог создаётся только при живом окне и явно принадлежит ему на всех трёх платформах.
   **Срез 19F-5 сделан: строка состояния.** Небольшая машина состояний рядом с загрузками, а не отдельно от них: `Idle`, `Loading { generation, file }`, `Ready { file }`, `Failed { file, message }`. `Ready` наступает только после атомарной замены сцены и камеры – порядок в event loop'е «показать, затем объявить», и мутация, меняющая его местами, роняет ворота. `Failed` сохраняет прежнюю модель на экране и говорит, что случилось: раньше ошибка уходила только в stderr, которого у оконного приложения фактически нет.
   **Устаревший ответ не меняет ни сцену, ни строку.** Поколение хранится в самом `Loading`, поэтому отказ от опоздавшего ответа – один факт в одном месте, а не два одинаковых условия у двух вызывающих. Отмена диалога не делает ничего: `None` не порождает ни поколения, ни worker'а, ни изменения строки. Строка, которая изменилась, – это причина нарисовать кадр, и на пути неудачной загрузки единственная; отдельные ворота требуют, чтобы отброшенный ответ кадра не просил.
   **Ворота:** переход `Loading → Ready`, `Loading → Failed` с сохранением камеры, `A → B → поздний ответ A`, `A → B → ответ B → поздняя ошибка A`, отменённый диалог и имя документа без пути. Пять мутаций роняют их: объявить раньше кадра, забыть поколение в статусе, стартовать загрузку при отменённом диалоге, не сообщать об изменении строки и сообщать о нём всегда. Ревью нашло две щели в проводке: переход второго Open в `Loading` не просил кадр, поэтому старый `Ready` оставался видим до конца долгой загрузки; поздняя ошибка старого поколения не меняла строку, но печаталась в stderr до проверки поколения. Теперь старт и завершение проходят через app-boundary функции: только принятый переход просит кадр, и только принятая ошибка доходит до обоих каналов диагностики.
   **Срез 19F-6, часть первая: прогресс начал что-то значить.** Ядра сообщают 0.0 и 1.0 на *операцию*, поэтому сырой поток отчётов проходил бы 0→1 по разу на фичу, и «готово» было бы неотличимо от «готова первая деталь». Теперь `rebuild_cold` оборачивает sink и отдаёт отчёты ядра как долю **документа**, а `snapshot_of` делит шкалу на две фазы – постройка до `BUILDING`, отрисовка после, – и внутри отрисовки нарезает её по объектам. Шкала одна, монотонная, и заканчивается ровно один раз. Отчитываются только те пункты плана, о которых спрашивали ядро: расширить это до «каждый пункт плана» значило бы позволить progress-колбэку отменить перестройку раньше той работы, за которой он наблюдает, и это уронило существующие ворота на очистку кэша.
   **Срез 19F-6, часть вторая: прогресс по поколениям и Cancel.** У каждой загрузки свой relay: worker пишет в него новейшую долю, а event loop будит **один раз** – событие не несёт числа, потому что к моменту доставки оно уже устарело. Тысяча отчётов подряд оставляет за собой одно событие, и в нём новейшее значение, а не первое; последнее сказанное не теряется ни при каком порядке. Изменение меньше половины процента кадра не стоит.
   **Cancel возвращает окно к описанию того, что нарисовано.** Прежняя модель остаётся на экране, строка снова называет её, а брошенное чтение отвечает позже и отбрасывается как любой устаревший ответ. Если на экране ещё ничего не было – `Idle`, потому что объявить брошенный документ готовым хуже, чем не сказать ничего. Кнопка предлагается только когда есть что останавливать.
   **Ворота:** объединение отчётов (500 отчётов – одно пробуждение, читается новейшее), непотеря последнего значения, прогресс чужого поколения игнорируется, прогресс текущего двигает строку и просит кадр, Cancel сохраняет камеру и строку, Cancel на первой загрузке даёт `Idle`, кнопка отсутствует, когда останавливать нечего. Шесть мутаций роняют ворота, в том числе «игнорировать разбиение фаз» – она прошла первую версию scene-ворот, потому что те не замечали, что бар доходил до 100% на первом же меше. Ревью нашло ещё одну такую границу: один объект `ImportedStep` может содержать несколько leaf-definition, и первоначальная нарезка по объектам отдавала каждому их мешу весь диапазон объекта. Теперь этот диапазон дополнительно делится между уникальными leaf-definition; отдельный assembly-gate требует монотонности и единственного завершения при двух разных деталях внутри одного импорта.
   **Срез 19G-1 сделан: клик выбирает definition.** `ferritecad-scene` возвращает рядом со snapshot каталог `mesh index → Body(ObjectId) | ImportedDefinitionRef`: две половины одного ответа, и они намеренно врозь. Snapshot – это то, что рисует GPU, и он не переживает свою сессию; каталог – это то, что клик *значит*, сказанное так, как это мог бы хранить документ. Каталог сериализуется, `PickId` – нет и не будет: он привязан к identity одного snapshot'а и именно поэтому его безопасно выбрасывать.
   **Выделение живёт в globals, а не в per-draw uniform.** Все размещения одной definition несут одну и ту же identity, поэтому одно сравнение в шейдере покрывает их все – список, который рендерер держал бы в согласии с draw'ами, не нужен, и выбор ничего не переписывает из загруженного один раз. Pick из чужого snapshot'а не выбирает ничего: снимок, который сейчас рисуется, спрашивают, и неузнанный ответ становится «ничего». При замене документа selection сбрасывается отдельно: identity snapshot'а детерминирована содержимым, поэтому геометрически одинаковые документы могут иметь одну identity при разных записях каталога.
   **Клик – это нажатие и отпускание почти на одном месте.** Правило живёт в reducer'е: жест, который проехал больше `CLICK_SLOP`, был orbit'ом, а нажатие, забранное панелью, к модели вопросов не задаёт. Вопрос снимается тем, кто на него отвечает, поэтому offscreen-кадр рисуется один раз на клик, а не каждый кадр после него.
   **Ворота:** каталог совпадает по индексам со snapshot'ом и даёт один и тот же ответ для четырёх размещений; нативное тело названо своим объектом; запись каталога переживает round-trip; клик, drag, панель и потеря фокуса; фон снимает выбор; pick из прежней картинки не выбирает в новой. На GPU: выбор меняет **все** размещения выбранной definition и **не** трогает соседнюю; pick из чужой картинки не меняет ни пикселя. Вертикаль против OCCT 8.0.1 теперь проверяет и каталог: четыре куба сборки дают одну запись с ключом, который назвал сам файл. Ревью закрыл три щели в проводке: клик теперь сам просит кадр, в котором будет прочитан pick; новая сцена атомарно заменяет `PreparedSnapshot`, каталог и сброшенный selection, поэтому геометрически одинаковый другой документ не может принять старый `PickId`; `SceneItem` исчерпывающий, и новый вид сущности остановит компиляцию UI, пока не получит осмысленное имя, вместо молчаливого `None`.
   **Срез 19G-2 сделан: идентичность отделена от того, что читает человек.** Каталог сцены теперь `CatalogueEntry`: `item` – переносимая идентичность (`Body(ObjectId)` либо `Imported(ImportedDefinitionRef)`) и единственная часть, которая сериализуется; рядом лежат факты, собранные при загрузке, – имя, файл источника, число solid'ов. Совпадение по ним запрещено конструкцией: имена повторяются законно, и два тела с именем `Plate` остаются двумя телами, а `#5` в двух файлах – двумя определениями, различимыми только источником. Имя файла берётся последним компонентом даже если документ записал целый путь: подсказка для человека не должна выводить на экран чей-то домашний каталог.
   **Инспектор выделения в `ferritecad-ui` – только чтение и только переносимые роли.** Панель не знает ни документа, ни ядра: `Selected` перечисляет, какие факты бывают, а `rows()` собирает то, что действительно попадёт на экран, как данные – поэтому ворота читают текст, а не веру. В словаре типа нет роли для pick, mesh index, face, shape handle, session или occurrence. Обычный `&str` сам по себе не доказывает происхождение текста, поэтому путь отсекается раньше, на границе каталога сцены; отдельный тест проверяет и Unix-, и Windows-разделители. Имена из документа не фильтруются по словам: деталь законно может называться `Surface`. Пустой выбор говорит «Nothing selected», а не исчезает: пустая полоса неотличима от переставшего работать интерфейса.
   **Переходы состояния идут одним оператором.** `commit_scene` заменяет картинку, каталог, выбор и камеру вместе либо не трогает ничего: неудачная и отменённая загрузка сохраняют и модель, и сделанный в ней выбор, успешная – снимает выбор даже когда новый документ даёт байт-идентичную геометрию. Семантический выбор строится только двумя просмотрами – snapshot называет definition, каталог говорит, что это, – без поиска и без отката к имени.
   **Ворота:** факты нативного тела и импортированного definition; одинаковые имена остаются различимы по идентичности; один `definition_key` в двух источниках остаётся различим по источнику; четыре размещения дают один выбор; фон снимает и подсветку, и инспектор; успешная замена снимает выбор, неудачная сохраняет; сам инспектор не добавляет transient-роль или путь к контролируемым строкам, а имена из документа переносит без переосмысления. Семь мутаций роняют ворота: сохранить выбор при успешной замене, снять его при неудачной, разрешать выбор без обращения к текущему snapshot'у, дать всем файлам один источник, показать записанный путь целиком, добавить в инспектор строку с mesh index, убрать из него источник рядом с ключом.
   **Границы среза:** выбор не сохраняется в документ, схема и capability не менялись, occurrence-выбор и picking граней и рёбер не добавлялись, C++, FFI и мост OCCT не тронуты. Визуальное подтверждение на экране в этот срез не входило и не заявляется.
20. **[сделано]** Провести первый benchmark review и утвердить следующий срез. Корпус fillet/shell – 20 процедурных деталей с provenance, проходами через предел, B-Rep validation, детерминизмом и честными отказами на OCCT 8.0.1 трёх ОС. **Главная находка: `IsDone()` лжёт:** плита 60x40x10 при r=5.1 и r=6 даёт невалидную форму большего объёма, поэтому адаптер проверяет каждый результат через `BRepCheck_Analyzer` и не выдаёт handle при отказе. Solver-review завершён отдельно: нейтральный корпус до 208 уравнений, persistent constraint graph на drag, три неразрешимых случая и mapping native tags обратно в caller constraint indices. Оба кандидата проходят correctness-gate; baseline – planegcs из пиннутого FreeCAD 1.0.1 за широту уже реализованных sketch-ограничений, а не за неустойчивую разницу локальных микротаймингов. Решение зафиксировано в [ADR 0001](decisions/0001-sketch-solver.md); LM остаётся reference. Открыты масштабирование/разреженность, hardware profile и package/CI planegcs на Linux и Windows.

## 15. Чего не делать до beta

- не писать собственное B-Rep-ядро;
- не считать STEP редактируемым исходным форматом;
- не хранить ссылки как индексы граней;
- не принимать DWG/JT/IFC в scope без конкретного пользователя и бюджета;
- не заменять UI-фреймворк во время построения MVP;
- не начинать сборки и чертежи, пока не стабилизированы детали и topological naming;
- не объявлять performance победой без воспроизводимого замера и исходных данных.

## 16. Решения, принятые перед первым коммитом

Три вопроса, которые этот план оставлял открытыми, закрыты:

| Вопрос | Решение |
| --- | --- |
| Название и расширение | FerriteCAD, репозиторий `ferrite-cad`, crate'ы `ferritecad-*`, документ `.fcad`, кэш `.fcad-cache` |
| Целевые платформы | Windows, Linux и macOS – все три продуктовые и равноправные в CI |
| Источник тестового корпуса | Собственные процедурно сгенерированные детали и открыто лицензированные датасеты; происхождение STEP-файлов в `fixtures/step/PROVENANCE.md` |

Дополнительно, по итогам разбора самого плана, изменены три решения RFC: кэш вынесен в отдельный файл-спутник (§4.1), граница FFI строится плоским `extern "C"` шимом вместо `cxx`, а «временный внешний solver» конкретизирован как planegcs. Обоснования – в [архитектурном RFC](architecture-decisions.md).

Минимальные версии ОС остаются открытыми и определяются тем, что реально соберётся на этапе 0: для macOS это следствие выбора между universal binary и `lipo`, для Windows – выбранного MSVC runtime. Все остальные крупные решения зафиксированы в RFC и должны меняться только по результатам измерений этапа 0.
