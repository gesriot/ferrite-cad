# План реализации локального параметрического MCAD

**Статус:** рабочий план первой версии

**Горизонт:** от первого коммита до публичной beta параметрического part-моделлера

**Базовый документ:** [архитектурные решения](architecture-decisions.md)

## 1. Результат первой версии

Beta должна позволять пользователю:

1. создать эскиз на базовой плоскости;
2. задать базовые геометрические и размерные ограничения;
3. создать и изменить Extrude, Revolve, Cut, Fillet, Chamfer, Shell, Mirror и Pattern;
4. сохранить модель в нативный документ, открыть его на другой машине и перестроить без кэшей;
5. получить честную диагностическую ошибку при потерянной топологической ссылке;
6. импортировать и экспортировать STEP, экспортировать STL;
7. работать без заморозки интерфейса во время долгого перестроения.

Сборки, чертежи, ЕСКД, DXF и скриптинг не входят в этот результат. Нельзя называть beta «заменой SolidWorks»; корректное обещание – быстрый локальный параметрический моделлер деталей.

## 2. Принципы исполнения

- Каждый этап заканчивается работающим вертикальным срезом, а не набором библиотек.
- Ни одна фича не считается готовой без persistence, undo, тестов топологического именования и измерения производительности.
- Кэш ускоряет работу, но тесты регулярно запускают полное перестроение без него.
- Все ошибки ядра и потерянные ссылки видимы пользователю; неверный успешный результат хуже отказа.
- Внешние форматы являются входом/выходом, но не моделью редактирования.
- Новая зависимость добавляется только с лицензией, владельцем и причиной появления.

## 3. Рабочая структура репозитория

Предлагаемая структура Rust workspace:

```text
crates/
  ferritecad-types/          UUID, единицы, допуски, ошибки, канонические хэши   [есть]
  ferritecad-document/       IR, CBOR envelopes, SQLite, миграции, кэш-спутник   [есть]
  ferritecad-eval/           планирование и последовательный cold evaluator       [есть]
  ferritecad-kernel/         GeometryKernel trait и kernel-agnostic типы          [есть]
  ferritecad-occt/           Rust часть адаптера OCCT                            [есть]
  ferritecad-occt-bridge/    C++17 `extern "C"` шим и CMake-сборка               [есть]
  ferritecad-topology/       именование, разрешение ссылок, history mapping        [есть]
  ferritecad-sketch/         геометрия эскизов, ограничения и solver API
  ferritecad-tessellation/   LOD и перенос данных для GPU
  ferritecad-render/         wgpu, камера, ID picking, выделение
  ferritecad-exchange/       STEP/XDE и STL
  ferritecad-ui/             egui, команды, панели и взаимодействия
  ferritecad-app/            composition root, окно, настройки, telemetry opt-in
  ferritecad-cli/            create, inspect, validate, dump-graph, clear-cache   [есть]
  ferritecad-testkit/        тестовые модели, сравнения, профилирование
tests/
  corpus/             лицензированно чистые STEP и native fixtures
  topology/           сценарии сохранения/потери ссылок
  snapshots/          изображения и сериализованные результаты
docs/
```

Отметка `[есть]` означает crate, существующий в репозитории; остальные появляются в своём этапе.

Топологическая сортировка намеренно осталась в `ferritecad-document`: документ обязан уметь ответить на «в каком порядке это перестраивать» сам по себе, и `evaluation_order` уже покрыт тестами там. `ferritecad-eval` её переиспользует, а не дублирует, поэтому частичный план по построению является подпоследовательностью полного, а не вторым мнением о порядке. Хэши входов фич живут в `ferritecad-types` и `ferritecad-document` по той же причине – они часть определения объекта, а не планировщика. Последовательный cold evaluator уже исполняет полный план через `GeometryKernel`; отменяемый job scheduler остаётся отдельной работой после появления реального адаптера и модели владения kernel-сессиями у worker'ов.

Прямые зависимости допустимы только вниз: UI не знает OCCT, а document не знает UI и `TopoDS_Shape`. `ferritecad-occt-bridge` – единственное место, где используются заголовки OCCT.

## 4. Сквозные технические правила

### 4.1. Документ и миграции

- Применять `PRAGMA foreign_keys = ON` для каждого соединения: в SQLite это настройка соединения, выключенная по умолчанию, а не свойство файла.
- Любое изменение схемы – отдельная миграция с тестами upgrade и downgrade/readonly fallback. Миграция и запись её номера в `user_version` идут одной транзакцией.
- В `meta` хранить `format_version`, `minimum_reader_version`, UUID документа и единицы отображения; `capabilities` – денормализованный индекс обязательных возможностей. Перед предоставлением write-доступа сверять его с envelope-объявлениями: повреждённый индекс не имеет права сделать документ небезопасно записываемым.
- Payload фичи – CBOR envelope с вложенной byte string; неизвестные payload сохраняются как исходные байты и никогда не перекодируются.
- Сохранять обязательные данные и кэш в **разных файлах**: документ `.fcad`, спутник `.fcad-cache`. Удаление спутника не должно менять результат перестроения, и это проверяется тестом, который просто удаляет файл.
- Документ использует `journal_mode=DELETE` и `synchronous=FULL`, поэтому закрытый документ – один самодостаточный файл. WAL применяется только к спутнику кэша.
- `PRAGMA application_id` содержит `FCAD` для документа и `FCAC` для спутника; чужая SQLite-база отвергается до любой попытки её прочитать.

### 4.2. Хэширование и детерминизм

- Идентификаторы: UUIDv7 в 16-байтовом каноническом представлении.
- Хэши: BLAKE3 от канонической сериализации входов, версии алгоритма и допусков.
- Запретить NaN/Infinity, нормализовать отрицательный ноль и порядок неупорядоченных коллекций.
- Не сравнивать B-Rep по байтам между разными платформами; сравнивать семантический результат, число сущностей, допуски, объём, площадь, bbox и ожидаемые ссылки.

### 4.3. Ошибки и отмена

- Все публичные операции возвращают `Result<T, CadError>` с классификацией: input, constraint, topology, kernel, IO, cancellation, unsupported.
- FFI не допускает C++ исключений за границу вызова.
- Отмена не сохраняет частичный результат в документ или кэш.
- Неуспешное перестроение сохраняет последний корректный результат только для отображения, но помечает дерево фич ошибкой.

### 4.4. Лицензии и supply chain

- В первом коммите создать `LICENSE`, `THIRD_PARTY_LICENSES.md`, `deny.toml`, `SECURITY.md` и CI-проверку `cargo deny check`.
- Зафиксировать версии и checksums сторонних C/C++ архивов.
- Не добавлять GPL/AGPL-код в процесс приложения без отдельного решения по лицензии.
- Перед распространением включить notices OCCT, LGPL и инструкции по замене динамической библиотеки.

## 5. Этап 0 – подготовка и проверка рисков

**Оценка:** 2–4 недели для одного разработчика.

**Цель:** убрать неверные предположения до появления пользовательского UI.

### Работы

1. **[сделано]** Создать workspace, CI для Windows/Linux/macOS, форматирование, clippy, unit tests и проверку лицензий.
2. **[частично]** Собрать OCCT как динамические библиотеки на всех трёх платформах; зафиксировать тег, контрольную сумму, toolchain, CMake и способ упаковки DLL/SO/dylib. Сделано: OCCT `V8_0_1` собирается shared и проходит smoke-test 8/8 на Linux, Windows и macOS; тег, коммит, SHA-256, размер архива и тулчейн каждой платформы записаны в [build-occt.md](build-occt.md) по прогону [31254884697](https://github.com/gesriot/ferrite-cad/actions/runs/31254884697). Предыдущий кандидат `V8_0_0` прошёл те же три платформы в прогоне [31227437597](https://github.com/gesriot/ferrite-cad/actions/runs/31227437597). Осталось: способ упаковки библиотек в поставку, а для macOS – install name `@rpath`, выбор между universal binary и `lipo`, подпись и нотаризация. Ничего из этого прогоном не проверялось: он собирает и запускает, но не пакует.
3. **[сделано]** Собрать чистый C++ smoke-test: box, extrude, boolean, fillet, сериализация B-Rep, чтение/запись STEP через XDE, тесселяция. Реализация – [`tools/occt-smoke`](../tools/occt-smoke); 8/8 PASS на трёх платформах. Текущий STEP-вход – собственная синтетическая сборка `fixtures/step/canonical/02-flat-assembly.step`: имена, два цвета и миллиметры переживают чтение и круг записи/чтения через XDE.
4. **[сделано]** Сформировать легально доступный тестовый корпус: 20 деталей с агрессивными fillet/shell, 5–10 STEP-сборок, несколько повреждённых файлов. Геометрическая часть – 20 процедурных деталей, описанных параметрами прямо в `fillet_shell_corpus.rs`. STEP-часть – семь собственных AP242-моделей и пять детерминированно повреждённых вариантов в `fixtures/step`; для каждого из 14 артефактов записаны происхождение, размер и SHA-256 в [`PROVENANCE.md`](../fixtures/step/PROVENANCE.md), а обычный CI проверяет и суммы, и полноту списка. `tools/build-step-corpus` после чтения проверяет схему, исходные единицы, дерево definitions/instances, UTF-8-имена, placements, definition/instance colours и непустую валидную геометрию; pin-workflow требует одинаковый семантический манифест на OCCT 8.0.1 трёх ОС. STEP-байты не обязаны совпадать из-за недетерминированного порядка независимых цветовых сущностей writer'а. Старый Pro/ENGINEER fixture без записанного происхождения удалён и заменён синтетической сборкой. Корпус реальных файлов SolidWorks/NX/Creo с проверенными лицензиями остаётся отдельной interoperability-работой и этим пунктом не считается выполненным.
5. Создать бенчмарк-проект для OCCT: время, память, процент ошибок и валидность результата для каждой операции.
6. **[сделано]** Быстро прототипировать solver API на 200 ограничениях: собственный минимальный LM/Dogleg против planegcs. Изолированный стенд и общий корпус до 208 уравнений готовы; оба кандидата проходят общий предел невязки, отвергают три заведомо неразрешимых системы и называют ограничения в простом конфликте. Drag измеряется на 50 обновлениях одного target без перестройки constraint graph planegcs; setup, diagnose и шаги разделены. Planegcs начинает каждый шаг от gesture-start reference, LM – от предыдущего решения; это реальные семантики кандидатов, а не скрытая эквивалентность. Baseline – planegcs, решение и его обратимость записаны в [ADR 0001](decisions/0001-sketch-solver.md). Точные времена не считаются стабильным benchmark до появления hardware profile и повторного cold/warm протокола.
7. Записать hardware profile для бенчмарков: CPU, RAM, ОС, OCCT build flags, версия драйвера.

### Артефакты

- воспроизводимый build guide;
- `ferritecad benchmark-kernel`;
- CSV/JSON результатов и список непроходимых геометрических случаев;
- решение о baseline solver, подтверждённое измерениями;
- перечень обязательных внешних notices.

### Gate выхода

- **[пройден]** OCCT стабильно собирается и динамически грузится на Windows, Linux и macOS;
- **[пройден]** smoke-test читает и экспортирует минимум один STEP с именем и цветом;
- **[пройден]** известны пределы fillet/shell на воспроизводимом процедурном корпусе;
- **[пройден]** есть решение, которое не блокирует MVP: baseline solver – planegcs, собственный LM остаётся независимым reference-кандидатом.

Все четыре критерия gate этапа 0 пройдены. При этом список работ этапа ещё не исчерпан: не записан hardware profile; vendor-interoperability корпус требует реальных файлов и проверки лицензий; packaging planegcs на Linux/Windows и лицензионный комплект поставки остаются отдельной обязательной работой. Gate снимает архитектурные блокеры, но не превращает эти пункты в выполненные.

## 6. Этап 1 – фундамент модели и формата

**Оценка:** 3–5 недель.

**Цель:** получить маленький, но долговечный документ без UI.

### Работы

1. Реализовать базовые типы: `DocumentId`, `ObjectId`, `FeatureId`, `StableEntityId`, Quantity, Unit, Tolerance, Transform, `CadError`.
2. Реализовать SQLite schema v1 и транзакционный repository API.
3. Реализовать envelope CBOR и raw-preservation неизвестных объектов.
4. Реализовать объекты `Document`, `Body`, `Sketch`, `ExtrudeFeature`, `Parameter`, `TopologyRef` и таблицу зависимостей.
5. Реализовать загрузку, сохранение, миграцию и read-only режим для неподдерживаемых capability.
6. Реализовать канонический хэш параметров и входов фич.
7. Реализовать CLI: `inspect`, `validate`, `dump-graph`, `clear-cache`.

### Тесты

- создание → сохранение → загрузка → повторное сохранение;
- сохранение неизвестного CBOR payload без изменения байтов;
- невалидный UUID, цикл в DAG, отсутствующая зависимость, неверная единица;
- crash-safe тесты на искусственном прерывании записи;
- открытие документа после удаления всех кэш-таблиц.

### Gate выхода

CLI создаёт документ с эскизом и Extrude, валидирует его, сохраняет и открывает его с той же семантической IR. Старый reader открывает документ с неизвестной capability только read-only.

## 7. Этап 2 – ядро, DAG и первый вертикальный срез

**Оценка:** 5–8 недель.

**Цель:** `Sketch → Extrude → save → cold rebuild` без пользовательского UI.

### Работы

1. **[сделано]** Описать `GeometryKernel` и DTO, не содержащие OCCT-типов. Crate `ferritecad-kernel` зависит только от `ferritecad-types`: ни OCCT, ни C/C++, ни `build.rs`, ни FFI, ни document/eval. Определены identity ядра для cache key, плоский профиль с помеченными сегментами, extrude и transform, B-Rep blob, параметры тесселяции и mesh, история generated/modified/deleted, явные tolerance, отмена и progress. Handles ядра не сериализуются и привязаны к сессии. Mock-ядро на арифметике позволяет тестировать вышележащие слои без установленного OCCT.
2. **[частично]** Реализовать C++ bridge: создание профиля из 2D-контура, extrude, transform, тесселяция, B-Rep encode/decode и запрос history. Сделано: плоский `extern "C"` ABI с opaque-сессией, кодами состояния и caller-owned буферами; фиксированная ширина ABI-кодов, фактический `noexcept` на всех экспортируемых функциях и перехват `Standard_Failure`, `std::exception` и неизвестных исключений во всех fallible entry points. Реальный путь `Line/Arc профиль → Extrude → release` собирает солид, возвращает историю сторон через `BRepTools_History` и крышки через `FirstShape`/`LastShape`; повторное появление одного OCCT sub-shape получает тот же session-local id. `KernelIdentity` читает версию OCCT из библиотеки, а build-часть содержит полный BLAKE3-256 digest исходников моста, target и C++ toolchain. Проверено на пиннутой OCCT `V8_0_1` на всех трёх платформах прогоном [31275991427](https://github.com/gesriot/ferrite-cad/actions/runs/31275991427): 25 тестов адаптера против настоящей геометрии, а динамическая линковка подтверждена по самому тестовому бинарю – `libTKernel.so.8.0` на Linux, `TKernel.dll` на Windows, `@rpath/libTKernel.8.0.dylib` на macOS. Windows-имя DLL не содержит версии; там именно `8.0.1` подтверждают разрешённый pin с checksum и строка `OCC_VERSION_COMPLETE=8.0.1` запущенного smoke-test, а не вывод `dumpbin`. B-Rep encode/decode работает: бинарный формат OCCT через `BinTools`, обёрнутый собственным заголовком v2 с длиной и BLAKE3-256 checksum payload'а; проверка `KernelIdentity` перед декодированием, отказ на повреждённом, чужом, старом и более новом blob'е, cross-session roundtrip. Тесселяция возвращает positions/normals/indices и диапазоны треугольников на тех же face handles; location и orientation применяются в мосте. Каждый вызов очищает transient mesh до и после работы, поэтому результат зависит от своих deflection-параметров, а не от предыдущей сетки, и рисование не меняет сериализуемый B-Rep. Остался `transform` – сейчас он явно возвращает `Unsupported`.

   Важно: **декодированная форма несёт геометрию и ничего больше.** Формат B-Rep хранит форму, а не историю операций, которые её построили, поэтому у восстановленной формы нет ни боковых граней, ни крышек – мост отказывает на этих запросах, а не отвечает пустым списком, который слой именования прочитал бы как «фича ничего не произвела». Подключать warm cache к evaluator нельзя до задачи №14: только вместе с сохранённым mapping'ом топологии cache hit становится безопасным.
3. **[частично]** В `ferritecad-eval` реализовать dirty propagation и планирование перестроения. Сделано: обратный индекс зависимостей, транзитивный dirty set от нескольких корней, `RebuildPlan` с порядком и детерминированными уровнями параллелизма, facade `DocumentGraph` над `&Document`, честный отказ на цикле и висячем ребре. Осталось: отменяемый job scheduler. Cold evaluator из пункта 4 исполняет план последовательно; уровни параллелизма `RebuildPlan` вычисляются, но пока никем не исполняются, потому что сессия ядра не разделяема между потоками.
4. **[частично]** Реализовать feature evaluator для эскиза и extrude. Сделано: последовательный cold evaluator `rebuild_cold` в `ferritecad-eval`, работающий против `dyn GeometryKernel` и проверенный как на `MockKernel` без OCCT, так и на настоящем `OcctKernel` с сохранением/повторным открытием `.fcad`. Срез – `DatumPlane → Sketch → Extrude → Body`, один замкнутый внешний контур из Line/Arc, только `NewBody` и `Blind`/`Symmetric`. Сегменты эскиза упорядочиваются обходом цепочки, а не берутся в порядке хранения. Всё за пределами среза – `Circle`, точки, отверстия, несколько контуров, booleans, `ThroughAll`, неизвестные типы объектов – возвращает `Unsupported`, а не приближение. Перед обращением к ядру документ проходит semantic validation. Проверены детерминизм повторного и после переоткрытия документа перестроения, отмена до, посреди и на последнем progress-событии, а также освобождение всех shape handles, включая путь через ошибку. Осталось: инкрементальное перестроение по dirty set и отменяемый job scheduler. `rebuild_cached` перестраивает документ целиком и лишь пропускает вычисление тех фич, чей архив нашёлся, – это не инкрементальное перестроение.
5. **[частично]** Реализовать `ferritecad-topology`: выпуск семантических имён для эскиза и ExtrudeCap/ExtrudeSide, mapping истории и resolver. ### Критические тесты топологического именования

Для каждой из последовательностей ниже тест меняет параметр предшественника, очищает кэш и проверяет ожидаемый результат:

- высота Extrude меняется, ссылки на cap и стороны живы;
- профиль получает/теряет сегмент – ссылка либо остаётся семантически корректной, либо даёт явную ошибку;
- порядок обхода граней искусственно изменён в adapter fixture – результат не меняется;
- закоммиченная фикстура плиты даёт тот же манифест cardinality/uniqueness на mock и на OCCT;
- восстановление из документа не опирается на прежний `TopoDS_Shape`;
- нерешаемая ссылка не выбирает другую грань.

### Gate выхода

Одна модель с эскизом и extrude после полной очистки кэша воспроизводится из SQLite. Ссылка на грань extrude остаётся валидной после изменения высоты, а потерянная ссылка диагностируется явно.

## 10. Этап 5 – параметрические фичи и naming

**Оценка:** 6–12 месяцев; выпускать инкрементально.

**Цель:** реальная деталь, а не демонстрация.

Каждая фича проходит один и тот же lifecycle: typed data model → evaluator → семантические outputs → persistent naming → UI command → persistence/migration → unit/property/topology/performance tests → документация и sample.

| Волна | Фичи | Обязательные проверочные сценарии |
| --- | --- | --- |
| 5A | Extrude, Revolve, базовые datum planes, transform | изменение размеров профиля, смена направления, ссылки на caps/side faces |
| 5B | Boolean Cut/Fuse/Common, multi-body | split/merge, удаление входной грани, ссылки между телами |
| 5C | Fillet и Chamfer | цепочка рёбер, изменение радиуса, исчезновение ребра, корректная ошибка |
| 5D | Shell, Draft, Mirror, Linear/Circular Pattern | удалённая грань, инстансы, симметричные случаи, изменение количества |
| 5E | параметры, expressions, suppression, rollback, UI дерева | грязное распространение только на зависимые узлы, повторное включение фич |

Для boolean, fillet, chamfer и shell негативные тесты равноправны позитивным: операция может законно не строиться. Ошибка должна содержать feature ID, пользовательское имя, классификацию и, если возможно, подсказку, что изменить.

### Gate выхода

На тестовом наборе реальных деталей можно менять ранние параметры, получать корректное инкрементальное перестроение, экспортировать STEP/STL и не иметь молчаливого retargeting топологических ссылок.

## 13. Регистр рисков и реакция

| Риск | Ранний индикатор | Действие |
| --- | --- | --- |
| OCCT fillet/shell нестабилен | высокий процент ошибок на corpus | честные ограничения UI, минимальные reproducer, fallback/repair только после измерений |
| Naming даёт неверную грань | хотя бы один silent retargeting | блокировать фичу, добавить fixture; предпочесть явную ошибку |
| Собственный solver затягивается | не хватает базовых ограничений после оговорённого прототипа | зафиксировать временный solver за абстракцией, не тормозить viewer/format |
| Кэш-спутник разрастается | размер `.fcad-cache` растёт непропорционально модели | chunking есть с самого начала; далее eviction и GC по ключу, benchmark до оптимизации. Документ при этом не страдает: кэш – отдельный файл |
| UI блокируется ядром | P95 input latency растёт во время rebuild | обязательные worker jobs, отмена, immutable snapshots |
| FFI или OCCT рушит приложение | crash на импортируемом файле | minimal reproducer, exception boundary, затем worker process для рискованных путей |
| Scope creep | новая крупная подсистема до завершения P0/P1 | вести backlog отдельно; вход только через утверждённый gate |
| Лицензионный конфликт | зависимость без разрешённой лицензии | CI блокирует merge, разрешение документируется до добавления |

Важно не приписывать capability обратную совместимость, которой нет: бинарь с SQL schema target v2 отвергает v3 ещё до чтения envelope. `exchange.step.imported.v1` – более точный инструмент для читателя, который уже понимает schema v3, но не смысл конкретного imported-объекта: он сохраняет envelope байт в байт и открывает документ read-only. Многомегабайтные байты в CBOR `objects.payload` не кладутся; payload держит `source_id`, `content_hash`, `byte_len`, переносимую сцену, identity импортёра и его диагностику.
   **Достижимость – строка, а не поле в payload.** `imported_source_refs` связывает объект и источник с `ON DELETE CASCADE` со стороны объекта и `RESTRICT` со стороны байтов, поэтому SQLite снимает притязание даже с объекта, который этот build декодировать не умеет. Каждая успешная правка добирает источники, на которые никто не ссылается, но перед транзакцией проверяется согласованность известных imported payload'ов и reachability rows: повреждённая таблица ссылок блокирует запись, а не превращает потенциально восстанавливаемый orphan в окончательную потерю. Замена imported-объекта обычным снимает старое притязание; повторное использование content-addressed строки сравнивает не только записанный hash, но и фактические bytes/length. Документ с непонятым объектом открыт read-only и до сборки мусора не доходит. Источник неизменяем: другие байты – новый `source_id` и новый hash, а не правка под старой идентичностью; одинаковое содержимое хранится один раз.
   **Контракт связывания.** `Scene::persist()` даёт handle-free проекцию (`PersistedScene`), `PersistedScene::bind(current)` возвращает **только** переданную свежую сцену и только после позиционного сравнения всей проекции: unit, schema, количество и порядок definitions, name и solids каждой, всё дерево instances, definition/parent, имена, row-major 3x4 placement, colour source и linear RGB. Сравнение точное, без допуска: это проверка тождества повторного чтения уже проверенных байтов, а допуск разрешил бы связать реально сдвинувшийся placement. Имена не являются идентичностью – одинаковые имена законны, поэтому поиска «похожего» definition нет, а любая перестановка, изменившая переносимую проекцию, отвергается с указанием расхождения. Граница записана явно: две definitions с одинаковыми persisted-полями и полностью симметричными occurrences эта проекция различить не может. Durable-ссылок внутрь imported assembly пока нет; до их появления обязателен source-stable definition key из STEP/XDE, а не геометрический fallback. `ShapeHandle` не реализует `Serialize`; это проверено `const`-утверждением, а не обзором. Non-finite значения не проходят ни при decode, ни при persistence, `-0.0` канонизируется.
   **Порядок и транзакция.** Всё, что может отказать – чтение файла, проверка длины и BLAKE3, импорт, построение проекции, строгая сверка – заканчивается до `Document::write`. Rejected import не открывает транзакцию вовсе: у него нет сцены. Успешный импорт пишется одной транзакцией: байты, объект, притязание на байты, capability и метаданные. Отказ не меняет `.fcad` ни на байт и не двигает `modified_at`; байтовые ворота снимаются после того, как документ уже создан и открыт, потому что `Document::open` сам мигрирует и ставит persistent pragmas.
   **Две диагностики, а не одна.** `diagnostics_at_import` – историческое наблюдение, оно не перезаписывается; `diagnostics_now` – то, что сказало текущее чтение. Им соответствуют отдельные `imported_by` и `reopened_by`, поэтому текущий отчёт и свежие handles не остаются без provenance. Другая `KernelIdentity` сама по себе не запрещает открыть документ: `build` содержит target triple, и одна и та же версия на другой ОС отличается по построению. Identity – provenance; сверяется сцена. Отказ связывания освобождает все shapes, которые это чтение построило: иначе документ, который не открывается, тёк бы при каждой попытке.
   **Ворота.** Без OCCT: невозможность сериализовать handle, полнота проекции, связывание в другой session, отказ на перестановке/переименовании/solids/unit/schema/иерархии/placement/цвете, одинаковые имена без выбора «первого», миграция v2→v3 без потери объектов и topology refs, проверка hash/byte_len/BLOB, обнаружение порчи до вызова ядра, неизменность файла при отказе, отсутствие недостижимых байтов после удаления объекта, сохранение непонятого imported-объекта. Против настоящего OCCT: семь канонических файлов проходят import → save → close документа и session → open → новая session → reimport, handles заведомо другие, а имена, дерево, placements, цвета, единицы и solids совпадают; повреждённые, но импортируемые файлы сохраняют историческую диагностику и отдельно дают текущую; отвергнутые файлы не пишут ничего; несоответствие сохранённой сцены отказывается, а не привязывает похожее; на всех путях `live_shape_count` равен нулю. Закоммиченная фикстура плиты мигрирована в schema v3 на месте – все идентификаторы, payload'ы и хэши прежние, – потому что read-only путь отказывает немигрированному документу вместо чтения его как будто новые таблицы уже есть.
   **Срез 18C сделан.** `ferritecad import-step <файл.step> -o <документ.fcad>` – первый путь, на котором пользователь приносит чужой файл. Входной файл открывается один раз и только на чтение: он не переписывается, не нормализуется и не перемещается, что проверяется по байтам и по mtime после прогона. Документ строится в атомарно созданной приватной scratch-директории рядом с назначением и публикуется одним шагом – `hard_link` без `--force` даёт атомарный no-clobber, `rename` с `--force` – обычную замену old-or-new; ни один путь выхода не оставляет `.partial`. Директория резервирует namespace до того, как SQLite получает путь: одной проверки отсутствующего имени было бы недостаточно, потому что между ней и открытием можно подставить symlink. Логика публикации вынесена в общий `publish` и используется и экспортом STL, и импортом: детали здесь тонкие, а вторая копия – это второе место, где они разойдутся.
   **Три исхода, а не два.** Код 0 – документ записан и чтение ничего не сообщило; код 4 – документ записан целиком и чтение что-то сообщило; код 5 – не записано ничего. Скрипт различает их без разбора текста, и ни один из трёх не означает, что файл корректен. При коде 0 отчёт прямо говорит, что молчание описывает читателя, а не файл: на 8.0.1 один из повреждённых файлов переносится и не вызывает ни одной диагностики, оставаясь с испорченной координатой. Слов «корректен», «валиден» и «без проблем» в выводе нет, и это закреплено тестом. Исходные байты попадают в документ целиком, поэтому после импорта исходный файл можно удалить – тест это и делает, а затем читает документ. В `inspect` у импортированного объекта видно число definitions и placements, размер и имя источника, ядро-импортёр и сколько всего было сказано при импорте. Имя объекта по умолчанию берётся из имени файла и меняется `--name`; имена, которые файл дал своим частям, при этом не трогаются. В provenance пишется имя файла, а не путь: путь положил бы раскладку одной машины в документ, который должен переезжать, и всё равно никогда не открывается.

   **Результат: `PRODUCT_DEFINITION` присутствует, уникален и стабилен на десяти из одиннадцати файлов, дающих сцену.** Исключение – специально повреждённый файл со столкнувшимся идентификатором, описанный ниже; два файла, которые OCCT отвергает, сцены не дают, и ключа им не нужно. Идентификаторы совпадают на Linux, Windows и macOS и совпадают при повторном чтении тех же байтов вторым reader'ом. Путь до него типизированный, а не обход графа: вверх строго через `ADVANCED_BREP_SHAPE_REPRESENTATION` и `SHAPE_DEFINITION_REPRESENTATION`, затем вниз через проверенные поля и `PRODUCT_DEFINITION_SHAPE` до `PRODUCT_DEFINITION`; сборочная половина принимает только `NEXT_ASSEMBLY_USAGE_OCCURRENCE`, а не его общий базовый тип. Ограничить произвольный обход числом шагов было бы недостаточно: он всё ещё мог бы прийти в соседнюю деталь.
   **У сборки нет собственной геометрии, а значит нет и собственной сущности.** `shape entity` пригоден для всех definitions только в 4 файлах из 11 – то есть отсутствует именно на узлах, которые пользователь скорее всего и выберет. Сборка именуется через `NEXT_ASSEMBLY_USAGE_OCCURRENCE`: родитель, на котором сходятся все её компоненты. Две находки записаны как форма риска, а не как происшествия: одна сборка может содержать одну деталь несколько раз, и каждое размещение – своё occurrence (без схлопывания дубликатов корректная вложенная сборка выглядела неопознаваемой); две сборки с одинаковым набором компонентов по компонентам неразличимы, и probe в этом случае не выдаёт ключ, а не выбирает.
   **Что делает столкнувшийся идентификатор – измерено.** Добавлен воспроизводимый fixture `06-duplicate-product-definition.step`: `#31` записан дважды с разным содержимым (второй несёт formation и context другой детали), при этом все ссылки в файле по-прежнему разрешаются. Прежний `05-duplicate-entity-id.step` этот вопрос не задавал – он дублирует shape representation и дублирует идентично, так что неоднозначности нет. OCCT читает новый файл (`RetDone`), сообщает на загрузке `F: Ident defined SEVERAL TIMES : #31`, успешно переносит и выдаёт те же три узла с теми же объёмами, что и неповреждённая сборка. **Геометрия цела; потеряна идентичность.** Обе детали ключи сохраняют, а собственный ключ теряет сборка: occurrences её компонентов ссылаются на другой `#31`, поэтому родитель, на котором сходятся все компоненты, пуст, и probe не выдаёт ключ, а не выбирает между ними.
   **Это и есть режим отказа, под который надо проектировать, и он не тот, которого ждёшь.** Столкнувшийся идентификатор не даёт двух definitions с одним ключом – такое поймала бы проверка уникальности. Он даёт узел **без** ключа в файле, который импортируется и выглядит совершенно нормально. Значит §18D-2 обязан проверять полноту («у каждой definition есть ключ»), а не только уникальность; load-диагностика при этом доступна и объясняет причину, чего `04-corrupted-number.step` не даёт. Уникальность на произвольных vendor-файлах остаётся измерением на этом корпусе, а не свойством формата, поэтому обе проверки – на чтении.

Rust-сторона декодера проверяет то же самое повторно – она не может освободить shapes и потому слабее, но не даёт повреждённому буферу стать сценой.
   **Маршрут идентичности вынесен в общий заголовок** `crates/ferritecad-occt-bridge/src/step_identity.hpp` и включается и мостом, и `tools/step-key-probe`. Две копии сделали бы измерение утверждением о probe: при первом же расхождении ворота продолжали бы проходить, пока импортёр делает другое. Матрица ключей после выноса не изменилась ни на байт.
   **`06-duplicate-product-definition.step` больше не создаёт документ.** CLI `import-step` даёт код 5, ничего не пишет и говорит `identifying` – это отказ FerriteCAD, а не ядра. Ворота: ключи присутствуют, уникальны и совпадают при двух чтениях на семи канонических файлах; столкновение отвергается, диагностика ровно одна и со стадией identity, `live_shape_count` после отказа равен нулю; процессный тест CLI подтверждает, что каталог не изменился.
   **Срез 18D-2B-1 сделан.** Persisted scene **v2**: у definition появился `key`, а instance называет свой definition ключом, а не индексом. Индекс остался только у `parent` – и по праву: instance не то, что файл именует, это место, а порядок мест и есть дерево.
   **Связывание идёт по идентичности.** Множества ключей обязаны совпасть точно: перестановка проходит, исчезнувший, появившийся, переименованный и дублированный ключ – отказ с освобождением всех shapes. Проверено и на mock, и против настоящего OCCT: файл, прочитанный и затем описанный в обратном порядке, связывается, и каждое размещение получает именно ту деталь, которую называет.
   **v1 и v2 сравниваются одним кодом**, и вся разница между ними – что именно считается идентичностью definition: у v2 это ключ, у v1 позиция, потому что позиция – всё, что v1 когда-либо о них знал. Отсюда без отдельного правила следует, что перестановка отвергается в v1 и принимается в v2: переставленная v1-сцена действительно изменила единственное, что записала.
   **Legacy v1 продолжает открываться read-write**, связывается по позиции и записывается обратно тем же layout'ом: `StoredScene::keys()` возвращает `None`, а синтез ключа из позиции запрещён – получилось бы нечто, выглядящее идентичностью и ведущее себя как индекс. Payload-версия объекта берётся из самой сцены, а не из билда, поэтому v1-объект под v2-заголовком невозможен. Capability не менялась: старый билд видит незнакомый layout знакомого типа, сохраняет envelope дословно и ничего не теряет.
   **Срез 18D-2B-2 сделан.** `ImportedDefinitionRef { source_id, definition_key }` – один валидируемый тип, а не два поля, которые вызывающий обязан помнить сверить. Пустой ключ отвергается конструктором, и сохранённая ссылка проверяется при десериализации, а не считается верной за то, что раскодировалась.
   **Разрешение идёт внутри названного source и больше нигде.** Ссылка называет байты, к которым относится; чтение знает, из каких байтов оно получено; расхождение – отказ, а не поиск вокруг. Fallback по имени, позиции или ближайшему совпадению отсутствует как операция: ссылка, разрешившаяся во что-то правдоподобное, хуже неразрешившейся. Source и версия сохранённой сцены внутри `ReopenedStepImport` доступны только для чтения: вызывающий не может подменить source перед проверкой или объявить legacy v1-сцену версией v2 и разрешить ссылку по ключам, которые появились только при текущем чтении.
   **Три отказа – три разных факта, и они различаются по `ErrorKind`,** так что вызывающему не нужно разбирать текст: `Input` – ссылка про другой source (она не потеряна, она никогда не была про этот импорт); `Unsupported` – сцена v1, ключ не утрачен, его никогда не существовало, и синтез из позиции ответил бы на вопрос, на который документ не соглашался; `Topology` – тот самый source, и ничто в нём больше не несёт эту идентичность, то есть потерянная ссылка. Это ровно та классификация, которую §16C уже печатает как `invalid`/`unsupported`/`lost` с кодами 1/2/3.
   **Столкновение ключей взято из корпуса, а не придумано:** `01-single-part.step` и `02-flat-assembly.step` оба описывают `step.product_definition#5` – плиту и кронштейн. Ворота против настоящего OCCT: оба файла импортируются в один документ, документ и сессия закрываются, в новой сессии сборка переоткрывается, ссылка в свой source разрешается в свежий handle (заведомо не в прежний), ссылка с тем же ключом в чужой source отвергается, хотя definition с этим самым текстом лежит рядом, а неизвестный ключ даёт `Topology`. На всех путях `live_shape_count` равен нулю.
   **Occurrence path намеренно не включён.** У definition есть идентичность, записанная источником; у occurrence – только положение в дереве, и ссылка, смешавшая эти два уровня, выглядела бы durable, опираясь на индекс. Дальше viewport и vendor-interoperability корпус.
19. Поднять `wgpu` viewport с камерой и immutable mesh snapshot.
20. **[сделано]** Провести первый benchmark review и утвердить следующий срез. Корпус fillet/shell – 20 процедурных деталей с provenance, проходами через предел, B-Rep validation, детерминизмом и честными отказами на OCCT 8.0.1 трёх ОС. **Главная находка: `IsDone()` лжёт:** плита 60x40x10 при r=5.1 и r=6 даёт невалидную форму большего объёма, поэтому адаптер проверяет каждый результат через `BRepCheck_Analyzer` и не выдаёт handle при отказе. Solver-review завершён отдельно: нейтральный корпус до 208 уравнений, persistent constraint graph на drag, три неразрешимых случая и mapping native tags обратно в caller constraint indices. Оба кандидата проходят correctness-gate; baseline – planegcs из пиннутого FreeCAD 1.0.1 за широту уже реализованных sketch-ограничений, а не за неустойчивую разницу локальных микротаймингов. Решение зафиксировано в [ADR 0001](decisions/0001-sketch-solver.md); LM остаётся reference. Открыты масштабирование/разреженность, hardware profile и package/CI planegcs на Linux и Windows.

## 15. Чего не делать до beta

- не писать собственное B-Rep-ядро;
- не считать STEP редактируемым исходным форматом;
- не хранить ссылки как индексы граней;
- не принимать DWG/JT/IFC в scope без конкретного пользователя и бюджета;
- не заменять UI-фреймворк во время построения MVP;
- не начинать сборки и чертежи, пока не стабилизированы детали и topological naming;
- не объявлять performance победой без воспроизводимого замера и исходных данных.

## 16. Решения, принятые перед первым коммитом

Три вопроса, которые этот план оставлял открытыми, закрыты:

| Вопрос | Решение |
| --- | --- |
| Название и расширение | FerriteCAD, репозиторий `ferrite-cad`, crate'ы `ferritecad-*`, документ `.fcad`, кэш `.fcad-cache` |
| Целевые платформы | Windows, Linux и macOS – все три продуктовые и равноправные в CI |
| Источник тестового корпуса | Собственные процедурно сгенерированные детали и открыто лицензированные датасеты; происхождение STEP-файлов в `fixtures/step/PROVENANCE.md` |

Дополнительно, по итогам разбора самого плана, изменены три решения RFC: кэш вынесен в отдельный файл-спутник (§4.1), граница FFI строится плоским `extern "C"` шимом вместо `cxx`, а «временный внешний solver» конкретизирован как planegcs. Обоснования – в [архитектурном RFC](architecture-decisions.md).

Минимальные версии ОС остаются открытыми и определяются тем, что реально соберётся на этапе 0: для macOS это следствие выбора между universal binary и `lipo`, для Windows – выбранного MSVC runtime. Все остальные крупные решения зафиксированы в RFC и должны меняться только по результатам измерений этапа 0.
