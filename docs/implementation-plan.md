# План реализации локального параметрического MCAD

**Статус:** рабочий план первой версии

**Горизонт:** от первого коммита до публичной beta параметрического part-моделлера

**Базовый документ:** [архитектурные решения](architecture-decisions.md)

## 1. Результат первой версии

Beta должна позволять пользователю:

1. создать эскиз на базовой плоскости;
2. задать базовые геометрические и размерные ограничения;
3. создать и изменить Extrude, Revolve, Cut, Fillet, Chamfer, Shell, Mirror и Pattern;
4. сохранить модель в нативный документ, открыть его на другой машине и перестроить без кэшей;
5. получить честную диагностическую ошибку при потерянной топологической ссылке;
6. импортировать и экспортировать STEP, экспортировать STL;
7. работать без заморозки интерфейса во время долгого перестроения.

Сборки, чертежи, ЕСКД, DXF и скриптинг не входят в этот результат. Нельзя называть beta «заменой SolidWorks»; корректное обещание – быстрый локальный параметрический моделлер деталей.

## 2. Принципы исполнения

- Каждый этап заканчивается работающим вертикальным срезом, а не набором библиотек.
- Ни одна фича не считается готовой без persistence, undo, тестов топологического именования и измерения производительности.
- Кэш ускоряет работу, но тесты регулярно запускают полное перестроение без него.
- Все ошибки ядра и потерянные ссылки видимы пользователю; неверный успешный результат хуже отказа.
- Внешние форматы являются входом/выходом, но не моделью редактирования.
- Новая зависимость добавляется только с лицензией, владельцем и причиной появления.

## 3. Рабочая структура репозитория

Предлагаемая структура Rust workspace:

```text
crates/
  ferritecad-types/          UUID, единицы, допуски, ошибки, канонические хэши   [есть]
  ferritecad-document/       IR, CBOR envelopes, SQLite, миграции, кэш-спутник   [есть]
  ferritecad-eval/           планирование и последовательный cold evaluator       [есть]
  ferritecad-kernel/         GeometryKernel trait и kernel-agnostic типы          [есть]
  ferritecad-occt/           Rust часть адаптера OCCT                            [есть]
  ferritecad-occt-bridge/    C++17 `extern "C"` шим и CMake-сборка               [есть]
  ferritecad-topology/       именование, разрешение ссылок, history mapping        [есть]
  ferritecad-sketch/         геометрия эскизов, ограничения и solver API
  ferritecad-tessellation/   LOD и перенос данных для GPU
  ferritecad-render/         wgpu, камера, ID picking, выделение
  ferritecad-exchange/       STEP/XDE и STL
  ferritecad-ui/             egui, команды, панели и взаимодействия
  ferritecad-app/            composition root, окно, настройки, telemetry opt-in
  ferritecad-cli/            create, inspect, validate, dump-graph, clear-cache   [есть]
  ferritecad-testkit/        тестовые модели, сравнения, профилирование
tests/
  corpus/             лицензированно чистые STEP и native fixtures
  topology/           сценарии сохранения/потери ссылок
  snapshots/          изображения и сериализованные результаты
docs/
```

Отметка `[есть]` означает crate, существующий в репозитории; остальные появляются в своём этапе.

Топологическая сортировка намеренно осталась в `ferritecad-document`: документ обязан уметь ответить на «в каком порядке это перестраивать» сам по себе, и `evaluation_order` уже покрыт тестами там. `ferritecad-eval` её переиспользует, а не дублирует, поэтому частичный план по построению является подпоследовательностью полного, а не вторым мнением о порядке. Хэши входов фич живут в `ferritecad-types` и `ferritecad-document` по той же причине – они часть определения объекта, а не планировщика. Последовательный cold evaluator уже исполняет полный план через `GeometryKernel`; отменяемый job scheduler остаётся отдельной работой после появления реального адаптера и модели владения kernel-сессиями у worker'ов.

Прямые зависимости допустимы только вниз: UI не знает OCCT, а document не знает UI и `TopoDS_Shape`. `ferritecad-occt-bridge` – единственное место, где используются заголовки OCCT.

## 4. Сквозные технические правила

### 4.1. Документ и миграции

- Применять `PRAGMA foreign_keys = ON` для каждого соединения: в SQLite это настройка соединения, выключенная по умолчанию, а не свойство файла.
- Любое изменение схемы – отдельная миграция с тестами upgrade и downgrade/readonly fallback. Миграция и запись её номера в `user_version` идут одной транзакцией.
- В `meta` хранить `format_version`, `minimum_reader_version`, UUID документа и единицы отображения; `capabilities` – денормализованный индекс обязательных возможностей. Перед предоставлением write-доступа сверять его с envelope-объявлениями: повреждённый индекс не имеет права сделать документ небезопасно записываемым.
- Payload фичи – CBOR envelope с вложенной byte string; неизвестные payload сохраняются как исходные байты и никогда не перекодируются.
- Сохранять обязательные данные и кэш в **разных файлах**: документ `.fcad`, спутник `.fcad-cache`. Удаление спутника не должно менять результат перестроения, и это проверяется тестом, который просто удаляет файл.
- Документ использует `journal_mode=DELETE` и `synchronous=FULL`, поэтому закрытый документ – один самодостаточный файл. WAL применяется только к спутнику кэша.
- `PRAGMA application_id` содержит `FCAD` для документа и `FCAC` для спутника; чужая SQLite-база отвергается до любой попытки её прочитать.

### 4.2. Хэширование и детерминизм

- Идентификаторы: UUIDv7 в 16-байтовом каноническом представлении.
- Хэши: BLAKE3 от канонической сериализации входов, версии алгоритма и допусков.
- Запретить NaN/Infinity, нормализовать отрицательный ноль и порядок неупорядоченных коллекций.
- Не сравнивать B-Rep по байтам между разными платформами; сравнивать семантический результат, число сущностей, допуски, объём, площадь, bbox и ожидаемые ссылки.

### 4.3. Ошибки и отмена

- Все публичные операции возвращают `Result<T, CadError>` с классификацией: input, constraint, topology, kernel, rendering, IO, cancellation, unsupported.
- FFI не допускает C++ исключений за границу вызова.
- Отмена не сохраняет частичный результат в документ или кэш.
- Неуспешное перестроение сохраняет последний корректный результат только для отображения, но помечает дерево фич ошибкой.

### 4.4. Лицензии и supply chain

- В первом коммите создать `LICENSE`, `THIRD_PARTY_LICENSES.md`, `deny.toml`, `SECURITY.md` и CI-проверку `cargo deny check`.
- Зафиксировать версии и checksums сторонних C/C++ архивов.
- Не добавлять GPL/AGPL-код в процесс приложения без отдельного решения по лицензии.
- Перед распространением включить notices OCCT, LGPL и инструкции по замене динамической библиотеки.

## 5. Этап 0 – подготовка и проверка рисков

**Оценка:** 2–4 недели для одного разработчика.

**Цель:** убрать неверные предположения до появления пользовательского UI.

### Работы

1. **[сделано]** Создать workspace, CI для Windows/Linux/macOS, форматирование, clippy, unit tests и проверку лицензий.
2. **[частично]** Собрать OCCT как динамические библиотеки на всех трёх платформах; зафиксировать тег, контрольную сумму, toolchain, CMake и способ упаковки DLL/SO/dylib. Сделано: OCCT `V8_0_1` собирается shared и проходит smoke-test 8/8 на Linux, Windows и macOS; тег, коммит, SHA-256, размер архива и тулчейн каждой платформы записаны в [build-occt.md](build-occt.md) по прогону [31254884697](https://github.com/gesriot/ferrite-cad/actions/runs/31254884697). Предыдущий кандидат `V8_0_0` прошёл те же три платформы в прогоне [31227437597](https://github.com/gesriot/ferrite-cad/actions/runs/31227437597). Осталось: способ упаковки библиотек в поставку, а для macOS – install name `@rpath`, выбор между universal binary и `lipo`, подпись и нотаризация. Ничего из этого прогоном не проверялось: он собирает и запускает, но не пакует.
3. **[сделано]** Собрать чистый C++ smoke-test: box, extrude, boolean, fillet, сериализация B-Rep, чтение/запись STEP через XDE, тесселяция. Реализация – [`tools/occt-smoke`](../tools/occt-smoke); 8/8 PASS на трёх платформах. Текущий STEP-вход – собственная синтетическая сборка `fixtures/step/canonical/02-flat-assembly.step`: имена, два цвета и миллиметры переживают чтение и круг записи/чтения через XDE.
4. **[сделано]** Сформировать легально доступный тестовый корпус: 20 деталей с агрессивными fillet/shell, 5–10 STEP-сборок, несколько повреждённых файлов. Геометрическая часть – 20 процедурных деталей, описанных параметрами прямо в `fillet_shell_corpus.rs`. STEP-часть – семь собственных AP242-моделей и пять детерминированно повреждённых вариантов в `fixtures/step`; для каждого из 14 артефактов записаны происхождение, размер и SHA-256 в [`PROVENANCE.md`](../fixtures/step/PROVENANCE.md), а обычный CI проверяет и суммы, и полноту списка. `tools/build-step-corpus` после чтения проверяет схему, исходные единицы, дерево definitions/instances, UTF-8-имена, placements, definition/instance colours и непустую валидную геометрию; pin-workflow требует одинаковый семантический манифест на OCCT 8.0.1 трёх ОС. STEP-байты не обязаны совпадать из-за недетерминированного порядка независимых цветовых сущностей writer'а. Старый Pro/ENGINEER fixture без записанного происхождения удалён и заменён синтетической сборкой. Корпус реальных файлов SolidWorks/NX/Creo с проверенными лицензиями остаётся отдельной interoperability-работой и этим пунктом не считается выполненным.
5. Создать бенчмарк-проект для OCCT: время, память, процент ошибок и валидность результата для каждой операции.
6. **[сделано]** Быстро прототипировать solver API на 200 ограничениях: собственный минимальный LM/Dogleg против planegcs. Изолированный стенд и общий корпус до 208 уравнений готовы; оба кандидата проходят общий предел невязки, отвергают три заведомо неразрешимых системы и называют ограничения в простом конфликте. Drag измеряется на 50 обновлениях одного target без перестройки constraint graph planegcs; setup, diagnose и шаги разделены. Planegcs начинает каждый шаг от gesture-start reference, LM – от предыдущего решения; это реальные семантики кандидатов, а не скрытая эквивалентность. Baseline – planegcs, решение и его обратимость записаны в [ADR 0001](decisions/0001-sketch-solver.md). Точные времена не считаются стабильным benchmark до появления hardware profile и повторного cold/warm протокола.
7. Записать hardware profile для бенчмарков: CPU, RAM, ОС, OCCT build flags, версия драйвера.

### Артефакты

- воспроизводимый build guide;
- `ferritecad benchmark-kernel`;
- CSV/JSON результатов и список непроходимых геометрических случаев;
- решение о baseline solver, подтверждённое измерениями;
- перечень обязательных внешних notices.

### Gate выхода

- **[пройден]** OCCT стабильно собирается и динамически грузится на Windows, Linux и macOS;
- **[пройден]** smoke-test читает и экспортирует минимум один STEP с именем и цветом;
- **[пройден]** известны пределы fillet/shell на воспроизводимом процедурном корпусе;
- **[пройден]** есть решение, которое не блокирует MVP: baseline solver – planegcs, собственный LM остаётся независимым reference-кандидатом.

Все четыре критерия gate этапа 0 пройдены. При этом список работ этапа ещё не исчерпан: не записан hardware profile; vendor-interoperability корпус требует реальных файлов и проверки лицензий; packaging planegcs на Linux/Windows и лицензионный комплект поставки остаются отдельной обязательной работой. Gate снимает архитектурные блокеры, но не превращает эти пункты в выполненные.

## 6. Этап 1 – фундамент модели и формата

**Оценка:** 3–5 недель.

**Цель:** получить маленький, но долговечный документ без UI.

### Работы

1. Реализовать базовые типы: `DocumentId`, `ObjectId`, `FeatureId`, `StableEntityId`, Quantity, Unit, Tolerance, Transform, `CadError`.
2. Реализовать SQLite schema v1 и транзакционный repository API.
3. Реализовать envelope CBOR и raw-preservation неизвестных объектов.
4. Реализовать объекты `Document`, `Body`, `Sketch`, `ExtrudeFeature`, `Parameter`, `TopologyRef` и таблицу зависимостей.
5. Реализовать загрузку, сохранение, миграцию и read-only режим для неподдерживаемых capability.
6. Реализовать канонический хэш параметров и входов фич.
7. Реализовать CLI: `inspect`, `validate`, `dump-graph`, `clear-cache`.

### Тесты

- создание → сохранение → загрузка → повторное сохранение;
- сохранение неизвестного CBOR payload без изменения байтов;
- невалидный UUID, цикл в DAG, отсутствующая зависимость, неверная единица;
- crash-safe тесты на искусственном прерывании записи;
- открытие документа после удаления всех кэш-таблиц.

### Gate выхода

CLI создаёт документ с эскизом и Extrude, валидирует его, сохраняет и открывает его с той же семантической IR. Старый reader открывает документ с неизвестной capability только read-only.

## 7. Этап 2 – ядро, DAG и первый вертикальный срез

**Оценка:** 5–8 недель.

**Цель:** `Sketch → Extrude → save → cold rebuild` без пользовательского UI.

### Работы

1. **[сделано]** Описать `GeometryKernel` и DTO, не содержащие OCCT-типов. Crate `ferritecad-kernel` зависит только от `ferritecad-types`: ни OCCT, ни C/C++, ни `build.rs`, ни FFI, ни document/eval. Определены identity ядра для cache key, плоский профиль с помеченными сегментами, extrude и transform, B-Rep blob, параметры тесселяции и mesh, история generated/modified/deleted, явные tolerance, отмена и progress. Handles ядра не сериализуются и привязаны к сессии. Mock-ядро на арифметике позволяет тестировать вышележащие слои без установленного OCCT.
2. **[частично]** Реализовать C++ bridge: создание профиля из 2D-контура, extrude, transform, тесселяция, B-Rep encode/decode и запрос history. Сделано: плоский `extern "C"` ABI с opaque-сессией, кодами состояния и caller-owned буферами; фиксированная ширина ABI-кодов, фактический `noexcept` на всех экспортируемых функциях и перехват `Standard_Failure`, `std::exception` и неизвестных исключений во всех fallible entry points. Реальный путь `Line/Arc профиль → Extrude → release` собирает солид, возвращает историю сторон через `BRepTools_History` и крышки через `FirstShape`/`LastShape`; повторное появление одного OCCT sub-shape получает тот же session-local id. `KernelIdentity` читает версию OCCT из библиотеки, а build-часть содержит полный BLAKE3-256 digest исходников моста, target и C++ toolchain. Проверено на пиннутой OCCT `V8_0_1` на всех трёх платформах прогоном [31275991427](https://github.com/gesriot/ferrite-cad/actions/runs/31275991427): 25 тестов адаптера против настоящей геометрии, а динамическая линковка подтверждена по самому тестовому бинарю – `libTKernel.so.8.0` на Linux, `TKernel.dll` на Windows, `@rpath/libTKernel.8.0.dylib` на macOS. Windows-имя DLL не содержит версии; там именно `8.0.1` подтверждают разрешённый pin с checksum и строка `OCC_VERSION_COMPLETE=8.0.1` запущенного smoke-test, а не вывод `dumpbin`. B-Rep encode/decode работает: бинарный формат OCCT через `BinTools`, обёрнутый собственным заголовком v2 с длиной и BLAKE3-256 checksum payload'а; проверка `KernelIdentity` перед декодированием, отказ на повреждённом, чужом, старом и более новом blob'е, cross-session roundtrip. Тесселяция возвращает positions/normals/indices и диапазоны треугольников на тех же face handles; location и orientation применяются в мосте. Каждый вызов очищает transient mesh до и после работы, поэтому результат зависит от своих deflection-параметров, а не от предыдущей сетки, и рисование не меняет сериализуемый B-Rep. Остался `transform` – сейчас он явно возвращает `Unsupported`.

   Важно: **декодированная форма несёт геометрию и ничего больше.** Формат B-Rep хранит форму, а не историю операций, которые её построили, поэтому у восстановленной формы нет ни боковых граней, ни крышек – мост отказывает на этих запросах, а не отвечает пустым списком, который слой именования прочитал бы как «фича ничего не произвела». Подключать warm cache к evaluator нельзя до задачи №14: только вместе с сохранённым mapping'ом топологии cache hit становится безопасным.
3. **[частично]** В `ferritecad-eval` реализовать dirty propagation и планирование перестроения. Сделано: обратный индекс зависимостей, транзитивный dirty set от нескольких корней, `RebuildPlan` с порядком и детерминированными уровнями параллелизма, facade `DocumentGraph` над `&Document`, честный отказ на цикле и висячем ребре. Осталось: отменяемый job scheduler. Cold evaluator из пункта 4 исполняет план последовательно; уровни параллелизма `RebuildPlan` вычисляются, но пока никем не исполняются, потому что сессия ядра не разделяема между потоками.
4. **[частично]** Реализовать feature evaluator для эскиза и extrude. Сделано: последовательный cold evaluator `rebuild_cold` в `ferritecad-eval`, работающий против `dyn GeometryKernel` и проверенный как на `MockKernel` без OCCT, так и на настоящем `OcctKernel` с сохранением/повторным открытием `.fcad`. Срез – `DatumPlane → Sketch → Extrude → Body`, один замкнутый внешний контур из Line/Arc, только `NewBody` и `Blind`/`Symmetric`. Сегменты эскиза упорядочиваются обходом цепочки, а не берутся в порядке хранения. Всё за пределами среза – `Circle`, точки, отверстия, несколько контуров, booleans, `ThroughAll`, неизвестные типы объектов – возвращает `Unsupported`, а не приближение. Перед обращением к ядру документ проходит semantic validation. Проверены детерминизм повторного и после переоткрытия документа перестроения, отмена до, посреди и на последнем progress-событии, а также освобождение всех shape handles, включая путь через ошибку. Осталось: инкрементальное перестроение по dirty set и отменяемый job scheduler. `rebuild_cached` перестраивает документ целиком и лишь пропускает вычисление тех фич, чей архив нашёлся, – это не инкрементальное перестроение.
5. **[частично]** Реализовать `ferritecad-topology`: выпуск семантических имён для эскиза и ExtrudeCap/ExtrudeSide, mapping истории и resolver. ### Критические тесты топологического именования

Для каждой из последовательностей ниже тест меняет параметр предшественника, очищает кэш и проверяет ожидаемый результат:

- высота Extrude меняется, ссылки на cap и стороны живы;
- профиль получает/теряет сегмент – ссылка либо остаётся семантически корректной, либо даёт явную ошибку;
- порядок обхода граней искусственно изменён в adapter fixture – результат не меняется;
- закоммиченная фикстура плиты даёт тот же манифест cardinality/uniqueness на mock и на OCCT;
- восстановление из документа не опирается на прежний `TopoDS_Shape`;
- нерешаемая ссылка не выбирает другую грань.

### Gate выхода

Одна модель с эскизом и extrude после полной очистки кэша воспроизводится из SQLite. Ссылка на грань extrude остаётся валидной после изменения высоты, а потерянная ссылка диагностируется явно.

## 10. Этап 5 – параметрические фичи и naming

**Оценка:** 6–12 месяцев; выпускать инкрементально.

**Цель:** реальная деталь, а не демонстрация.

Каждая фича проходит один и тот же lifecycle: typed data model → evaluator → семантические outputs → persistent naming → UI command → persistence/migration → unit/property/topology/performance tests → документация и sample.

| Волна | Фичи | Обязательные проверочные сценарии |
| --- | --- | --- |
| 5A | Extrude, Revolve, базовые datum planes, transform | изменение размеров профиля, смена направления, ссылки на caps/side faces |
| 5B | Boolean Cut/Fuse/Common, multi-body | split/merge, удаление входной грани, ссылки между телами |
| 5C | Fillet и Chamfer | цепочка рёбер, изменение радиуса, исчезновение ребра, корректная ошибка |
| 5D | Shell, Draft, Mirror, Linear/Circular Pattern | удалённая грань, инстансы, симметричные случаи, изменение количества |
| 5E | параметры, expressions, suppression, rollback, UI дерева | грязное распространение только на зависимые узлы, повторное включение фич |

Для boolean, fillet, chamfer и shell негативные тесты равноправны позитивным: операция может законно не строиться. Ошибка должна содержать feature ID, пользовательское имя, классификацию и, если возможно, подсказку, что изменить.

### Gate выхода

На тестовом наборе реальных деталей можно менять ранние параметры, получать корректное инкрементальное перестроение, экспортировать STEP/STL и не иметь молчаливого retargeting топологических ссылок.

## 13. Регистр рисков и реакция

| Риск | Ранний индикатор | Действие |
| --- | --- | --- |
| OCCT fillet/shell нестабилен | высокий процент ошибок на corpus | честные ограничения UI, минимальные reproducer, fallback/repair только после измерений |
| Naming даёт неверную грань | хотя бы один silent retargeting | блокировать фичу, добавить fixture; предпочесть явную ошибку |
| Собственный solver затягивается | не хватает базовых ограничений после оговорённого прототипа | зафиксировать временный solver за абстракцией, не тормозить viewer/format |
| Кэш-спутник разрастается | размер `.fcad-cache` растёт непропорционально модели | chunking есть с самого начала; далее eviction и GC по ключу, benchmark до оптимизации. Документ при этом не страдает: кэш – отдельный файл |
| UI блокируется ядром | P95 input latency растёт во время rebuild | обязательные worker jobs, отмена, immutable snapshots |
| FFI или OCCT рушит приложение | crash на импортируемом файле | minimal reproducer, exception boundary, затем worker process для рискованных путей |
| Scope creep | новая крупная подсистема до завершения P0/P1 | вести backlog отдельно; вход только через утверждённый gate |
| Лицензионный конфликт | зависимость без разрешённой лицензии | CI блокирует merge, разрешение документируется до добавления |

Важно не приписывать capability обратную совместимость, которой нет: бинарь с SQL schema target v2 отвергает v3 ещё до чтения envelope. `exchange.step.imported.v1` – более точный инструмент для читателя, который уже понимает schema v3, но не смысл конкретного imported-объекта: он сохраняет envelope байт в байт и открывает документ read-only. Многомегабайтные байты в CBOR `objects.payload` не кладутся; payload держит `source_id`, `content_hash`, `byte_len`, переносимую сцену, identity импортёра и его диагностику.
   **Достижимость – строка, а не поле в payload.** `imported_source_refs` связывает объект и источник с `ON DELETE CASCADE` со стороны объекта и `RESTRICT` со стороны байтов, поэтому SQLite снимает притязание даже с объекта, который этот build декодировать не умеет. Каждая успешная правка добирает источники, на которые никто не ссылается, но перед транзакцией проверяется согласованность известных imported payload'ов и reachability rows: повреждённая таблица ссылок блокирует запись, а не превращает потенциально восстанавливаемый orphan в окончательную потерю. Замена imported-объекта обычным снимает старое притязание; повторное использование content-addressed строки сравнивает не только записанный hash, но и фактические bytes/length. Документ с непонятым объектом открыт read-only и до сборки мусора не доходит. Источник неизменяем: другие байты – новый `source_id` и новый hash, а не правка под старой идентичностью; одинаковое содержимое хранится один раз.
   **Контракт связывания.** `Scene::persist()` даёт handle-free проекцию (`PersistedScene`), `PersistedScene::bind(current)` возвращает **только** переданную свежую сцену и только после позиционного сравнения всей проекции: unit, schema, количество и порядок definitions, name и solids каждой, всё дерево instances, definition/parent, имена, row-major 3x4 placement, colour source и linear RGB. Сравнение точное, без допуска: это проверка тождества повторного чтения уже проверенных байтов, а допуск разрешил бы связать реально сдвинувшийся placement. Имена не являются идентичностью – одинаковые имена законны, поэтому поиска «похожего» definition нет, а любая перестановка, изменившая переносимую проекцию, отвергается с указанием расхождения. Граница записана явно: две definitions с одинаковыми persisted-полями и полностью симметричными occurrences эта проекция различить не может. Durable-ссылок внутрь imported assembly пока нет; до их появления обязателен source-stable definition key из STEP/XDE, а не геометрический fallback. `ShapeHandle` не реализует `Serialize`; это проверено `const`-утверждением, а не обзором. Non-finite значения не проходят ни при decode, ни при persistence, `-0.0` канонизируется.
   **Порядок и транзакция.** Всё, что может отказать – чтение файла, проверка длины и BLAKE3, импорт, построение проекции, строгая сверка – заканчивается до `Document::write`. Rejected import не открывает транзакцию вовсе: у него нет сцены. Успешный импорт пишется одной транзакцией: байты, объект, притязание на байты, capability и метаданные. Отказ не меняет `.fcad` ни на байт и не двигает `modified_at`; байтовые ворота снимаются после того, как документ уже создан и открыт, потому что `Document::open` сам мигрирует и ставит persistent pragmas.
   **Две диагностики, а не одна.** `diagnostics_at_import` – историческое наблюдение, оно не перезаписывается; `diagnostics_now` – то, что сказало текущее чтение. Им соответствуют отдельные `imported_by` и `reopened_by`, поэтому текущий отчёт и свежие handles не остаются без provenance. Другая `KernelIdentity` сама по себе не запрещает открыть документ: `build` содержит target triple, и одна и та же версия на другой ОС отличается по построению. Identity – provenance; сверяется сцена. Отказ связывания освобождает все shapes, которые это чтение построило: иначе документ, который не открывается, тёк бы при каждой попытке.
   **Ворота.** Без OCCT: невозможность сериализовать handle, полнота проекции, связывание в другой session, отказ на перестановке/переименовании/solids/unit/schema/иерархии/placement/цвете, одинаковые имена без выбора «первого», миграция v2→v3 без потери объектов и topology refs, проверка hash/byte_len/BLOB, обнаружение порчи до вызова ядра, неизменность файла при отказе, отсутствие недостижимых байтов после удаления объекта, сохранение непонятого imported-объекта. Против настоящего OCCT: семь канонических файлов проходят import → save → close документа и session → open → новая session → reimport, handles заведомо другие, а имена, дерево, placements, цвета, единицы и solids совпадают; повреждённые, но импортируемые файлы сохраняют историческую диагностику и отдельно дают текущую; отвергнутые файлы не пишут ничего; несоответствие сохранённой сцены отказывается, а не привязывает похожее; на всех путях `live_shape_count` равен нулю. Закоммиченная фикстура плиты мигрирована в schema v3 на месте – все идентификаторы, payload'ы и хэши прежние, – потому что read-only путь отказывает немигрированному документу вместо чтения его как будто новые таблицы уже есть.
   **Срез 18C сделан.** `ferritecad import-step <файл.step> -o <документ.fcad>` – первый путь, на котором пользователь приносит чужой файл. Входной файл открывается один раз и только на чтение: он не переписывается, не нормализуется и не перемещается, что проверяется по байтам и по mtime после прогона. Документ строится в атомарно созданной приватной scratch-директории рядом с назначением и публикуется одним шагом – `hard_link` без `--force` даёт атомарный no-clobber, `rename` с `--force` – обычную замену old-or-new; ни один путь выхода не оставляет `.partial`. Директория резервирует namespace до того, как SQLite получает путь: одной проверки отсутствующего имени было бы недостаточно, потому что между ней и открытием можно подставить symlink. Логика публикации вынесена в общий `publish` и используется и экспортом STL, и импортом: детали здесь тонкие, а вторая копия – это второе место, где они разойдутся.
   **Три исхода, а не два.** Код 0 – документ записан и чтение ничего не сообщило; код 4 – документ записан целиком и чтение что-то сообщило; код 5 – не записано ничего. Скрипт различает их без разбора текста, и ни один из трёх не означает, что файл корректен. При коде 0 отчёт прямо говорит, что молчание описывает читателя, а не файл: на 8.0.1 один из повреждённых файлов переносится и не вызывает ни одной диагностики, оставаясь с испорченной координатой. Слов «корректен», «валиден» и «без проблем» в выводе нет, и это закреплено тестом. Исходные байты попадают в документ целиком, поэтому после импорта исходный файл можно удалить – тест это и делает, а затем читает документ. В `inspect` у импортированного объекта видно число definitions и placements, размер и имя источника, ядро-импортёр и сколько всего было сказано при импорте. Имя объекта по умолчанию берётся из имени файла и меняется `--name`; имена, которые файл дал своим частям, при этом не трогаются. В provenance пишется имя файла, а не путь: путь положил бы раскладку одной машины в документ, который должен переезжать, и всё равно никогда не открывается.

   **Результат: `PRODUCT_DEFINITION` присутствует, уникален и стабилен на десяти из одиннадцати файлов, дающих сцену.** Исключение – специально повреждённый файл со столкнувшимся идентификатором, описанный ниже; два файла, которые OCCT отвергает, сцены не дают, и ключа им не нужно. Идентификаторы совпадают на Linux, Windows и macOS и совпадают при повторном чтении тех же байтов вторым reader'ом. Путь до него типизированный, а не обход графа: вверх строго через `ADVANCED_BREP_SHAPE_REPRESENTATION` и `SHAPE_DEFINITION_REPRESENTATION`, затем вниз через проверенные поля и `PRODUCT_DEFINITION_SHAPE` до `PRODUCT_DEFINITION`; сборочная половина принимает только `NEXT_ASSEMBLY_USAGE_OCCURRENCE`, а не его общий базовый тип. Ограничить произвольный обход числом шагов было бы недостаточно: он всё ещё мог бы прийти в соседнюю деталь.
   **У сборки нет собственной геометрии, а значит нет и собственной сущности.** `shape entity` пригоден для всех definitions только в 4 файлах из 11 – то есть отсутствует именно на узлах, которые пользователь скорее всего и выберет. Сборка именуется через `NEXT_ASSEMBLY_USAGE_OCCURRENCE`: родитель, на котором сходятся все её компоненты. Две находки записаны как форма риска, а не как происшествия: одна сборка может содержать одну деталь несколько раз, и каждое размещение – своё occurrence (без схлопывания дубликатов корректная вложенная сборка выглядела неопознаваемой); две сборки с одинаковым набором компонентов по компонентам неразличимы, и probe в этом случае не выдаёт ключ, а не выбирает.
   **Что делает столкнувшийся идентификатор – измерено.** Добавлен воспроизводимый fixture `06-duplicate-product-definition.step`: `#31` записан дважды с разным содержимым (второй несёт formation и context другой детали), при этом все ссылки в файле по-прежнему разрешаются. Прежний `05-duplicate-entity-id.step` этот вопрос не задавал – он дублирует shape representation и дублирует идентично, так что неоднозначности нет. OCCT читает новый файл (`RetDone`), сообщает на загрузке `F: Ident defined SEVERAL TIMES : #31`, успешно переносит и выдаёт те же три узла с теми же объёмами, что и неповреждённая сборка. **Геометрия цела; потеряна идентичность.** Обе детали ключи сохраняют, а собственный ключ теряет сборка: occurrences её компонентов ссылаются на другой `#31`, поэтому родитель, на котором сходятся все компоненты, пуст, и probe не выдаёт ключ, а не выбирает между ними.
   **Это и есть режим отказа, под который надо проектировать, и он не тот, которого ждёшь.** Столкнувшийся идентификатор не даёт двух definitions с одним ключом – такое поймала бы проверка уникальности. Он даёт узел **без** ключа в файле, который импортируется и выглядит совершенно нормально. Значит §18D-2 обязан проверять полноту («у каждой definition есть ключ»), а не только уникальность; load-диагностика при этом доступна и объясняет причину, чего `04-corrupted-number.step` не даёт. Уникальность на произвольных vendor-файлах остаётся измерением на этом корпусе, а не свойством формата, поэтому обе проверки – на чтении.

Rust-сторона декодера проверяет то же самое повторно – она не может освободить shapes и потому слабее, но не даёт повреждённому буферу стать сценой.
   **Маршрут идентичности вынесен в общий заголовок** `crates/ferritecad-occt-bridge/src/step_identity.hpp` и включается и мостом, и `tools/step-key-probe`. Две копии сделали бы измерение утверждением о probe: при первом же расхождении ворота продолжали бы проходить, пока импортёр делает другое. Матрица ключей после выноса не изменилась ни на байт.
   **`06-duplicate-product-definition.step` больше не создаёт документ.** CLI `import-step` даёт код 5, ничего не пишет и говорит `identifying` – это отказ FerriteCAD, а не ядра. Ворота: ключи присутствуют, уникальны и совпадают при двух чтениях на семи канонических файлах; столкновение отвергается, диагностика ровно одна и со стадией identity, `live_shape_count` после отказа равен нулю; процессный тест CLI подтверждает, что каталог не изменился.
   **Срез 18D-2B-1 сделан.** Persisted scene **v2**: у definition появился `key`, а instance называет свой definition ключом, а не индексом. Индекс остался только у `parent` – и по праву: instance не то, что файл именует, это место, а порядок мест и есть дерево.
   **Связывание идёт по идентичности.** Множества ключей обязаны совпасть точно: перестановка проходит, исчезнувший, появившийся, переименованный и дублированный ключ – отказ с освобождением всех shapes. Проверено и на mock, и против настоящего OCCT: файл, прочитанный и затем описанный в обратном порядке, связывается, и каждое размещение получает именно ту деталь, которую называет.
   **v1 и v2 сравниваются одним кодом**, и вся разница между ними – что именно считается идентичностью definition: у v2 это ключ, у v1 позиция, потому что позиция – всё, что v1 когда-либо о них знал. Отсюда без отдельного правила следует, что перестановка отвергается в v1 и принимается в v2: переставленная v1-сцена действительно изменила единственное, что записала.
   **Legacy v1 продолжает открываться read-write**, связывается по позиции и записывается обратно тем же layout'ом: `StoredScene::keys()` возвращает `None`, а синтез ключа из позиции запрещён – получилось бы нечто, выглядящее идентичностью и ведущее себя как индекс. Payload-версия объекта берётся из самой сцены, а не из билда, поэтому v1-объект под v2-заголовком невозможен. Capability не менялась: старый билд видит незнакомый layout знакомого типа, сохраняет envelope дословно и ничего не теряет.
   **Срез 18D-2B-2 сделан.** `ImportedDefinitionRef { source_id, definition_key }` – один валидируемый тип, а не два поля, которые вызывающий обязан помнить сверить. Пустой ключ отвергается конструктором, и сохранённая ссылка проверяется при десериализации, а не считается верной за то, что раскодировалась.
   **Разрешение идёт внутри названного source и больше нигде.** Ссылка называет байты, к которым относится; чтение знает, из каких байтов оно получено; расхождение – отказ, а не поиск вокруг. Fallback по имени, позиции или ближайшему совпадению отсутствует как операция: ссылка, разрешившаяся во что-то правдоподобное, хуже неразрешившейся. Source и версия сохранённой сцены внутри `ReopenedStepImport` доступны только для чтения: вызывающий не может подменить source перед проверкой или объявить legacy v1-сцену версией v2 и разрешить ссылку по ключам, которые появились только при текущем чтении.
   **Три отказа – три разных факта, и они различаются по `ErrorKind`,** так что вызывающему не нужно разбирать текст: `Input` – ссылка про другой source (она не потеряна, она никогда не была про этот импорт); `Unsupported` – сцена v1, ключ не утрачен, его никогда не существовало, и синтез из позиции ответил бы на вопрос, на который документ не соглашался; `Topology` – тот самый source, и ничто в нём больше не несёт эту идентичность, то есть потерянная ссылка. Это ровно та классификация, которую §16C уже печатает как `invalid`/`unsupported`/`lost` с кодами 1/2/3.
   **Столкновение ключей взято из корпуса, а не придумано:** `01-single-part.step` и `02-flat-assembly.step` оба описывают `step.product_definition#5` – плиту и кронштейн. Ворота против настоящего OCCT: оба файла импортируются в один документ, документ и сессия закрываются, в новой сессии сборка переоткрывается, ссылка в свой source разрешается в свежий handle (заведомо не в прежний), ссылка с тем же ключом в чужой source отвергается, хотя definition с этим самым текстом лежит рядом, а неизвестный ключ даёт `Topology`. На всех путях `live_shape_count` равен нулю.
   **Occurrence path намеренно не включён.** У definition есть идентичность, записанная источником; у occurrence – только положение в дереве, и ссылка, смешавшая эти два уровня, выглядела бы durable, опираясь на индекс. Дальше viewport и vendor-interoperability корпус.
19. **[частично]** Поднять `wgpu` viewport с камерой и immutable mesh snapshot.
   **Срез 19A сделан (view-only, без GPU).** `ferritecad-viewport` превращает меши и размещения в то, что может нарисовать GPU: упакованный неизменяемый `RenderSnapshot`, `Camera`, переживающая resize, и draw list в определённом порядке. Крейт не зависит ни от документа, ни от OCCT и не имеет зависимости, которая позволила бы: только `ferritecad-kernel` (словарь `Mesh`) и `ferritecad-types`.
   **Pick называет definition, а не размещение.** Четыре болта в плите – это одна definition и четыре draw'а, и клик по любому даёт один и тот же `PickId`. Информация, позволяющая различить размещения, до результата pick'а просто не доходит – не отфильтрована в конце, а не переносится вовсе, поэтому никакая последующая правка не начнёт её ронять случайно. Причина та же, что и в §18D-2B: у definition есть идентичность, записанная исходным файлом, а у occurrence – только позиция в дереве, которую следующий импорт волен перенумеровать. Occurrence path намеренно не создан, поэтому viewport не может превратить instance index в сохраняемую ссылку.
   **Pick не является форматом хранения:** у крейта нет прямой зависимости для сериализации, и `PickId` не реализует соответствующий трейт. При этом его raw `u32` намеренно доступен для GPU pick-буфера, поэтому вызывающий технически может записать число сам; такое число имеет смысл только вместе с тем snapshot, который его отрисовал. Readback обязан удерживать именно этот snapshot, а durable selection начинается с identity definition в документе, не с `PickId`.
   **Ворота (headless, без графики):** упаковка в interleaved position+normal с проверкой смещений и bounds; отказ на меше, который GPU не смог бы нарисовать (индекс за пределами, не-конечные позиция или нормаль, переполнение при сужении `f64` в `f32` или при vertex transform); композиция размещений на три уровня вглубь и мировые bounds по всем восьми углам, а не по двум; пустой размещённый mesh не создаёт extent; отказ на forward reference родителя; детерминированный порядок draw'ов – два построения одной модели дают побайтово равный список, и порядок не сортируется по мешу; pick называет definition и никогда размещение, а уже декодированный `PickId` не может молча перенацелиться в другом snapshot; значение pick-буфера вне диапазона попадает в фон; viewport нулевого размера даёт конечные матрицы (aspect = 1, `is_drawable()` = false) для трёх вырожденных размеров; framing одной точки и отказ на бессмысленном боксе; все восемь углов модели остаются внутри wgpu clip volume, в том числе в портретном viewport; пустой snapshot не выдумывает extent.
   **Первый wgpu smoke не вошёл в 19A, но прежний supply-chain блокер уже снят upstream.** Проверенный тогда `wgpu 27` тянул `paste` с RUSTSEC-2024-0436 (unmaintained), поэтому исключение в `deny.toml` намеренно не добавлялось. На 2026-08-12 актуальный `wgpu 30.0.0` больше не содержит `paste`; его полный трёхплатформенный graph отдельно проходит фактический `deny.toml` проекта (`advisories`, `bans`, `licenses`, `sources`), а MSRV крейта 1.87 ниже MSRV проекта 1.90.
   **Срез 19B сделан.** `ferritecad-viewport-gpu` рисует snapshot на настоящем устройстве, off screen: цветовой, глубинный и pick target'ы, минимальный WGSL и readback. Ни окна, ни `egui` – их отсутствие и есть то, что делает срез проверяемым: всё, что здесь утверждается, утверждается о кадре, а не о том, как он попал на экран.
   **`wgpu 30.0.0` проходит проектный `deny.toml` без исключений:** `paste` (RUSTSEC-2024-0436) в графе больше нет, все четыре проверки cargo-deny чистые; граф вырос с 89 до 179 крейтов. Это ровно тот случай, ради которого §19A остановился и не стал добавлять исключение – версия решила вопрос сама.
   **Кадр держит именно тот snapshot, которым отрисован.** `Frame::pick_at` разрешает pick против него, а не против «текущего», поэтому чтение pick-буфера чужим snapshot'ом невозможно не по договорённости, а потому, что кадр и его snapshot нельзя разделить. Это тот же класс ошибки, который §19A закрыл на уровне `PickId`, и здесь он закрыт на уровне владения.
   **Ворота (9 smoke-тестов; пропуск разрешён только когда adapter отсутствует, а не когда найденный adapter отказал в device):** snapshot доходит до цветового target'а в том канале, в котором был задан; pick-буфер возвращает те же идентичности, что были в него положены, а фон читается как `NOTHING`, а не как definition ноль; оба размещения одной definition рисуются в разных половинах кадра и дают один и тот же pick – проверка сканированием, а не по угаданным координатам; кадр не разрешается против другого snapshot'а; viewport нулевого размера даёт пустой кадр, а размер больше device limits отвергается до GPU allocation; пустой snapshot даёт очищенный кадр, а не отказ; normal под non-uniform scale освещается так же, как эквивалентная геометрия с запечённым transform; два кадра одного snapshot'а побайтово равны – утверждение не о GPU вообще, а о том, что в этом рендерере нет ни времени, ни счётчика кадров, ни обхода чего-либо неупорядоченного.
   **Две находки при сборке записаны там, где их встретят:** layout uniform'а в WGSL и в Rust обязан совпадать точно – `vec3<u32>` выравнивается на 16 и растянул бы структуру со 96 до 112 байт, поэтому padding – три скаляра; а квадрат в плоскости XY при камере, смотрящей вдоль +Y, виден с ребра и неотличим от «ничего не нарисовалось», что стоило одного ложного диагноза. `.wgsl` добавлен в проверку лицензионных заголовков: шейдер, вынесенный из репозитория, иначе не несёт лицензии вовсе.
   **Срез 19C сделан.** `PreparedSnapshot` держит резидентные GPU-буферы: `Renderer::prepare` загружает геометрию один раз, а повторные кадры пишут матрицу и гоняют pass, не трогая вершины. Проверяется не на слово: `Renderer::geometry_uploads()` открыт наружу ровно затем, чтобы «загружено один раз» можно было утверждать снаружи, как `live_shape_count` у адаптера ядра, и тест рисует десять кадров с десяти разных камер, требуя, чтобы счётчик не сдвинулся и чтобы картинки при этом различались – иначе тест прошёл бы, ничего не доказав.
   **Три вещи viewport'а теперь принадлежат тому, чем они на самом деле являются:** смысл модели – `RenderSnapshot`, её буферы – `PreparedSnapshot`, одно её прочтение – `Frame`. `PreparedSnapshot` принадлежит подготовившему его `Renderer` (`RendererId` устроен как `SessionId` ядра и по той же причине), и чужой renderer отказывается его рисовать вместо того, чтобы лезть в память другого устройства; отказ – по имени, а не как ошибка драйвера вдали от причины. Старый `Frame` продолжает разрешать picks против своего snapshot'а: тест рисует две модели, у которых raw pick равен 1 в обеих, и требует, чтобы каждый кадр отвечал про свою.
   **Срез 19D сделан.** Интерактивная камера – чистые операции над `Camera` в `ferritecad-viewport`, без `winit` и `egui`: `orbit`, `pan`, `zoom`, `look_from` со стандартными видами и изометрией. Что означает перетаскивание, решено и проверено до того, как что-либо начнёт эти события доставлять, поэтому §19E останется тонким.
   **Что закреплено.** Orbit сохраняет расстояние и точку интереса, применяет yaw и pitch по отдельности и упирается чуть ниже полюса: ровно на вертикали ось up и направление взгляда параллельны, бокового вектора нет, и вид перевернулся бы вокруг оси, которой пользователь не касался. Pan двигает eye и target вместе и ровно на те пиксели, которые ему дали, – измерено по экрану в NDC, а не через `world_per_pixel`, иначе тест соглашался бы с любым ответом функции, которую проверяет. Zoom экспоненциальный и обратимый, никогда не доходит до цели и тянет за собой near/far: камера, приблизившаяся в сто раз с плоскостью отсечения там, где её оставил framing, обрезала бы ровно то, к чему приблизилась. `frame` теперь сохраняет направление: «покажи целиком» – это не «и спереди».
   **Плановый вид имеет сторону.** Сверху и снизу мировая ось up совпадает с направлением взгляда и как up не годится, поэтому эти виды несут свою: север вверх, а низ – зеркало верха, а не его поворот. Проверяется по картинке: точка севернее центра обязана оказаться выше центра экрана и не сместиться вбок. Orbit определён вокруг мировой оси up и восстанавливает её, иначе каждый drag докручивал бы крен.
   **Ворота проверены мутациями.** 28 headless-тестов; каждая из четырнадцати внесённых поломок – снятый clamp, проигнорированный yaw, перепутанные оси pan, инвертированный zoom, потерянный множитель в `world_per_pixel`, framing, возвращающий вид спереди, – роняет ворота. Три первые редакции тестов проходили при снятом clamp, при проигнорированном yaw и при `world_per_pixel` без расстояния; они переписаны так, чтобы измерять угол и экран, а не знак и не самих себя. Ревью добавило ещё две численные границы: недоступен весь viewport, если нулевое любое измерение, а не только высота; длина направления считается устойчивым `hypot`, поэтому большая, но представимая в `f32` модель не превращает расстояние в бесконечность. Жест, чей следующий pose или GPU matrix переполнился бы, не применяется частично.
   **Срез 19E-1 сделан.** Выделена граница surface. `Renderer::for_surface` просит адаптер, умеющий выводить именно в эту поверхность, а `Renderer::new` – любой, умеющий считать: на машине может быть несколько адаптеров, и первый считающий не всегда связан с дисплеем, на котором окно. Раньше оконный путь взял бы headless-адаптер и упал бы позже, внутри драйвера, с сообщением ни о том, ни о другом.
   **`WindowSurface` владеет жизненным циклом:** формат и alpha-режим берутся из возможностей самой поверхности, `resize` переконфигурирует, нулевой размер деконфигурирует (окно свёрнуто – это обычное состояние, а не ошибка), а размер больше предела устройства обрезается, а не отвергается: окно такое, какое есть, и отказ рисовать оставил бы его пустым.
   **Решения вынесены в функции над значениями и проверены без окна.** `recovery_for` отвечает на каждый ответ поверхности: `Lost`/`Outdated` – переконфигурировать и повторить ровно один раз (второй повтор не помог бы, а цикл повесил бы event loop); `Timeout`/`Occluded` – пропустить кадр, оба состояния проходят сами; `Validation` – ошибка самой программы, которую повтор только спрятал бы. `Suboptimal` рисуется, а не выбрасывается, и переконфигурируется после показа: картинка верна, разошлась конфигурация, и выброшенный кадр показал бы пользователю рывок ради того, чего он не видит.
   **Идентичности в окно не пишутся.** Кадр окна рисуется десятки раз в секунду, а pick запрашивают по клику, поэтому платить за второе на каждом первом – платить постоянно за то, что нужно изредка; picking идёт через offscreen-путь с той же камерой. Пайплайн собирается по формату, в который рисуют, но из одного определения: вторая копия стала бы вторым местом, где разъедутся vertex layout, depth state и правило отсечения. Проверка «чужой `PreparedSnapshot`» тоже одна на оба пути.
   **Ворота:** 6 headless-тестов решений (нулевой и запредельный размер, все пять ответов поверхности, две последовательности после единственного retry и ownership устройства) плюс прежние 12 GPU smoke; семь исходных мутаций – разрешённый нулевой размер, необрезанный размер, `Lost`/`Timeout`/`Occluded` как фатальные, `Validation` как повторяемая – все роняют ворота. Ревью добавило восьмую: `Lost -> Suboptimal` обязан нарисовать полученный кадр и переконфигурировать после него; прежняя проверка отдельных ответов этого нарушения state machine не видела. `WindowSurface` также хранит `RendererId`: resize и present с другим устройством отказывают до изменения состояния или получения texture, а не падают позже в драйвере. Самого окна здесь нет намеренно: ни одна платформа CI не может открыть его в тесте (на Linux нет дисплея, на macOS event loop только в главном потоке), поэтому `winit` приходит в **19E-2** вместе с event loop и `egui`. Замерено заранее: `winit 0.30` без `wayland-csd-adwaita` проходит `deny.toml` без исключений (иначе тянет `ttf-parser`, RUSTSEC-2026-0192) и добавляет 113 крейтов.
   **Срез 19E-2 начат: frame-composition seam.** Поверхность выдаёт одну текстуру на кадр, поэтому окно с моделью и интерфейсом поверх обязано делить именно её: сначала модель, затем интерфейс, и только потом публикация. `WindowSurface::begin` – этот шов; overlay, взявший свою текстуру, просил бы второй кадр, а отработавший после `present` рисовал бы в то, что уже на экране. `WindowSurface::present` остался целым кадром там, где над моделью ничего нет, и собран из того же шва, поэтому оба пути приобретают и переконфигурируют одинаково.
   **Заимствование делает работу, а не украшает.** `SurfaceFrame` держит `&mut WindowSurface`, пока жив, поэтому окно нельзя переконфигурировать при незакрытой текстуре – а wgpu документирует `configure` в этот момент как панику, то есть заимствование превращает падение в ошибку компиляции. Ворота – два `compile_fail` doctest: незакрытый frame не даёт resize, а неочищенный frame не открывает texture view; рядом `no_run`-двойник правильной последовательности. Оба негативных теста проверены обратными мутациями, при которых запрещённая программа начинает собираться и ворота краснеют. Ревью сделало порядок структурным: только `SurfaceFrame::draw_scene(self)` выдаёт `ComposedSurfaceFrame`, и только второй открывает `view` overlay и позволяет `present`; поэтому интерфейс нельзя нарисовать до очищающей сцены, а сцену нельзя вызвать повторно и стереть интерфейс. `begin` заимствует вместе с surface и её `Renderer`, а следующие состояния больше не принимают renderer параметром: texture устройства A нельзя нарисовать или опубликовать через устройство B даже теоретически; overlay получает ссылки на правильные device/queue/view из одного состояния. `present` потребляет кадр, потому что текстура публикуется ровно один раз, а переконфигурация после `Suboptimal` происходит уже после того, как texture ушла.
   **Срез 19E-2 сделан.** `ferritecad-ui` – чистый reducer ввода: события идут внутрь, `Camera` двигается, кадр запрашивается. Ни окна, ни surface, ни renderer, ни event loop в сигнатурах нет, поэтому каждое правило – тест, а не «попробуй руками». `ferritecad-app` владеет окном, event loop'ом и surface, и в нём остаётся только проводка.
   **Интерфейсу дано право первого отказа.** Каждое событие приходит с флагом «интерфейс уже хочет это»; флаг соблюдается в reducer'е, потому что «был ли этот клик для панели» – правило о смысле приложения, а не о том, как toolkit докладывает события. Захваченное событие не двигает камеру и не начинает жест, но **позицию указателя всё равно обновляет**: иначе после прохода курсора над панелью первый же drag прыгнул бы на её ширину. Начатый в viewport'е жест интерфейс не отбирает – модель не должна замирать, когда курсор пересёк панель, и это отдельные ворота.
   **Один размер на обе стороны:** `resize` задаёт камеру и возвращает то, чем настраивать surface, поэтому разойтись они не могут; камера с одним соотношением сторон в surface с другим растянула бы модель. **Redraw схлопывается на обеих границах:** reducer объединяет смысловые причины, а `FrameScheduler` отдельно гарантирует один фактический `Window::request_redraw` до начала кадра. Первая проводка снимала флаг и тут же ставила его обратно после каждого события, поэтому полагалась только на необязательное coalescing самой платформы; четыре headless-ворота планировщика ловят эту щель, выбор самого раннего срока и отмену таймера немедленным кадром. `egui::request_repaint_after` будит `ControlFlow::WaitUntil` через user event, поэтому анимация не застывает в спящем loop и не требует polling; первый кадр запрашивается явно после `resumed`. Потеря фокуса завершает жест и забывает прежнюю позицию: ОС не обязана прислать отпускание кнопки окну, которое уже потеряло фокус.
   **Кадр композируется в порядке, который держит тип, а не комментарий:** `begin → draw_scene → egui в загруженный view → present`, одна текстура на кадр. Ручной smoke: окно открывается, показывает фиксированную сцену из двух коробок, переживает resize и закрытие. Документ и OCCT – следующим срезом, после доказанного event loop.
   **Решение по шрифту принято: встроенный набор `egui`.** Системный шрифт дал бы разный интерфейс и покрытие символов на трёх ОС, а свой vendored-файл повторил бы ту же лицензионную обязанность отдельным asset'ом. Следующий срез включает `default_fonts`, разрешает OFL-1.1 и Ubuntu-font-1.0 в `deny.toml`, записывает конкретные шрифты и право их распространения в `THIRD_PARTY_LICENSES.md` и кладёт оба полных текста лицензий в поставку. Одного прохождения `cargo deny` недостаточно: приложение встраивает font software в бинарь, а обе лицензии требуют сохранить свои условия при распространении. До этого прямоугольник-маркер остаётся честным доказательством композиции без текста.
   **Срез 19E-3 сделан: решение исполнено.** Встроенные шрифты `egui` включены, `deny.toml` разрешает `OFL-1.1` и `Ubuntu-font-1.0` только как exception для проверенного `epaint_default_fonts` 0.36.1, а не глобально: иной крейт и даже обновление набора обязаны пройти новое ревью. Обе – шрифтовые лицензии: они разрешают встраивать шрифт в приложение и распространять вместе с ним, ничего не требуют от самого кода, но требуют, чтобы условия сопровождали шрифт. Поэтому полные тексты скопированы дословно в `licences/fonts/` из того самого крейта, что несёт файлы, а не заменены ссылкой, которая может переехать.
   **Что именно встроено:** Hack Regular (MIT, с вкладом DejaVu в public domain и уведомлением Bitstream Vera), Ubuntu Light (Ubuntu Font Licence 1.0), Noto Emoji Regular (SIL OFL 1.1) и emoji-icon-font (MIT) – перечислены в `THIRD_PARTY_LICENSES.md` с указанием, что где используется. Шрифты не изменяются: и условие reserved font name в OFL, и правило переименования в UFL срабатывают именно на модификацию, а здесь файлы встраиваются как опубликованы. Разрешение в `deny.toml` расширяет только типографику – обе лицензии не касаются кода, который их рисует.
   **Ворота на текст, а не на веру.** `this_build_can_draw_words` меряет ширину разложенной строки: без шрифта она равна нулю, и это тихий отказ – ни ошибки, ни паники, просто интерфейс без слов; там же проверяется, что длинное слово шире короткого, иначе измерялась бы константа. Рядом сквозной тест: подпись обязана дать больше геометрии после тесселяции, чем пустой кадр, потому что шрифт, который разложился, но не дал глифов, прошёл бы первую проверку и всё равно ничего не нарисовал. Оба теста headless. Попутно выяснено, что epaint паникует, если уронить `TexturesDelta` неприменённым – это ровно атлас шрифта, который обязан доехать до рендерера. Первый pixel-smoke показал, что app загружал и освобождал команды, но оставлял их записанными в delta, поэтому объект всё равно паниковал при уничтожении; теперь обе коллекции применяются через `drain`, а ворота требуют и вызова upload/free, и пустого остатка.
   **Панель видов заменила маркер:** семь кнопок с теми же горячими клавишами, из одного списка `VIEWS`, который теперь читает и keyboard binding, чтобы подпись на кнопке не разошлась с тем, что делает клавиша. Ревью нашло, что первая проводка оставила рядом отдельный `match 1..7`; он удалён, а отдельные ворота требуют, чтобы каждая напечатанная клавиша вернула именно свой вид. Панель возвращает выбранное и ничего не применяет – нажатие идёт через тот же reducer, что и клавиша, иначе камера двигалась бы из двух мест. Ручной smoke: окно, две коробки, панель с читаемыми подписями, resize и закрытие.
   **Срез 19F-1 сделан: headless loader.** `ferritecad-scene` – единственное место, знающее одновременно документ и viewport: read-only open, холодная перестройка, тесселяция, упаковка в `RenderSnapshot`. Ни окна, ни event loop, ни жёсткой связи с OCCT: ядро передаётся аргументом, поэтому весь путь проверяется против mock'а на трёх ОС без Open CASCADE, а сессию выбирает вызывающий. Кэш не читается намеренно – он экономит время, и картинка не должна зависеть от состояния файла-спутника.
   **Смотреть на документ – значит не трогать его.** Открытие идёт через `Document::open_read_only`: ни миграции схемы, ни изменения persistent pragma. Побайтового сравнения после загрузки для этого мало – на актуальной схеме `Document::open` тоже ничего не пишет, и мутация «заменить на `open`» первую версию ворот пережила. Настоящая разница видна на документе, который другая программа оставила в режиме WAL: read-only путь отказывает с внятным сообщением, а `open` переписал бы журнальный режим чужого файла и мог бы оставить рядом `-wal` и `-shm`. Ворота ставят копию плиты в WAL и требуют отказа при неизменных байтах и отсутствии спутников.
   **Shapes возвращаются на каждом пути.** Всё, что может отказать, выполняется внутри одного замыкания, после которого стоит единственный `release_all`. Ворота на отмену специально устроены так, чтобы утечка была возможна: ядро сначала успешно строит модель, и только потом отказывает – загрузчик, освобождавший shapes лишь на успешном выходе, прошёл бы все остальные тесты. Отдельно проверяется отмена **между телами**: ядро отвечает корректно и возвращает готовый меш, потому что контракт разрешает алгоритму доработать начатую единицу работы; заметить смену намерения обязан загрузчик, иначе он дотесселирует модель, которую уже никто не ждёт. Обе мутации – убрать `release_all`, убрать проверку отмены в цикле – роняют ворота.

Проверка настоящей геометрии OCCT 8.0.1 идёт третьим срезом, вместе с воротами на само окно.
   **Срез 19F-2 сделан: `ferritecad-viewer <file.fcad>`.** Документ читается в отдельном потоке, ответ приходит одним user event'ом, а `Renderer::prepare` и замена текущего snapshot'а происходят на UI-потоке. Окно открывается пустым и получает модель, когда модель готова: перестройка и тесселяция – секунды работы, и выполненные между двумя событиями они заморозили бы интерфейс ровно на это время. Ядро создаётся и уничтожается внутри worker'а – сессия принадлежит своему потоку, и брошенная загрузка не переживает свои shapes. Закрытие окна отменяет загрузку и **дожидается** worker'а: оставить его умирать вместе с процессом значило бы, что единственный путь, освобождающий геометрию, никем не проходится.
   **Замена атомарна, а ошибка сохраняет кадр.** Кандидаты камеры и GPU-сцены готовятся отдельно от текущих и присваиваются лишь после успеха обоих. Ревью нашло щель в первой версии: камера наводилась на новые габариты до `Renderer::prepare`, поэтому отказ upload оставлял старую геометрию с камерой, смотрящей на модель, которой на GPU нет. Отдельные ворота теперь отказывают upload после успешного framing и требуют, чтобы ни камера, ни долг кадра не изменились. Что ошибка значит для камеры – правило reducer'а и проверено там: успешная загрузка наводит камеру на новые габариты и требует кадр, неудачная не двигает ничего и не требует ничего, поэтому на экране остаётся то, что там было. Пустой документ камеру тоже не двигает – наводиться не на что, а придуманное расстояние до пустоты хуже прежнего положения.
   **Первый pixel-smoke нашёл непроверенный оконный pass.** Окно жило до прихода модели, но первый кадр с реальной геометрией падал валидацией wgpu: surface pipeline объявлял `[colour, None]`, что означает два attachment-slot'а, тогда как оконный render pass передаёт ровно один. Оконный pipeline теперь строит список длины один, а отдельный GPU-тест исполняет именно одноцветовой `draw_into` без pick-target; offscreen-путь с двумя target'ами остаётся прежним.
   **Ворота:** «окно не блокируется» проверено порядком, а не таймингом – загрузка удерживается на канале, и вызывающий поток обязан дойти до проверки раньше, чем она ответит; мутация «выполнить загрузку на месте» роняет тест за 5 секунд вместо того, чтобы его повесить. Плюс аргумент командной строки (один документ, ни ноля, ни двух), доставка ошибки наружу вместо проглатывания и три ворот reducer'а.    **Срез 19F-3 сделан: сохранённые STEP-импорты видны.** Импорт переоткрывается через `reopen_step_import`, каждое нарисованное definition тесселируется один раз, а размещения складываются в мировые до попадания в snapshot. Обе половины геометрии документа – перестроенные тела и импортированная сцена – живут в одной kernel-сессии и освобождаются в одном месте: на успехе, на ошибке и на отмене.
   **Ключевое измерение: рисуются только листья.** Сборка приходит и как definition, чей shape – весь compound, и как отдельные instance'ы того, что внутри. Замерено на настоящем OCCT: `BoltPattern` даёт 864 треугольника, ровно четыре `Bolt` по 216, а `OuterGroup` – 48 при 12 у `Cube`. Поэтому instance с детьми – структура, а не геометрия: он не рисуется, но его placement остаётся тем, в чём сидят дети. Обратный вариант нарисовал бы каждую сборку дважды, и заметить это по картинке почти невозможно.
   **Cold evaluator больше не отвергает документ с импортом, но и не молчит о нём.** У импортированного объекта нечего пересчитывать: его геометрия – байты, а чтение байтов требует importer'а, а не kernel'а, и заводить его в eval значило бы развернуть зависимость, которую проект держит однонаправленной. `RebuildResult::imports()` называет такие объекты, и `rebuild` печатает про них строку: отчёт, упомянувший только построенное, читался бы как «это всё, что в файле есть».
   **Чтение STEP приходит функцией, а не вторым объектом.** `GeometryKernel` – контракт ядра, `StepImporter` – контракт документа, и ни один shipped-крейт не смотрит из адаптера ядра обратно на документ. Передача ядра *в* функцию вместо захвата – то, что позволяет одному `&mut` удовлетворить оба контракта; документ без импортов её не вызывает вовсе.

Четыре мутации – рисовать контейнеры, игнорировать дерево, не отдавать импортированные shapes, красить всё одним цветом – роняют их. Вертикаль закрыта против OCCT 8.0.1: `import-step` шипнутой командой, загрузка как во viewer'е, кадр на GPU и подсчёт пикселей, откалиброванный пустой сценой в том же кадре, плюс pick, попадающий в куб. В pin-workflow GPU обязателен через `FERRITECAD_REQUIRE_GPU=1`: отсутствие адаптера роняет прогон, а не оставляет зелёный skip, который можно заметить только ручным чтением лога. Ревью также вернуло прежнюю границу loader'а через `dyn GeometryKernel`: функция чтения STEP остаётся передаваемой отдельно, но вызывающий не обязан знать конкретный тип ядра.
   **Срез 19F-4 сделан: повторное Open с поколениями.** Каждый запрос получает монотонный `LoadGeneration`, новый запрос отменяет предыдущий и **не ждёт** его: отмена – это просьба, ядро замечает её на следующей фиче, и всё это время окно иначе стояло бы замороженным. Ответ принимается только от текущего поколения; запоздалый кадр и запоздалая ошибка отбрасываются молча – жалоба «этот документ не открылся» про файл, который пользователь уже сменил, была бы жалобой не про тот файл. Брошенный worker не выбрасывается, а сохраняется: `drop` у `JoinHandle` отвязывает поток, а отвязанный worker владеет kernel-сессией, которую никто не дождётся. Завершённые присоединяются по `is_finished`, все оставшиеся – на выходе.
   **Ворота на гонки:** `A → B → ответ B → ответ A` и `A → B → ошибка A` – на экране остаётся B, и отброшенный ответ не просит кадр. Плюс монотонность поколений, отмена предыдущего без ожидания, присоединение завершённого без ожидания незавершённого и полная остановка на выходе. Пять мутаций роняют ворота; шестая – «отменять и ждать по одному вместо всех сразу» – не роняет, потому что это свойство времени, а не результата, и таймингового утверждения здесь не ставится. Ворота на выход считает сам worker, уже после того как заметил отмену: `stop_all`, который бы просто забыл потоки, добежал бы до проверки раньше них.
   **Диалог выбора файла: сначала замер, потом код.** `rfd 0.15` добирается до XDG-портала через `ashpd` и `zbus` – 72 крейта, включая целый async-рантайм и ICU. `rfd 0.17` говорит по протоколу портала сам: **два** крейта, `rfd` и `objc2-app-kit` на macOS, всё остальное уже есть через `wgpu` и `winit`. `cargo deny check` – advisories, bans, licenses, sources – зелёный. Фичи названы явно, как у `winit`: default, который однажды поменяется, – это дерево зависимостей, которое поменялось без чьего-либо решения. Диалог вызывается **после** публикации кадра: модальное окно крутит свой event loop, и открыть его, держа взятую texture поверхности, значило бы держать её всё время, пока пользователь ходит по папкам. Ревью нашло, что включённая ради parent identifier фича `wayland` не использовалась: без `set_parent` портал получал пустой идентификатор, а диалог жил отдельно от viewer'а и мог уйти за него. Теперь диалог создаётся только при живом окне и явно принадлежит ему на всех трёх платформах.
   **Срез 19F-5 сделан: строка состояния.** Небольшая машина состояний рядом с загрузками, а не отдельно от них: `Idle`, `Loading { generation, file }`, `Ready { file }`, `Failed { file, message }`. `Ready` наступает только после атомарной замены сцены и камеры – порядок в event loop'е «показать, затем объявить», и мутация, меняющая его местами, роняет ворота. `Failed` сохраняет прежнюю модель на экране и говорит, что случилось: раньше ошибка уходила только в stderr, которого у оконного приложения фактически нет.
   **Устаревший ответ не меняет ни сцену, ни строку.** Поколение хранится в самом `Loading`, поэтому отказ от опоздавшего ответа – один факт в одном месте, а не два одинаковых условия у двух вызывающих. Отмена диалога не делает ничего: `None` не порождает ни поколения, ни worker'а, ни изменения строки. Строка, которая изменилась, – это причина нарисовать кадр, и на пути неудачной загрузки единственная; отдельные ворота требуют, чтобы отброшенный ответ кадра не просил.
   **Ворота:** переход `Loading → Ready`, `Loading → Failed` с сохранением камеры, `A → B → поздний ответ A`, `A → B → ответ B → поздняя ошибка A`, отменённый диалог и имя документа без пути. Пять мутаций роняют их: объявить раньше кадра, забыть поколение в статусе, стартовать загрузку при отменённом диалоге, не сообщать об изменении строки и сообщать о нём всегда. Ревью нашло две щели в проводке: переход второго Open в `Loading` не просил кадр, поэтому старый `Ready` оставался видим до конца долгой загрузки; поздняя ошибка старого поколения не меняла строку, но печаталась в stderr до проверки поколения. Теперь старт и завершение проходят через app-boundary функции: только принятый переход просит кадр, и только принятая ошибка доходит до обоих каналов диагностики.
   **Срез 19F-6, часть первая: прогресс начал что-то значить.** Ядра сообщают 0.0 и 1.0 на *операцию*, поэтому сырой поток отчётов проходил бы 0→1 по разу на фичу, и «готово» было бы неотличимо от «готова первая деталь». Теперь `rebuild_cold` оборачивает sink и отдаёт отчёты ядра как долю **документа**, а `snapshot_of` делит шкалу на две фазы – постройка до `BUILDING`, отрисовка после, – и внутри отрисовки нарезает её по объектам. Шкала одна, монотонная, и заканчивается ровно один раз. Отчитываются только те пункты плана, о которых спрашивали ядро: расширить это до «каждый пункт плана» значило бы позволить progress-колбэку отменить перестройку раньше той работы, за которой он наблюдает, и это уронило существующие ворота на очистку кэша.
   **Срез 19F-6, часть вторая: прогресс по поколениям и Cancel.** У каждой загрузки свой relay: worker пишет в него новейшую долю, а event loop будит **один раз** – событие не несёт числа, потому что к моменту доставки оно уже устарело. Тысяча отчётов подряд оставляет за собой одно событие, и в нём новейшее значение, а не первое; последнее сказанное не теряется ни при каком порядке. Изменение меньше половины процента кадра не стоит.
   **Cancel возвращает окно к описанию того, что нарисовано.** Прежняя модель остаётся на экране, строка снова называет её, а брошенное чтение отвечает позже и отбрасывается как любой устаревший ответ. Если на экране ещё ничего не было – `Idle`, потому что объявить брошенный документ готовым хуже, чем не сказать ничего. Кнопка предлагается только когда есть что останавливать.
   **Ворота:** объединение отчётов (500 отчётов – одно пробуждение, читается новейшее), непотеря последнего значения, прогресс чужого поколения игнорируется, прогресс текущего двигает строку и просит кадр, Cancel сохраняет камеру и строку, Cancel на первой загрузке даёт `Idle`, кнопка отсутствует, когда останавливать нечего. Шесть мутаций роняют ворота, в том числе «игнорировать разбиение фаз» – она прошла первую версию scene-ворот, потому что те не замечали, что бар доходил до 100% на первом же меше. Ревью нашло ещё одну такую границу: один объект `ImportedStep` может содержать несколько leaf-definition, и первоначальная нарезка по объектам отдавала каждому их мешу весь диапазон объекта. Теперь этот диапазон дополнительно делится между уникальными leaf-definition; отдельный assembly-gate требует монотонности и единственного завершения при двух разных деталях внутри одного импорта.
   **Срез 19G-1 сделан: клик выбирает definition.** `ferritecad-scene` возвращает рядом со snapshot каталог `mesh index → Body(ObjectId) | ImportedDefinitionRef`: две половины одного ответа, и они намеренно врозь. Snapshot – это то, что рисует GPU, и он не переживает свою сессию; каталог – это то, что клик *значит*, сказанное так, как это мог бы хранить документ. Каталог сериализуется, `PickId` – нет и не будет: он привязан к identity одного snapshot'а и именно поэтому его безопасно выбрасывать.
   **Выделение живёт в globals, а не в per-draw uniform.** Все размещения одной definition несут одну и ту же identity, поэтому одно сравнение в шейдере покрывает их все – список, который рендерер держал бы в согласии с draw'ами, не нужен, и выбор ничего не переписывает из загруженного один раз. Pick из чужого snapshot'а не выбирает ничего: снимок, который сейчас рисуется, спрашивают, и неузнанный ответ становится «ничего». При замене документа selection сбрасывается отдельно: identity snapshot'а детерминирована содержимым, поэтому геометрически одинаковые документы могут иметь одну identity при разных записях каталога.
   **Клик – это нажатие и отпускание почти на одном месте.** Правило живёт в reducer'е: жест, который проехал больше `CLICK_SLOP`, был orbit'ом, а нажатие, забранное панелью, к модели вопросов не задаёт. Вопрос снимается тем, кто на него отвечает, поэтому offscreen-кадр рисуется один раз на клик, а не каждый кадр после него.
   **Ворота:** каталог совпадает по индексам со snapshot'ом и даёт один и тот же ответ для четырёх размещений; нативное тело названо своим объектом; запись каталога переживает round-trip; клик, drag, панель и потеря фокуса; фон снимает выбор; pick из прежней картинки не выбирает в новой. На GPU: выбор меняет **все** размещения выбранной definition и **не** трогает соседнюю; pick из чужой картинки не меняет ни пикселя. Вертикаль против OCCT 8.0.1 теперь проверяет и каталог: четыре куба сборки дают одну запись с ключом, который назвал сам файл. Ревью закрыл три щели в проводке: клик теперь сам просит кадр, в котором будет прочитан pick; новая сцена атомарно заменяет `PreparedSnapshot`, каталог и сброшенный selection, поэтому геометрически одинаковый другой документ не может принять старый `PickId`; `SceneItem` исчерпывающий, и новый вид сущности остановит компиляцию UI, пока не получит осмысленное имя, вместо молчаливого `None`.
   **Срез 19G-2 сделан: идентичность отделена от того, что читает человек.** Каталог сцены теперь `CatalogueEntry`: `item` – переносимая идентичность (`Body(ObjectId)` либо `Imported(ImportedDefinitionRef)`) и единственная часть, которая сериализуется; рядом лежат факты, собранные при загрузке, – имя, файл источника, число solid'ов. Совпадение по ним запрещено конструкцией: имена повторяются законно, и два тела с именем `Plate` остаются двумя телами, а `#5` в двух файлах – двумя определениями, различимыми только источником. Имя файла берётся последним компонентом даже если документ записал целый путь: подсказка для человека не должна выводить на экран чей-то домашний каталог.
   **Инспектор выделения в `ferritecad-ui` – только чтение и только переносимые роли.** Панель не знает ни документа, ни ядра: `Selected` перечисляет, какие факты бывают, а `rows()` собирает то, что действительно попадёт на экран, как данные – поэтому ворота читают текст, а не веру. В словаре типа нет роли для pick, mesh index, face, shape handle, session или occurrence. Обычный `&str` сам по себе не доказывает происхождение текста, поэтому путь отсекается раньше, на границе каталога сцены; отдельный тест проверяет и Unix-, и Windows-разделители. Имена из документа не фильтруются по словам: деталь законно может называться `Surface`. Пустой выбор говорит «Nothing selected», а не исчезает: пустая полоса неотличима от переставшего работать интерфейса.
   **Переходы состояния идут одним оператором.** `commit_scene` заменяет картинку, каталог, выбор и камеру вместе либо не трогает ничего: неудачная и отменённая загрузка сохраняют и модель, и сделанный в ней выбор, успешная – снимает выбор даже когда новый документ даёт байт-идентичную геометрию. Ревью закрыло ещё один межсобытийный зазор: успешный Open обрывает незавершённый жест и отбрасывает запрос pick от прежней сцены, поэтому ответ загрузки между press/release или между click/redraw не может выбрать что-то в новом документе. Семантический выбор строится только двумя просмотрами – snapshot называет definition, каталог говорит, что это, – без поиска и без отката к имени.
   **Ворота:** факты нативного тела и импортированного definition; одинаковые имена остаются различимы по идентичности; один `definition_key` в двух источниках остаётся различим по источнику; четыре размещения дают один выбор; фон снимает и подсветку, и инспектор; успешная замена снимает выбор, неудачная сохраняет; сам инспектор не добавляет transient-роль или путь к контролируемым строкам, а имена из документа переносит без переосмысления. Семь мутаций роняют ворота: сохранить выбор при успешной замене, снять его при неудачной, разрешать выбор без обращения к текущему snapshot'у, дать всем файлам один источник, показать записанный путь целиком, добавить в инспектор строку с mesh index, убрать из него источник рядом с ключом.
   **Границы среза:** выбор не сохраняется в документ, схема и capability не менялись, occurrence-выбор и picking граней и рёбер не добавлялись, C++, FFI и мост OCCT не тронуты. Визуальное подтверждение на экране в этот срез не входило и не заявляется.
   **Срез 19G-3 сделан: канонические definition на всю сцену.** Документ дедуплицирует одинаковые байты, поэтому два `ImportedStep` могут делить один `ImportedSourceId`; при одинаковом `definition_key` у них одна и та же переносимая идентичность. Раньше дедупликация мешей жила внутри одного импортированного объекта, и такое definition паковалось дважды, получало два `PickId` и подсвечивалось наполовину. Теперь каталог один на всю загрузку и ключом ему служит только `SceneItem`: ни имя, ни имя файла, ни число solid'ов, ни порядок объектов, ни позиция в файле.
   **Факты для человека собираются, а не выбираются.** Одна идентичность, увиденная дважды, даёт одну запись: недостающее заполняется тем, кто это видел, а два непустых несогласных значения дают **отсутствие** значения – выбрать одно значило бы выдать порядок объектов за решение о том, какое имя верное. Состояний три, а не два: «никто не сказал» и «сказали разное» различаются, иначе третье наблюдение переоткрыло бы уже закрытый вопрос. Несогласные счётчики solid'ов – не два definition и не повод усреднять: у одной durable-идентичности одна геометрия, поэтому это отказ.
   **Ворота:** два объекта с одинаковыми байтами дают один source, одну запись каталога, один меш, обе расстановки, один `PickId` на обе и одну тесселяцию (считает сам kernel-обёртка, потому что «упаковано один раз» и «посчитано один раз» – разные утверждения); те же байты под двумя именами файлов остаются одной идентичностью, а спорное имя файла не показывается; один ключ в двух источниках остаётся двумя definition; одинаковые имена не сливают ни тела, ни определения; индексы каталога и snapshot'а совпадают по построению и расхождение – отказ; освобождение shapes на успехе, ошибке и отмене. Ревью закрыло побочный разрыв в progress: полностью повторное definition не вызывало тесселяцию и оставляло последнюю долю успешной загрузки незавершённой; теперь только пропущенная доля закрывается явно, а gate требует монотонности и ровно одного `1.0`. Восемь мутаций роняют ворота: канонизация внутри одного объекта, ключ без источника, имя как ключ, потеря второй расстановки, повторная тесселяция дубликата, тихий приём разных solid'ов, незакрытая progress-доля, переживший Open незавершённый клик.
   **Границы:** выбор не сохраняется, схема и capability не менялись, occurrence, грани, рёбра и вершины не выбираются, C++, FFI и мост OCCT не тронуты. Порядок расстановок остался документным: канонизируются definition, не occurrence.
   **Срез 19G-4 сделан: панель Definitions и двусторонний выбор.** Пробел был пользовательский: definition выбиралась только попаданием в геометрию, поэтому перекрытая, крошечная или оставшаяся за кадром часть из интерфейса была недоступна. Список показывает по одной строке на `CatalogueEntry` в порядке snapshot'а – два `ImportedStep` с общей идентичностью дают одну строку, сколько бы placement'ов они ни добавили.
   **Строка превращается в идентичность только через саму картинку.** `RenderSnapshot::pick_of` – проверенная обратная сторона `definition`: индекс вне снимка не даёт `PickId`, а полученный `PickId` разрешается только в том снимке, что его выдал. Приложение не может собрать `PickId` вручную вообще: поля приватны, и попытка даёт `E0451`, а не падающий тест. Позиция строки нигде не показывается и не переживает снимок.
   **Одна резолюция на обе стороны выбора.** `LiveScene::view` отдаёт список строк и отмеченную строку разом, поэтому отметка в списке и факты в инспекторе не могут разойтись: клик в viewport подсвечивает модель, отмечает строку и заполняет инспектор, нажатие строки делает то же самое с другого конца и просит кадр только если выбор действительно изменился. Пустая сцена честно говорит «No definitions» и ничего не выбирает.
   **Ворота:** индекс определения даёт `PickId`, читающийся обратно только в своём снимке, а вне диапазона и в чужом снимке – ничего; определение, размещённое многократно, даёт одну строку; два определения с одинаковым именем дают две строки и выбираются независимо; выбор другой строки меняет обе стороны и просит ровно один кадр, повторный и отсутствующий выбор не просят ни одного; отмеченная строка и описанное определение – одно и то же; строка из заменённой картинки не выбирает ничего; фон снимает обе стороны; успешная замена снимает выбор, неудачная и отменённая сохраняют; ни одна строка списка не называет transient-термин или путь. Ревью нашло ещё одну неоднозначность: два разных импортированных источника с одинаковыми basename, именем и обычным STEP-ключом читались как одинаковые строки, потому что summary не показывал source. Теперь переносимая идентичность источника показывается всегда, и отдельный gate держит этот случай.
   **Мутации роняют ворота:** имя как единственное содержимое строки, строка на placement вместо строки на definition, сдвиг нумерации `pick_of`, отметка «ничего» при сделанном выборе, отметка не той строки, переживший успешный Open выбор. Отдельно замерено, что «сырой `PickId` в app» не компилируется.
   **Границы:** это не document tree, не occurrence-выбор и не моделирование; schema, capabilities, persistence, C++, FFI, мост OCCT и STEP identity не тронуты; поиска-фолбэка нет.
   **Срез 19G-5 сделан: показать выбранное.** Пробел был прямым продолжением 19G-4: спрятанную, крошечную или оставшуюся за кадром definition стало можно выбрать, но не увидеть. Кнопка «Frame selected» и клавиша F ведут в одну операцию, а решение о камере принимает reducer: второй копии «куда поставить камеру» нет, и расходиться нечему.
   **Выбор по-прежнему называет definition, а не occurrence.** `RenderSnapshot::bounds_of` собирает все размещения выбранного определения и только его: не первое, не кликнутое и не всю сцену. Каждое размещение измеряется по всем восьми повёрнутым углам – габарит повёрнутого ящика не равен повороту его габарита, – и расчёт теперь один на всю картинку и на любую её часть, а не две слегка разные реализации. Определение без треугольников находится нигде, а не в начале координат; `NOTHING`, устаревший и чужой pick отвергаются, потому что разрешение идёт только через этот snapshot.
   **Недоступное действие ничего не делает.** Кнопка включена только когда картинка может сказать, где выбранное; отказ не двигает камеру, не меняет выбор и не просит кадр. Успех сохраняет направление взгляда и просит ровно один кадр.
   **Ворота:** одна definition за кадром попадает в кадр; два далёких размещения помещаются оба; соседняя definition в габарит не входит; повёрнутое размещение измерено по восьми углам; `NOTHING`, чужой pick и пустой меш отказывают; направление сохраняется; клавиша и кнопка – одна операция и одна константа; один успех – один кадр, повторные недоступные действия – ни одного; успешный Open по-прежнему снимает выбор и кадрирует новую сцену целиком, неудачный и отменённый сохраняют прежнее. Ревью нашло разрыв в клавиатурном пути: специальная ветка F обходила `response.consumed`, хотя интерфейс получает первый отказ на каждое событие, а стандартные view keys этот отказ уважают. Теперь claimed F не двигает камеру, и отдельный app-gate держит эту границу.
   **Мутации:** только первое размещение, габарит всей сцены, только два крайних угла, чужой pick принят, пустой меш получил протяжённость и claimed F принят как camera shortcut – все роняют ворота. Снятие выбора не стало отдельной мутацией: текущая операция берёт сцену по `&`, а существующий gate независимо требует сохранить тот же выбор. «Два кадра вместо одного» на этой границе неразличимо, потому что запрос кадра намеренно коалесцируется во флаг; измеримый отказ, запрос кадра при недоступном действии, gate роняет.
   **Срез 19G-6 сделан: показать всё.** Пробел был прямым продолжением 19G-5: после панорамирования и приближения модель уходила с экрана, ничего не было выбрано, и «Frame selected» оставался недоступен – вернуться можно было только повторным открытием документа. Кнопка «Frame all» и клавиша A возвращают вид на всю сцену.
   **Одна арифметика на оба действия.** Reducer получил `frame_extent`: показать выбранное и показать всё – один и тот же вопрос о разных вещах, и вторая копия «куда поставить камеру» была бы той, которая разойдётся. Отдельные ворота требуют, чтобы на сцене из одного определения оба маршрута оставили камеру **побайтово** одинаковой; мутация со вторым методом и другим полем зрения их роняет. Габарит берётся у самого snapshot'а – он посчитан один раз при упаковке, и пересобирать его из каталога, pick'ов или порядка определений значило бы завести второй ответ на решённый вопрос.
   **Действие доступно ровно тогда, когда есть что показывать.** Пустая картинка отключает кнопку, а прямой вызов ничего не делает: камера не двигается, выбор не трогается, кадр не запрашивается, сколько бы раз ни просили. `A`, забранная интерфейсом, до камеры не доходит – то же правило, что и у `F`. Home по-прежнему означает изометрию.
   **Ворота:** камера, уведённая с модели, возвращается так, что все восемь углов мировых габаритов оказываются в отсекающем объёме, включая точки, оказавшиеся позади камеры; несколько определений и далёкие размещения входят целиком; направление взгляда сохраняется; пустая протяжённость отвергается; кнопка включена тогда и только тогда, когда у snapshot'а есть габарит; `A` и кнопка – одна операция и одна константа; `FRAME_ALL_KEY` отличается от `FRAME_KEY` и от каждой клавиши вида; «показать всё» включает соседнее определение, которое «показать выбранное» не включает, и оставляет выбор нетронутым.
   **Мутации роняют ворота:** габарит выбранного вместо габарита сцены, сброс направления взгляда, выдуманная протяжённость у пустой картинки, включённая недоступная кнопка, обход `response.consumed`, совпадение `A` с `F` и с клавишей вида, второй экземпляр арифметики кадрирования. Снятие выбора не стало отдельной мутацией: текущая reducer-функция не получает сцену, а app-gate сохраняет selection вокруг вызова и требует то же значение после него. Это держит нынешнюю границу, но не выдаётся за структурную невозможность: код в `App::frame_whole_scene` мог бы скопировать bounds, а затем изменить selection. «Два кадра вместо одного» невыразимо, потому что запрос кадра – флаг, а не счётчик. Ревью также усилило viewport-gate: исходная проверка называла результат отсекающим объёмом, но проверяла только `x/w`, `y/w` и знак `w`; теперь она требует ещё и глубину WGPU `0 <= z/w <= 1`.
   **Срез 19H-1 сделан: опорная сетка мировой плоскости.** Модель рисовалась на пустоте: у плоской или симметричной детали не было ни масштаба, ни ориентации, а после орбиты негде было увидеть, куда делись начало координат и плоскость XY. Теперь на Z = 0 лежит сетка: тонкие линии, каждая десятая толще, оси через ноль различимы по цвету.
   **Шаг выбирается лестницей 1/2/5.** Планирование – чистая арифметика в `ferritecad-viewport`: один логарифм и три сравнения, без поиска, без цикла и без выделений, поэтому правило можно рассматривать без GPU. Берётся наименьшая ступень не ближе `MIN_PIXELS`, из чего следует и верхняя граница: не более двух с половиной раз минимума. Камера без площади и не-конечный масштаб дают отсутствие сетки, а не NaN.
   **Сетка принадлежит рендереру, а не документу.** Её нет в `RenderSnapshot`, в каталоге, в `SceneItem`, в габаритах и в разрешении выбора; фрагменты всегда пишут `PickId::NOTHING`, поэтому клик по линии – клик по фону. Геометрия сетки не загружается вовсе: позиции выводятся из номера вершины, так что `geometry_uploads()` сохраняет прежний смысл. Рисуется первой, с проверкой глубины, но без записи: деталь, лежащая ниже плоскости, закрывает линии, а не наоборот. Одна реализация на offscreen и на окно; пустая картинка не получает ни сетки, ни выдуманной протяжённости.
   **Ворота:** лестница выбирает ожидаемые шаги по обе стороны каждой декады, соседние зумы отличаются на одну ступень, экранный шаг остаётся в задокументированном интервале, major и оси выведены из того же нуля, нулевой и предельные размеры дают конечный ответ или отказ. На GPU: сетка видна, каждый её пиксель – `NOTHING`, модель сохраняет свой цвет, деталь под плоскостью рисуется без единой дырки, панорама и орбита двигают сетку по миру, зум меняет экранный шаг не более чем втрое, два одинаковых кадра совпадают побайтово, `geometry_uploads` не растёт, пустая сцена остаётся чёрной.
   **Мутации роняют ворота:** фиксированный шаг, шаг вне лестницы, экранная сетка, `pick` не `NOTHING`, запись глубины, сетка поверх модели, зависимость от номера кадра, «загрузка геометрии каждый кадр», выдуманная протяжённость у пустой сцены. Одна не наблюдаема в этой среде: расхождение шага между offscreen и оконным путём – окно в CI не открыть, а обе ветки зовут одну функцию, так что мутация возможна только переписыванием оконного пути. Ревью усилило ещё два доказательства: проверка границ 1/2/5 раньше повторяла формулу внутри теста, не вызывая production-решение, а world-space gate сравнивал целые кадры и мог принять движение модели за движение экранной сетки. Теперь первый вызывает ту же ladder-функцию, что `grid_plan`, на тринадцати декадах, второй сравнивает только пиксели, которые в обоих кадрах остаются фоном; отдельные счётчики требуют обе цветные оси и два уровня серых линий.
   **Границы:** ни видимости, ни hide/show/isolate, ни дерева, ни occurrence, ни граней, рёбер и вершин, ни моделирования, ни привязок и размеров; схема, capability, STEP identity, C++, FFI и мост не тронуты; переключателя и сохранённой настройки в этом срезе нет.
   **Срез 19I-1 сделан: наведение как отдельное transient-состояние.** До клика нельзя было понять, какая definition находится под указателем и какой геометрии соответствует строка списка: единственным способом посмотреть было выбрать и отменить. Теперь наведение – своё состояние: оно называет definition через `PickId` текущего снимка, подсвечивает все её размещения, не заполняет инспектор, не двигает отмеченную строку и нигде не сохраняется.
   **Владение и стоимость.** Вопрос живёт в reducer'е: незахваченное движение без drag'а спрашивает о последней позиции, движения до кадра схлопываются в одно, drag, захваченное панелью движение, отмена жеста и уход указателя вопрос снимают. Ответ – один offscreen-кадр и только когда вопрос появился, а не на каждый redraw; повторный тот же ответ кадра не просит. Строка списка отвечает сама через `snapshot.pick_of`, поэтому под панелью модель не опрашивается. Оконный кадр по-прежнему не рисует id-attachment, геометрия остаётся резидентной, `geometry_uploads()` не растёт.
   **Приоритет и границы.** Выбор и наведение передаются рендереру раздельно и оба проверяются снимком, который сейчас рисуется: чужой или устаревший `PickId` не подсвечивает ничего. Выбранное выглядит как выбранное, даже если на него же наведено; выбранное A и наведённое B различимы. Сетка остаётся `PickId::NOTHING` и на наведение не реагирует. Pick-буфер от подсветки не меняется.
   **Ворота:** в `ferritecad-ui` – вопрос задаётся и снимается на каждом из перечисленных событий, двадцать движений дают один вопрос о последней точке, строка сообщает наведение отдельно от нажатия; на GPU – наведённая definition меняет все свои размещения и ни одного соседнего, выбор и наведение различимы, выбор побеждает, чужой pick и `NOTHING` не подсвечивают ничего, фон и сетка не реагируют, повторное наведение не грузит геометрию и даёт тот же кадр; в приложении – строка и геометрия дают один ответ, переход A → B меняет только наведение, успешный Open забывает и наведение, и вопрос, неудачный сохраняет сцену целиком.
   **Мутации роняют ворота:** чужой `PickId` принят, повтор наведения просит кадр, наведение переживает успешный Open, указатель над панелью спрашивает модель, drag спрашивает о том, что проезжает, наведённая строка становится выбранной, наведение и выбор одного стиля, подсвечено только одно размещение, сетка реагирует на указатель, id-attachment в оконном конвейере. Ревью обнаружило, что первая проверка панели доказывала только reducer при искусственном `claimed = true`: `egui-winit` считает простое движение над toolbar не consumed, пока widget не использует pointer, поэтому настоящая проводка могла спросить модель сквозь панель. Теперь решение получает результат завершённого egui-pass: строка отвечает сама, остальная область UI возвращает `Clear`, а чистая функция держит именно это разветвление. Второй пробел был в цвете: смешивание только с белым оставляло белую деталь без какой-либо отметки. Контраст теперь выбирает светлую или тёмную сторону по luminance, а GPU gate требует различимые selection и hover отдельно для белой и чёрной геометрии. Запись наведения в выбор непосредственно внутри обработчика окна всё ещё не является исполнимой мутацией: функция ответа получает только поле наведения; проводка принимает чистый `HoverRequest`, но само окно в тесте не открывается.
   **Границы:** ни occurrence, ни граней, рёбер и вершин; ни схемы, capability, persistence, STEP identity, C++, FFI и моста; `PickId` остаётся transient, несериализуемым и не показывается.
   **Срез 19I-2 сделан: наведение на отдельную грань без выбора грани.** Ядро возвращает `MeshFaceRange` и гарантирует полное непересекающееся покрытие треугольников, но упаковщик хранил только вершины и индексы, поэтому две грани одной definition после упаковки были неразличимы и наведение могло отметить только деталь целиком. Теперь разбиение сохраняется при упаковке: `PackedMesh` держит по одному `u32` на вершину, `RenderSnapshot` знает, какой definition принадлежит каждая грань, а `FacePickId` – transient-идентичность, привязанная к снимку, с приватными полями, без сериализации и без показа пользователю. Ни `SubShapeHandle`, ни `ShapeHandle`, ни `SessionId` в снимке не остаются.
   **Что видно.** Наведение на геометрию отмечает грань под указателем, и одну и ту же грань во всех размещениях её definition; строка списка по-прежнему отмечает definition целиком, потому что список граней не содержит; клик по-прежнему выбирает definition; выбранное побеждает любое наведение. Состояние наведения стало тремя случаями – ничего, definition, грань – так что «ничего и definition три» и «грань семь, чья definition три» больше не приходится различать по тому, какое из двух полей заполнено.
   **Стоимость и границы.** Ни одного draw call на грань и ни одной продублированной вершины: таблица граней всей картинки готовится и грузится один раз в `prepare` рядом с геометрией, а фрагмент получает идентичность как плоско интерполируемый атрибут вершины. Buffer создаётся без `COPY_DST`, поэтому переписать его позже нельзя. Face target существует только в offscreen-пути; оконный конвейер остаётся с одним colour target. `Frame::pick_at` не изменился ни по смыслу, ни по сигнатуре – рядом появился `Frame::hit_at`, отдающий согласованные половины одного пикселя. Разбиение участвует в идентичности снимка: хешируются длины диапазонов индексов, то есть точное разбиение `MeshFaceRange`, а не порядок хранения вершин или значения handle'ов сессии. Исходный version 2 ошибочно хешировал пробеги в порядке хранения вершин; ревью исправило алгоритм и поэтому подняло `algorithm_version` до 3. Ревью также добавило атомарность отказа упаковщика: отвергнутый mesh не расходует face identities и не меняет повторно используемый builder.
   **Механизм выбран после того, как первый вариант провалился на Windows.** Сначала грань читалась через `primitive_index` и storage-таблицу на треугольник. Это работает на Metal и Vulkan и отвергается программным адаптером Direct3D: `create_render_pipeline` возвращает внутреннюю ошибку. Изоляция показала, что виноват именно `primitive_index` в этом шейдере – без него тот же конвейер собирается, с ним не собирается, хотя в синтетических комбинациях он там же проходит. Теперь идентичность грани – атрибут вершины с `@interpolate(flat)`: capability не нужна нигде, draw call на грань по-прежнему нет, вершины по-прежнему не дублируются, а таблица граней лежит отдельным буфером рядом с геометрией. Тесселяция даёт каждой грани свои узлы – это не предполагается, а проверяется при упаковке, и mesh с общей вершиной двух граней отвергается с внятным сообщением.
   **Отказ адаптера больше не роняет процесс.** Устройство, которое отказалось собрать конвейер, сообщало об этом через uncaptured-error handler, то есть паникой: на Windows это давало не «пропущено», а тридцать одно падение. Теперь создание конвейеров обёрнуто в error scope, и отказ становится `Unsupported` со словами самого драйвера – ровно тот же путь, что и у машины без адаптера.
   **Ворота:** в `ferritecad-viewport` – две грани одной definition дают две идентичности одной definition, грань из многих треугольников остаётся одной гранью, те же треугольники с другим разбиением – другая картинка, пустой mesh не имеет граней, грани нумеруются по всей картинке а не внутри definition, значение извне и грань чужой картинки не называют ничего, в публичных типах нет kernel-handle'ов; на GPU – две видимые грани читаются как одна definition и две грани, наведение на грань меняет её пиксели в обоих размещениях и не трогает соседнюю грань и соседнюю definition, наведение на definition по-прежнему меняет всё, выбор побеждает наведение на грань, pick-буфер от подсветки не меняется, фон и сетка не дают ни definition, ни грани, повторные кадры одинаковы и `geometry_uploads()` не растёт, оконный конвейер действительно с одним colour target; в приложении – наведение на грань не трогает выбор, чужая грань отмечает ничего, успешный Open забывает наведение, неудачный сохраняет сцену.
   **Мутации роняют ворота:** упаковщик игнорирует диапазоны граней; все треугольники mesh'а – одна грань; нумерация граней начинается заново в каждой definition; наведение на грань светит всю definition; наведение на грань побеждает выбор; чужая грань принимается; наведение на грань меняет pick-буфер; сетка называет грань; таблица граней грузится каждый кадр; face attachment добавлен в оконный конвейер; границы разбиения исключены из идентичности снимка – и отдельно вариант, где хешируется только число граней, но не места разделения. Две вещи названы честно: «нумеровать грани по размещению» структурно невыразимо – грани нумеруются при упаковке mesh'а, когда ни одного размещения ещё нет, поэтому проверена ближайшая выразимая мутация «заново в каждой definition»; а загрузку таблицы каждый кадр ворота ловят через счётчик загрузок, который теперь считает и таблицу граней – мутация, которая писала бы в буфер мимо счётчика, воротам не видна, и от неё защищает только отсутствие `COPY_DST` и то, что buffer достижим лишь через bind group, собранную в `prepare`.
   **Два входа вместо одного.** Оконный конвейер получил свой фрагментный вход: шейдер, чья output signature шире конвейера, Direct3D компилировать отказывается, а Metal это терпит. `fragment_main` пишет цвет, definition и грань, `fragment_colour` – только цвет, над одной функцией затенения, поэтому кадры совпадают по построению.
   **Границы:** ни выбора грани, ни моделирования по грани; ни occurrence, рёбер и вершин; ни схемы, capability, persistence, STEP identity, C++, FFI и моста; каталог, `SceneItem`, инспектор документа и portable topology references не тронуты; номер грани нигде не показан и нигде не сохранён.
   **Срез 19I-3 сделан: выбор именованной грани в портативных терминах.** Наведение уже умело показать конкретную грань, но клик по-прежнему выбирал только definition: у грани, у которой в документе есть durable semantic `TopologyRef`, не было способа быть выбранной и описанной как эта грань. Теперь клик по грани нативного тела, которую документ называет точно, выбирает грань; инспектор описывает её только тем, что хранит документ – ссылка, владелец, порождающая feature, ожидаемый kind, семантическая роль и правило выбора.
   **Владение разделено надвое.** `FacePickId` остаётся transient-идентичностью рендерера, привязанной к одному `RenderSnapshot`. Выбираемая грань – это полный детерминированный набор сохранённых `TopologyRef`, которые в текущем rebuild разрешаются ровно в эту грань. Обратная связь строится в `ferritecad-scene`, пока живы topology map и handle'ы из `MeshFaceRange`, и соединяется по handle'у – не по порядковому номеру грани, не по порядку треугольников, не по индексу mesh'а, не по геометрии, площади, центроиду или отображаемому имени. После упаковки ни `ShapeHandle`, ни `SubShapeHandle`, ни `SessionId` не остаются.
   **Что считается именем.** Только ссылка, разрешающаяся ровно в одну грань. Семейная ссылка на несколько граней не является именем ни для одной из них: выбрать из них ту, по которой кликнули, можно было бы только по порядку обхода. Если одну грань точно называют несколько ссылок, сохраняются все, в порядке документа; первая не выбирается. Если точного портативного имени нет, клик по-прежнему выбирает definition – это честный ответ, который приложение умело давать и раньше. Импортированные грани durable-имён не имеют и тоже выбирают свой definition.
   **Выбор – одно состояние.** `Selection` – это `Nothing`, `Definition` или `Face { грань, её definition, портативные значения }`, и поля `SelectedFace` приватны: собрать снаружи выбор, где грань принадлежит одному definition, а pick – другому, нельзя, и это проверено компилятором (`E0451`), а не тестом. Строки списка definitions по-прежнему выбирают definition.
   **Рисование и кадрирование.** У выбранной грани свой стиль, отличный и от выбранного definition, и от наведения; выбор побеждает любое наведение. Грань подсвечивается во всех размещениях своего definition и больше нигде. `Frame selected` кадрирует выбранную грань по её собственным треугольникам во всех размещениях, через ту же арифметику `Extent`, что и всё остальное – одна реализация «где это находится», а не вторая рядом. Pick- и face-буферы от подсветки не меняются, повторные кадры совпадают, `geometry_uploads()` не растёт.
   **Ворота:** в сцене – каждая точно названная грань плиты несёт ту ссылку, которая действительно разрешается в её `MeshFaceRange`; ядро, перечисляющее грани в обратном порядке, называет те же грани; семейная ссылка на две грани не становится именем ни одной; несколько точных ссылок сохраняются все и детерминированно; безымянная нативная грань и любая импортированная не получают выдуманного имени; переданная сцена не содержит ни kernel-handle'ов, ни transient-идентичностей; на GPU – выбранная грань меняет себя во всех размещениях и не трогает соседнюю грань, соседний definition, сетку и фон; выбор грани, выбор definition и наведение попарно различимы; выбор побеждает наведение; чужая грань не выбирает ничего; в приложении – клик по названной грани плиты выбирает грань и описывает её словами документа, строка выбирает definition, кадрирование берёт границы грани, успешный Open забывает выбор и наведение вместе, неудачный сохраняет сцену целиком, грань заменённой картинки ничего не выбирает в новой.
   **Мутации роняют ворота:** связывать грани по порядковому номеру `MeshFaceRange`; принимать первый результат многогранной ссылки; брать первую из нескольких точных; выдумывать ссылку для безымянной или импортированной грани; хранить `SubShapeHandle` или `FacePickId` как durable-значение; подсвечивать одно размещение; давать выбранной грани стиль наведения; ставить наведение выше выбора; кадрировать весь definition вместо грани; давать строке выбрать последнюю наведённую грань; переживать успешный Open; очищаться на неудачном; принимать устаревший `FacePickId` после замены картинки. Мутация «противоречивые definition и грань» структурно невыразима снаружи `ferritecad-scene` – поля `SelectedFace` приватны, и попытка собрать такой выбор в приложении не компилируется (`E0451`); это показано, а не заявлено. Две мутации сначала выживали: выдуманное имя для импортированной грани и принятый устаревший `FacePickId` – ворота были слишком слабыми, и усилены до тех, что ловят обе.
   **Ревью закрыло подмену смыслов при одинаковых пикселях.** Два документа могли дать побитно одинаковые mesh, placements и face partition, но только один из них хранил `TopologyRef`; их snapshot identity совпадала, поэтому `FaceNames` первого можно было ошибочно спросить через snapshot второго и выбрать безымянную грань как именованную. Ворота строят именно такую пару и сначала доказывают равенство всей рисуемой части. Теперь `TopologyRef::meaning_hash` детерминированно покрывает все переносимые поля ссылки и намеренно не включает fallback-подсказку, карта «definition → face → meanings» входит в opaque identity context снимка, а `FaceNames` привязана к получившейся identity. Поэтому одинаковые пиксели с разным документным смыслом выдают разные `PickId` и `FacePickId`, тогда как повторная загрузка того же смысла остаётся детерминированной. Алгоритм snapshot identity поднят до version 4. Отдельные ворота проверяют, что повторно привязать builder нельзя и что отказ второй привязки не меняет первую. Ревью также удалило противоречие README, где после правильного описания выбора именованной грани оставалось старое утверждение, будто ни одна грань не выбирается.
   **Границы:** ни записи в документ, ни схемы, ни capability; выбор нигде не сохраняется; у импортированных граней durable-имён по-прежнему нет; ни occurrence, ни рёбер, ни вершин; ни одной команды моделирования; C++, FFI, мост OCCT и STEP identity не тронуты; `FacePickId` остаётся transient, несериализуемым и не показывается.
   **Срез 19J-1 сделан: transient-видимость definition'ов, только «Hide selected» и «Show all».** Дефект: деталь, стоящая за другой, полностью перекрыта, и до этого среза не было операции, которая показала бы её и дала по ней кликнуть, не трогая документ и не двигая камеру. Сквозные ворота написаны первыми и упали именно на этом.
   **Владение.** Видимость – per definition, transient, привязана к снимку и нигде не сериализуется. `Visibility` живёт в `ferritecad-viewport` рядом с `RenderSnapshot`, поэтому читает его идентичность напрямую: маска, сделанная для другой картинки – в том числе для картинки из тех же треугольников с другими durable-значениями граней – не скрывает в этой ничего. Ключ – не «сырое целое»: скрывается то, что `Marked::known_to` подтвердил в этой картинке, поэтому устаревший или чужой `PickId` не скрывает ничего. Выбранная грань скрывает свой definition целиком, а не себя.
   **Одна арифметика на все пути.** Один цикл отрисовки (`Renderer::draw_model`) читает одну маску и вызывается и оконным, и offscreen-путём; границы видимого считает `Visibility::bounds` через тот же `Extent`, что и всё остальное. Скрытое не рисуется, а не притеняется: ни цвета, ни pick-, ни face-идентичности, ни подсветки, ни вклада в границы для `Frame all`. Геометрия не переупаковывается и не грузится заново: `geometry_uploads()` не растёт, одинаковые кадры совпадают побайтово.
   **Приложение.** `Hide selected` снимает выбор и наведение и забывает клик и вопрос, оставшиеся в полёте, не трогая камеру; `Show all` возвращает всё и ничего не выбирает; успешный Open сбрасывает видимость, выбор, наведение и жесты вместе, неудачный не меняет ничего. Кнопки доступны ровно тогда, когда им есть что делать; `H` и `U` читаются из тех же констант, что печатает панель, отличаются от `F`, `A`, всех видовых клавиш и `Home`, и не срабатывают, когда клавишу забрал интерфейс. Скрытая строка списка остаётся на месте, помечена как скрытая и не выбирает и не наводит невидимую геометрию.
   **Ворота:** в viewport – всё видно изначально; скрытие убирает все размещения и все грани одного definition и ни одного соседнего; `NOTHING`, устаревшая и чужая метки не скрывают ничего; видимые границы исключают скрытое; всё скрытое – границ нет; `Show all` восстанавливает ровно то, что было; повторные запросы идемпотентны; две картинки из одних треугольников с разными значениями не делят видимость. На GPU – передняя деталь сначала перекрывает заднюю; скрытие передней открывает заднюю с её собственными pick и face; пиксели скрытого становятся фоном, а не устаревшим pick'ом; сетка остаётся `NOTHING`; выбранная грань скрывает весь свой definition; выбор и наведение по скрытому ничего не подсвечивают; `geometry_uploads()` не растёт; одинаковая видимость даёт одинаковые кадры; оконный и offscreen конвейеры скрывают одно и то же. В приложении – доступность кнопок точна; клавиши совпадают с напечатанными; не сталкиваются с кадрированием и видами; consumed отменяет обе; Hide снимает выбор и наведение и просит кадр; Show all возвращает видимость и не возвращает выбор; строки остаются; `Frame all` берёт видимые границы; `Frame selected` после скрытия некуда вести; успешный Open сбрасывает видимость, неудачный сохраняет; камера не двигается ни от того, ни от другого; действие, которому нечего делать, не просит ничего.
   **Мутации роняют ворота:** скрывать только первое размещение; скрывать только выбранную грань; гасить цвет, оставляя identities; брать для `Frame all` границы всей картинки; принимать чужой сырой `PickId`; выкидывать скрытые строки из каталога; давать скрытой строке выбирать и наводить; переживать успешный Open; очищаться на неудачном; оставлять выбор и наведение на скрытом; грузить геометрию заново после изменения видимости; фильтровать только в offscreen-пути. Две вещи названы честно. Ворота на скрытую строку сначала не ловили ничего: они нажимали мимо строки, и это исправлено так, что то же нажатие по той же строке сначала обязано выбрать её, когда она видна. И удаление одной лишь явной проверки `is_hidden` в панели ворота не роняет – строка нарисована disabled, и egui уже не сообщает о нажатии; проверка оставлена как правило, записанное в нашем коде, а не унаследованное от семантики фреймворка, но ни один тест не отличает её отсутствия.
   **Ревью закрыл пустое скрытие.** Definition без треугольников всё ещё имеет строку и transient pick, поэтому первоначальный `Visibility::hide` называл его скрытие успешным: строка становилась hidden и включался `Show all`, хотя ни цвет, ни identity, ни extent измениться не могли. Ворота сначала воспроизводят этот случай на placed-but-empty mesh. Теперь единый `Visibility::can_hide` требует не только правильную snapshot identity и ещё видимый definition, но и реальные границы его геометрии; тот же predicate включает кнопку в приложении и исполняет действие. Недоступный Hide сохраняет selection, не создаёт hidden state и не просит redraw.
   **Границы:** ни isolate, ни показа по одной строке, ни дерева occurrence, ни видимости по размещению, ни скрытия отдельной грани, ни прозрачности, ни отсечения; ни persistence, схемы и capability; ни моделирования, рёбер и вершин; STEP identity, семантика `TopologyRef`, durability `PickId`/`FacePickId`, C++, FFI и мост OCCT не тронуты.
   **Срез 19J-2 сделан: Isolate selected.** Дефект: у детали, окружённой соседями, не было ни одной операции, которая оставила бы её выбранной и видимой, убрав всё остальное. `Hide selected` убирает саму цель и снимает выбор, а прятать соседей по одному значит каждый раз терять и заново делать выбор. Сквозные ворота написаны первыми, показывают именно это про `Hide selected` и падали, пока операции не было.
   **Владение.** Расширено существующее состояние `Visibility`, второй маски и никакого GPU-состояния видимости не появилось. Одно внутреннее правило разрешения (`hideable_definition` поверх `draws`) обслуживает `can_hide`, `hide`, `can_isolate` и `isolate`, поэтому «уже нигде» значит одно и то же для всех четырёх: definition без треугольников или без размещений не скрывается, не помечается скрытым при изоляции и не делает изоляцию доступной. Приложение получило свободную функцию `isolate_selected`, которая берёт выбор по неизменяемой ссылке – понизить выбранную грань до её definition она не может вообще, это отказ компилятора, а не тест. `Renderer::draw_model` остался единственным потребителем маски для окна и для readback; ни одного нового цикла отрисовки и ни одной новой загрузки геометрии.
   **Семантика.** Изоляция односторонняя: `Show all` – единственный путь назад, и он не выбирает ничего. Выбор сохраняется точно, включая грань и то, что документ о ней говорит; наведение и всё, что осталось в полёте – клик, вопрос, жест – забываются, потому что относятся к кадру, который сейчас заменится; камера не двигается. Успешный Open сбрасывает изоляцию вместе с выбором и наведением, неудачный сохраняет всё.
   **Ворота:** в viewport – изоляция одной из трёх оставляет ровно её; все размещения выбранной остаются; все размещения и все грани обоих соседей исчезают; выбранная грань изолирует свою деталь; ранее скрытое остаётся скрытым; видимые границы становятся границами выбранной; `Show all` возвращает ровно исходный набор; единственная видимая деталь делает изоляцию недоступной и не меняет ничего; пустые и неразмещённые definition'ы не становятся скрытыми и не делают изоляцию доступной; `NOTHING`, устаревшие и чужие метки не изолируют ничего; две картинки из одних треугольников с разными значениями не делят состояние; повтор идемпотентен. Две вещи названы честно. Мутации «вернуть выбранное вместо запрошенного» и «понизить выбранную грань» структурно невыразимы: `show_one` не получает выбор, и обе попытки дают `E0425`. И одна проверка не наблюдаема: удаление `has_geometry` из `showable_definition` ворота не роняет, потому что definition, которая ничего не рисует, вообще не может стать скрытой – `hide` её отвергает, `isolate` её не помечает, и до проверки геометрии дело не доходит. Проверка оставлена как локально записанное правило, но ни один тест её отсутствия не отличает; то, что пустая definition не становится осмысленным действием видимости, держат ворота на `hide` и `isolate`.
   **Ревью усилило no-op.** Первоначальные ворота вызывали `show_one` для уже видимой, пустой и чужой цели только при пустых hovered и pending-состояниях, поэтому не доказывали заявленное «не меняет ничего». Теперь перед отказом записаны настоящий hover, pending click, hover question, активный жест и камера. Мутация, которая переносит `forget_pending` и очистку hovered перед проверкой `Visibility::show`, падает на этих воротах; рабочее правило уже стояло в правильном порядке и менять production-код не потребовалось. Выбор сохраняется точно, если он на другой definition, и снимается, если скрывается именно она.

   **Ворота:** в viewport – каждая из четырёх операций записывает ровно ту маску, которую заменила, и отменяется в неё; две подряд отменяют только вторую; no-op между ними историю не портит; отмена расходуется с первого раза и вторым нажатием ничего не возвращает; отмена `Show all` восстанавливает смешанную расстановку, а не приближение к ней; границы до изменения и после отмены совпадают; история одной картинки не тратится через другую; пустые и неразмещённые definition'ы истории не создают. В приложении – сквозные ворота на четырёх definition'ах через настоящую панель; все пять входов участвуют в одной истории; точный выбор грани переживает отмену, пока грань видна; выбор, который отмена снова прячет, снимается; выбор, снятый Hide, не воскресает; правила успеха и no-op проверены настоящими кликом, вопросом и жестом; камера не двигается; семантика успешного и неудачного Open. На GPU – цвет, definition-pick и face-hit после отмены совпадают с кадром до изменения побайтово, включая все размещения и грани; `geometry_uploads()` не растёт; окно и readback читают одну и ту же текущую маску.
   **Мутации роняют ворота (четырнадцать наблюдались):** записывать историю на no-op; хранить самую старую контрольную точку вместо последней; отменять в `Show all`; восстанавливать один бит вместо всей маски; сохранять историю после отмены; сохранять выбор, который снова скрылся; сохранять hover, клик, вопрос и жест; двигать камеру; терять историю на неудачном Open; сохранять её на успешном; предлагать кнопку, когда отменять нечего; грузить геометрию заново; доводить восстановленную маску только до readback; тратить историю одной картинки через другую. Две вещи названы честно. Воскрешение старого выбора структурно невыразимо: в `undo_visibility` старого выбора нет и взять его неоткуда (`E0425`). И мутацию «записывать историю на no-op» ловят существующие ворота `asking_twice_for_the_same_visibility_changes_nothing_the_second_time`, а не новые: отказы, которые случаются раньше (скрыть уже скрытое, показать уже нарисованное, `NOTHING`, чужая метка), до правила истории вообще не доходят, и единственный no-op, который туда доходит – `Show all` при полностью видимой сцене.
   **Ревью исправило overclaim ворот.** Первоначальный отчёт и комментарий теста говорили, что все четыре definition'а в сквозных воротах размещены дважды, но `plate_and_more_bodies` создаёт четыре native body, а текущий loader размещает каждый ровно один раз. Ворота теперь утверждают это явно. Их сильная сторона – настоящий loader, настоящий `TopologyRef` названной грани и настоящая панель; повторные размещения принадлежат GPU-gate выше. Совместить durable native face с несколькими occurrence в одном loader-gate сейчас нельзя: native occurrence-пути в модели нет, а добавлять его ради теста вышло бы за границы среза. Production-дефекта в истории видимости не найдено.
   **Границы:** ни redo, ни общего стека отмены; ни persistence, схемы и capability; ни дерева occurrence, видимости по размещению и по грани; ни прозрачности, отсечения и секущих плоскостей; ни моделирования, рёбер и вершин; STEP identity, смысл `TopologyRef`, durability `PickId`/`FacePickId`, C++, FFI и мост OCCT не тронуты.
   **Срез 19K-1 сделан: ортографическая проекция.** Дефект: в перспективе две одинаковые грани на разной глубине занимают разное число пикселей, параллельные рёбра сходятся, и план или вид сбоку нельзя прочитать как чертёж. Сквозные ворота написаны первыми и меряют это в пикселях: две одинаковые плиты на разной дистанции дают 37 и 20 пикселей ширины в перспективе и обязаны давать одинаковую ширину в ортографии, оставаясь выбираемыми со своими definition- и face-идентичностями; ворота падали и без правила, и с заглушкой.
   **Владение.** `Projection::{Perspective, Orthographic}` – transient-состояние камеры в `ferritecad-viewport`: не факт документа, не состояние рендерера, не сериализуется и не входит в идентичность снимка. Матрицу по-прежнему выдаёт только `Camera::view_projection`, а ветвление на две проекции живёт внутри `projection()`, поэтому окно, readback, сетка, picking и кадрирование видят одно и то же. Перспектива осталась значением по умолчанию.
   **Что хранится.** В ортографии камера держит `half_height` – половину мировой высоты, которую покрывает вьюпорт на плоскости цели. Переключение туда берёт её из текущей дистанции, поэтому цель, направление, верх, размер вьюпорта и мир-на-пиксель сохраняются; переключение обратно выводит дистанцию из `half_height`, поэтому зум, сделанный в ортографии, уважается, а устаревшая дистанция не воскрешается. Зум в ортографии меняет масштаб и не двигает глаз – перемещение глаза вдоль направления взгляда там не меняет ничего. Кадрирование в ортографии берёт `half_height` из общей perspective-fit дистанции для сферы, описанной вокруг коробки, с учётом узкой оси. Поэтому все восемь углов попадают в clip volume и в портретном вьюпорте тоже, а последующее переключение в перспективу возвращает ту же fit-дистанцию и не выталкивает повёрнутый угол за экран.
   **Приложение.** Кнопка называет текущую проекцию, а не просто предлагает переключатель, и печатает `O` из той же константы, которую читает маршрутизация клавиш; `O` не совпадает ни с одной клавишей видов, кадрирования и видимости и уступает `response.consumed`. Решение – свободная функция `change_projection`, доступная без окна: выбор и видимость ей не передаются вообще, а hover, клик, вопрос и жест забываются, потому что каждый пиксель после смены проекции значит другое. Найден и исправлен настоящий дефект: `accept_load` не сбрасывал проекцию, и документ открывался в той, в которой оставили предыдущий; теперь новый документ открывается в перспективе, как и всё остальное transient-состояние начинается заново.
   **Ворота:** в viewport – перспектива по умолчанию; равные отрезки на разной глубине проецируются по-разному в перспективе и одинаково в ортографии; переключение в ортографию сохраняет цель, глаз, ориентацию и мир-на-пиксель; переключение обратно сохраняет цель, направление, ориентацию и мир-на-пиксель, но после ортографического зума ставит глаз на выведенную из нового масштаба дистанцию; двойное переключение без промежуточных действий возвращает матрицу с точностью 1e-5; зум ортографии меняет масштаб и не двигает глаз; pan сдвигает модель ровно на запрошенные пиксели в обеих проекциях; orbit сохраняет масштаб и проекцию; resize даёт правильное соотношение в альбомной и портретной ориентации; все стандартные виды и оба кадрирования сохраняют проекцию, и все восемь углов попадают в clip volume; нулевой и предельные вьюпорты остаются конечными. На GPU – две равные плиты дают равную ширину, и ширина совпадает с той, что предсказывает `world_per_pixel` камеры; обе остаются выбираемыми; передняя геометрия по-прежнему перекрывает заднюю; сетка остаётся в мире, её шаг в пикселях совпадает с `grid_plan`, и она не выбирается; повторные кадры совпадают побайтово; `geometry_uploads()` не растёт; окно и readback используют одну матрицу. В приложении – кнопка называет активную проекцию; печатаемая и маршрутизируемая клавиша – одна и та же; выбор грани с её значениями, маска видимости и её контрольная точка переживают смену точно; hover и всё в полёте забываются; при переключении в ортографию цель и глаз сохраняются; успешный Open начинает в перспективе, неудачный сохраняет текущую.
   **Ревью исправило два production-дефекта и overclaim.** Во-первых, `accept_load` сбрасывал проекцию до fallible-кадрирования: снимок с конечными и допустимыми для GPU вершинами, но с суммарным extent шире `f32`, возвращал ошибку уже после перевода старой камеры из ортографии в перспективу. Ворота сначала воспроизвели это вместе с настоящими pending click, hover и redraw; теперь весь reducer подготавливается на клоне и заменяется только после успешного кадрирования. App-gate неудачного Open также исправлен: прежде он вызывал `commit_scene` с клоном `camera`, но затем по ошибке проверял исходный `input`, которого вызов вообще не касался. Во-вторых, минимальный ортографический fit после переключения в перспективу давал слишком близкую дистанцию: у изометрически повёрнутой коробки один из восьми углов уходил из clip volume. Теперь `half_height` кадрирования выводится из общей perspective-fit дистанции, а новые ворота проходят весь переход. Документация больше не говорит, что любое переключение сохраняет позицию глаза: после зума в ортографии обратное переключение намеренно двигает глаз, чтобы сохранить новый масштаб.
   **Мутации роняют ворота (шестнадцать наблюдались):** рисовать ортографию перспективной матрицей; ставить масштаб ортографии в зависимость от глубины; сбрасывать цель и верх при переключении; восстанавливать устаревшую дистанцию после зума; двигать глаз вместо масштаба; путать соотношение сторон в портретной ориентации; сбрасывать проекцию из `Frame all` и из стандартного вида; менять выбор; сохранять hover, клик, вопрос и жест; грузить геометрию заново; выключать depth test; давать `O` чужое действие и игнорировать `response.consumed`; считать проекцию отдельно в пути модели и отдельно в пути сетки.
   **Две мутации сначала выжили и починены по-настоящему.** Собственная арифметика проекции в рендерере не ловилась: ворота сравнивали две плиты друг с другом, а равномерное сжатие всей картинки такое сравнение переживает. Теперь ширина плиты сверяется с `world_per_pixel` самой камеры, а шаг сетки – с `grid_plan`, поэтому обе ветви «одного источника матрицы» закрыты. Отдельно отмечено: первая попытка этой мутации патчила uniform сетки, а не модели, и «ALL PASS» означал не отсутствие ворот, а промах мутации.
   **Границы:** ни persistence, схемы и capability проекции; ни закладок камеры, именованных видов, UI отсечения, секущих плоскостей, прозрачности, каркасного режима и LOD; ни дерева occurrence и состояния по размещению; ни моделирования, рёбер и вершин; STEP identity, смысл `TopologyRef`, durability `PickId`/`FacePickId`, C++, FFI и мост OCCT не тронуты.
   **Срез 19K-2 сделан: зум колесом к точке под курсором.** Дефект: колесо приближало к `Camera::target`, поэтому деталь в стороне от центра уезжала от курсора и её приходилось догонять панорамированием. Ворота написаны первыми и меряют это в пикселях: точка на целевой плоскости в 94 пикселях левее и 73 выше центра после одного шага колеса оказывалась в (-135, +105), то есть уходила от курсора на 51 пиксель; ворота падали и на заглушке, повторяющей старое поведение.
   **Что именно закреплено.** Держится точка, где луч через пиксель пересекает плоскость, проходящую через цель перпендикулярно направлению взгляда. Это та же плоскость, которой уже меряются панорамирование и `world_per_pixel`, и она не требует чтения глубины. Поверхность, лежащая ближе или дальше этой плоскости, удерживается приблизительно, а не точно; точная привязка к произвольной видимой поверхности потребовала бы depth readback и в этот срез не входит. Это записано и в README, и в документации метода.
   **Владение.** Арифметика живёт в `Camera::zoom_at(amount, right, up)` – чистая операция, доступная без окна и без GPU. `right` и `up` – пиксели от центра вьюпорта, положительные вправо и вверх, ровно как у `Camera::pan`: какая ось `y` растёт вниз, решает слой окна, а не камера. `ViewportInput` переводит позицию курсора в эти оси и решает, есть ли она вообще и не забрал ли колесо интерфейс. `Camera::zoom` остался центральным зумом и выражен через `zoom_at(amount, 0.0, 0.0)`, а шаг и пределы вынесены в `zoomed` и `bounded_scale`, поэтому у центрального и привязанного зума одно определение того, что значит щелчок колеса. Ничего не добавлено в рендерер: ни арифметики камеры, ни буфера, ни прохода, ни загрузки геометрии. `Camera::view_projection` остался единственной дорогой из мира в clip space.
   **Как считается.** Целевая точка сдвигается в плоскости взгляда на `пиксельное смещение * (мир-на-пиксель до - мир-на-пиксель после)`. Нужны обе величины: любая из них по отдельности даёт фиксированный сдвиг, который ничего не удерживает. В перспективе меняется дистанция и глаз переносится вместе с целью; в ортографии меняется только `half_height`, а дистанция и направление взгляда остаются прежними, потому что движение глаза вдоль направления взгляда параллельная проекция не показывает. `accept_pose` теперь сообщает, принята ли поза, поэтому операция, меняющая и масштаб, и позу, отбрасывает весь кандидат целиком, а не оставляет половину.
   **Транзиентное состояние.** Успешная смена камеры забывает hover, невыполненный клик и половину клика от нажатия, потому что каждый пиксель после зума показывает другое. Жест не забывается: колесо во время перетаскивания – это зум во время перетаскивания, кнопка всё ещё нажата. Выбор, видимость, история видимости и проекция не трогаются вообще. Колесо, забранное интерфейсом, не меняет ничего, включая ожидающий клик. Колесо, упёршееся в предел, тоже не меняет ничего и не просит кадр, потому что показывать нечего нового.
   **Ворота:** в viewport – точка вне центра остаётся на том же пикселе при приближении и удалении в обеих проекциях; масштаб при этом меняется ровно на `exp(-amount)`, так что бездействие ворота не пройдёт; зум о центр совпадает с `Camera::zoom` побитово; удержание работает после orbit и pan, в альбомном и портретном вьюпорте; приближение и удаление о тот же пиксель возвращают глаз и цель в пределах 1e-3 и масштаб в пределах 1e-4; в ортографии дистанция и направление взгляда сохраняются, а глаз переносится вместе с целью; нечисловой ввод не меняет камеру вообще; конечный, но дикий курсор оставляет камеру конечной; вьюпорт нулевого размера остаётся конечным; четыреста шагов внутрь и восемьсот наружу не выводят числа за пределы. В UI-редьюсере – берётся последняя известная позиция курсора; после `PointerLeft` и отмены жеста колесо снова центральное; забранное колесо не меняет ни камеру, ни ожидающий клик, ни счётчик кадров; успешный зум чистит hover, клик и нажатие, но не жест, и просит кадр; пять шагов подряд должны один кадр, а не пять; проекция и семантика перетаскивания не меняются. На GPU – геометрия лежит в целевой плоскости, и центр отмеченной детали остаётся в пределах 1.5 пикселя от того же места в обеих проекциях; пиксель, на который указывали, принадлежит той же definition и той же грани; ширина известной плиты совпадает с тем, что говорит `world_per_pixel` камеры; соседняя деталь меняется тоже; ближняя деталь, нарисованная первой, переживает зум, то есть глубина всё ещё решает; шаг сетки совпадает с `grid_plan`, и всё, что не деталь, остаётся никем – без definition и без грани; повторные кадры совпадают побайтово; `geometry_uploads()` не растёт; сравнение оконного и readback-путей расширено на камеру после привязанного зума в обеих проекциях.
   **Мутации роняют ворота (наблюдались):** центральный зум вместо привязки; перевёрнутая экранная `y`; смещение по горизонтали, поделённое на соотношение сторон; только масштаб до зума; только масштаб после; привязка только в перспективе; привязка только в ортографии; ортографический зум, двигающий глаз вдоль направления взгляда; игнорирование `response.consumed`; сохранение устаревших hover, клика и нажатия; редьюсер, перестающий смотреть на позицию курсора; собственный шаг и собственные пределы у центрального зума; загрузка геометрии при смене камеры; выключенный depth test у модели; собственная арифметика проекции в пути модели и в пути сетки.
   **Две мутации ненаблюдаемы, и это сказано честно.** Первая: снятие проверки `right.is_finite() || up.is_finite()` в начале `zoom_at`. Ни одни ворота не падают, и не могут: сдвиг из нечисловой позиции даёт нечисловой глаз, а `accept_pose` отказывается от любой позы, у которой глаз не конечен, и отбрасывает кандидат целиком. Проверка оставлена как утверждение контракта на границе, но поведенчески она дублирующая. Вторая: `depth_compare: Always` в конвейере сетки. Сетка рисуется первой и представляет собой одну плоскую заплату, поэтому сравнение с пустым буфером глубины ничего не решает; на конвейере модели та же мутация ворота роняет.
   **Ошибка в собственных воротах, найденная мутацией.** Первая версия GPU-ворот сравнивала картинку только сама с собой, и мутация «рендерер считает проекцию сам» её не роняла; после того как ширина плиты стала сверяться с `world_per_pixel` камеры, роняет. Отдельно: в первой версии фикстуры ближняя плита сместила центр габаритов по `y`, и отмеченная деталь оказалась в десяти миллиметрах позади целевой плоскости – это заметили те же ворота о ширине, и фикстура выправлена так, что деталь действительно лежит в плоскости.
   **Ревью исправило нулевой шаг и формулировку интерфейса.** Горизонтальный жест трекпада приходит как колесо с нулевой вертикальной составляющей. В перспективе такой шаг заново собирал глаз из нормализованного направления и дистанции и на некоторых позах менял одну координату на один ULP; редьюсер принимал это за новый кадр, забывал ожидающие hover и click и просил перерисовку. Теперь `zoomed` замечает, что ограниченный масштаб не изменился, а `zoom_at` заканчивает до арифметики позы; pure-gate воспроизводит прежний однобитный сдвиг, reducer-gate сохраняет камеру, hover, click и redraw. README также больше не называет панель областью центрального зума: колесо над панелью принадлежит интерфейсу, а центральный fallback включается только когда у окна нет текущей позиции указателя.
   **Границы:** ни чтения буфера глубины, ни точной привязки к поверхности под курсором, ни анимации зума, ни закладок камеры, именованных видов, отсечения, секущих плоскостей, прозрачности, каркаса, LOD, состояния occurrence, persistence, схемы и capability. Смысл выбора, семантика видимости, STEP identity, `TopologyRef`, durability `PickId`/`FacePickId`, C++, FFI и мост OCCT не тронуты.
   **Срез 19K-3 сделан: зум щипком на трекпаде.** Дефект: `ferritecad-app` не разбирал `WindowEvent::PinchGesture`, и щипок на трекпаде macOS не делал ничего, хотя колесо уже работало. Ворота написаны первыми: `translate` синтетического `PinchGesture` возвращал `[]` вместо `[Pinch { delta }]`.
   **Одна операция, два устройства.** `Camera::zoom_at` остался единственной арифметикой камеры. В редьюсере появилось приватное правило `zoom_by(amount)`: где зум привязан, что камера откажется делать и что смена вида делает недействительным – свойства зума, а не устройства, которое о нём попросило. Колесо вызывает `zoom_by(delta * WHEEL_ZOOM)`, щипок – `zoom_by(delta)`. Второй константы скорости для щипка нет: winit отдаёт magnification delta, а не число щелчков, поэтому масштаб меняется на `exp(-delta)` без промежуточных множителей. Положительная дельта winit – это приближение, и знак переносится как есть.
   **Владение.** Разбор `WindowEvent::PinchGesture` живёт в `ferritecad-app`; ни `ferritecad-ui`, ни `ferritecad-viewport` не знают о winit. Фаза жеста намеренно не переводится в `GestureCancelled`: она описывает жизнь самого щипка, а объявить её отменой общего жеста значило бы выбросить позицию курсора и оборвать перетаскивание мышью, к которому щипок не имеет отношения. Нулевая дельта на любой фазе проходит обычный no-op rule. Правило принадлежности события вынесено из `match` окна в свободную функцию `claimed_by_interface(event, consumed, wants_pointer)`, поэтому «щипок над панелью принадлежит панели» стало утверждением, которое проверяется тестом, а не строкой внутри обработчика.
   **Транзиентное состояние.** Щипок, который действительно сдвинул камеру, забывает hover, ожидающий клик и половину клика от нажатия – ровно как колесо, тем же кодом. Он не трогает выбор, видимость и её историю, проекцию и уже идущее перетаскивание мышью. Щипок, забранный интерфейсом, нечисловой, нулевой, слишком малый или упёршийся в предел, не меняет ничего вообще, включая ожидающие вопросы и флаг кадра. Несколько обновлений щипка до отрисовки должны один кадр.
   **Ворота:** в приложении – синтетический `PinchGesture` доходит до редьюсера с тем же знаком и той же величиной; каждая из трёх неменяющих фаз, сконструированная с нулевой дельтой, переводится в щипок без увеличения, и после них перетаскивание мышью продолжает поворачивать модель, то есть позиция курсора не выброшена; щипок и колесо одинаково принадлежат интерфейсу, когда он их забрал или хочет курсор, а отпускание кнопки – нет. В редьюсере – направление и точная экспонента для четырёх дельт; щипок даёт ту же камеру, что и `Camera::zoom_at`, вызванный вручную; отмеченная точка целевой плоскости остаётся на том же пикселе в обеих проекциях при приближении и удалении, и в ортографии дистанция не меняется; берётся последняя позиция курсора, а после `PointerLeft` и отмены жеста щипок центральный; забранный щипок инертен, включая незавершённое нажатие; успешный щипок чистит hover, клик и нажатие, но сохраняет проекцию и перетаскивание; ноль, `NaN`, бесконечность и `1e-30` не меняют ни камеру, ни ожидающие hover, клик и нажатие, ни флаг кадра; шесть обновлений должны один кадр; щипок, упёршийся в предел, сохраняет ожидающие hover и клик и перестаёт просить кадры. На GPU новых ворот нет намеренно: щипок доходит до камеры тем же вызовом `zoom_at`, который уже закрыт пиксельными воротами 19K-2, и все они, вместе со сравнением оконного и readback-путей, остаются зелёными.
   **Мутации роняют ворота (наблюдались):** окно снова выбрасывает `PinchGesture`; знак щипка перевёрнут; щипок умножается на `WHEEL_ZOOM`; щипок центрируется на середине вьюпорта; щипок игнорирует то, что интерфейс хочет курсор; устаревшие hover, клик и нажатие сохраняются; щипок обрывает перетаскивание мышью; у щипка своя арифметика и свои пределы; зум меняет проекцию.
   **Что оказалось невозможным и ненаблюдаемым, честно.** Изменить выбор или видимость из правила зума структурно невозможно: `ViewportInput` не имеет таких полей, и попытка даёт `E0609: no field 'selection' on type '&mut ViewportInput'` и то же про `visibility`. Отдельно: снятие внешней проверки `candidate == *self` в `zoom_at` не роняет ни одних ворот. Причина в том, что вторая половина правки 1f1000f – возврат неизменённого кандидата из `zoomed`, когда ограниченный масштаб совпал с прежним, – уже гарантирует точное равенство, и внешняя проверка становится повторным утверждением того же. Снятие именно этой, работающей половины ворота роняет (`a_wheel_step_too_small_to_change_scale_changes_no_pose` и `a_wheel_with_no_vertical_step_changes_nothing_that_is_waiting`), как и снятие обеих. Обе половины сохранены.
   **Ревью сузило платформенное обещание и закрыло щель no-op.** Winit не обещает, что щипок на Windows или Linux станет scrolling, поэтому README больше этого не обещает: отдельный `PinchGesture` документирован на macOS/iOS, а viewer заявляет только macOS. Отдельно мутация, очищающая `pressed_at` до проверки, сдвинулась ли камера, оставила все 68 UI-тестов зелёными: прежние no-op gates держали hover и клик, но не вторую половину ещё не решённого клика. Теперь claimed, нулевые, нечисловые и слишком малые щипки сохраняют реальное незавершённое primary-нажатие; clamped-gate сохраняет ожидающие hover и клик. Та же мутация теперь падает.
   **Границы:** ни smart zoom и двойного касания, ни жестов поворота, ни навигации с сенсорного экрана, ни анимации зума; ни чтения глубины и точной привязки к произвольной поверхности; ни состояния рендерера, буферов, проходов и загрузок геометрии; ни persistence, схемы, capability, моделирования, C++, FFI и моста OCCT. Доставка щипка заявлена только для macOS, как её документирует winit; трансляция и ворота редьюсера собираются и выполняются на всех трёх платформах CI. Ручной smoke на трекпаде не проводился и не заявляется.
   **Срез 19K-4 сделан: поворот вида двумя пальцами.** Дефект: `ferritecad-app` не разбирал `WindowEvent::RotationGesture`. Сквозные ворота написаны первыми и падали на настоящих пикселях: в асимметричной сцене метка стояла в (214.5, 128), то есть на 86 пикселей правее середины, и после синтетического поворота на +90 градусов оставалась ровно там же. Заглушки с готовой арифметикой не было: ворота падали на пустом результате `translate`.
   **Семантика и владение.** Добавлена одна чистая операция `Camera::roll(radians)` в `ferritecad-viewport`. Положительный угол поворачивает мир на экране против часовой стрелки – туда же, куда идут пальцы, и туда же, куда winit считает положительным. Знак закреплён воротами о спроецированной точке, а не комментарием: точка, которую камера рисует справа от цели, после четверти оборота оказывается сверху. Поворот происходит вокруг текущего направления взгляда: меняется только `up`, а глаз, цель, дистанция, проекция, видимый масштаб, радиус и диапазон отсечения остаются прежними. Это не orbit: orbit крутит глаз вокруг модели относительно `WORLD_UP` и намеренно выравнивает наклонённый горизонт, поэтому событие в `ViewportEvent` своё – `Roll { radians }`.
   **Единицы и границы слоёв.** winit отдаёт градусы; камера работает в радианах; перевод происходит ровно в одном месте – в `translate` в `ferritecad-app`. Ни `ferritecad-ui`, ни `ferritecad-viewport` о winit и его единицах не знают. Фаза жеста описывает время жизни поворота и не переводится ни во что своё: она не потеря фокуса и не должна ронять позицию курсора или обрывать перетаскивание мышью. `claimed_by_interface` считает поворот таким же событием указателя, как колесо и щипок.
   **Транзиентное состояние.** Хвост «что делает недействительным изменение вида» вынесен из `zoom_by` в общее правило `settle_view(before)`, которым теперь пользуются и зум, и поворот: копии этого решения нет. Настоящий поворот забывает hover, ожидающий клик и половину клика от нажатия, просит кадр и сохраняет идущее перетаскивание мышью. Поворот, забранный интерфейсом, нулевой, нечисловой, бесконечный или слишком малый, не меняет ничего вообще, включая ожидающее нажатие и флаг кадра.
   **Правило «ничего не изменилось» пришлось сделать точным.** Первая версия сравнивала повёрнутый вектор с базисным до нормализации, и `roll(0.0)` переписывал сохранённый `up` с `[0, 0, 1]` на ортогонализованный `[0.00012, -0.0089, 0.99996]`: матрица та же, структура другая, и редьюсер решил бы, что вид сдвинулся. Ворота `a_turn_that_cannot_move_the_basis_leaves_the_camera_exactly_as_it_was` это поймали. Теперь сравниваются оба вектора после нормализации, и угол, который не может сдвинуть базис, не повод переписывать `up`.
   **Ворота:** в viewport – точка справа уходит вверх при положительной четверти оборота и вниз при отрицательной, в обеих проекциях; глаз, цель, дистанция, проекция, `world_per_pixel` и глубина каждой из трёх точек сохраняются точно, в альбомном и портретном вьюпорте и на камере, которую уже вращали и двигали; четверть оборота и обратно возвращает `up` в пределах 1e-6, полный оборот возвращает пиксель в пределах 0.05; две тысячи мелких поворотов оставляют `up` единичным в пределах 1e-4 и перпендикулярным взгляду в пределах 1e-4; ноль, `NaN`, обе бесконечности и `1e-30` – точные no-op; вьюпорт нулевого размера остаётся конечным; кадрирование сохраняет наклон, а именованный вид его выравнивает. В приложении – синтетический `RotationGesture` сохраняет знак и переводит градусы в радианы ровно один раз; все четыре фазы несут свою дельту и ни одна не становится потерей фокуса; нулевая фаза не обрывает перетаскивание, и оно продолжает поворачивать модель; поворот принадлежит панели так же, как щипок и колесо; сквозные ворота через настоящий рендер доказывают направление. В редьюсере – поворот доходит до камеры тем же, чем является `Camera::roll`; настоящий поворот чистит вопросы, но не жест и не проекцию, и не двигает цель; шесть перечисленных случаев не меняют ничего, включая ожидающее нажатие, которое после этого всё ещё выбирает. На GPU – модель поворачивается вокруг того, на что смотрит камера, в обеих проекциях; измеренное положение метки совпадает с тем, что говорит матрица камеры, до и после поворота; деталь сохраняет цвет, свою definition и свою грань, и её размер меняется меньше чем на пять процентов; ближняя деталь по-прежнему закрывает дальнюю; сетка поворачивается вместе с миром и остаётся никем; повторные кадры совпадают побайтово; `geometry_uploads()` не растёт; сравнение оконного и readback-путей расширено на повёрнутую камеру в обеих проекциях.
   **Мутации роняют ворота (двенадцать, все выполнены):** окно игнорирует `RotationGesture`; градусы считаются радианами; знак поворота обратный; глаз крутится вокруг цели вместо наклона горизонта; поворачивается только перспектива; поворот сбрасывает цель, масштаб и проекцию; поворот игнорирует то, что интерфейс хочет курсор; транзиентное состояние чистится до того, как известно, что камера сдвинулась; устаревшее состояние сохраняется после настоящего поворота; поворот обрывает перетаскивание мышью; смена камеры грузит геометрию; рендерер поворачивает модель сам; рендерер поворачивает сетку сам.
   **Одна мутация сначала выжила в новых воротах, и это исправлено по-настоящему.** «Рендерер поворачивает модель сам» ловилась только воротами 19K-2 о привязке колеса. Причина структурная и стоит того, чтобы её записать: ворота о повороте меряли поворот относительно самой картинки, а повороты в плоскости коммутируют, поэтому постоянный лишний угол в таком измерении невидим. Ворота дополнены сверкой измеренного положения метки с тем, что говорит `Camera::view_projection`, и теперь мутацию роняют.
   **Честное ограничение фикстуры.** Зафиксированная пластина – одна definition, поэтому «выбрана настоящая грань» и «что-то действительно скрыто» не могут сосуществовать в одной сцене: скрытие выбранного снимает выбор. Оба условия проверены в двух состояниях, до которых приложение действительно доходит, а не в одном, до которого оно дойти не может; это записано в самих воротах.
   **Ревью закрыло две щели reducer-gate и сузило app-claim.** Ворота успешного поворота создавали hover, а затем начинали middle-drag, который сам очищает hover; незавершённого primary-нажатия в них не было вовсе. Поэтому две точные мутации – восстановить только прежний hover после `settle_view` и восстановить только `pressed_at` – оставили все 72 UI-теста зелёными, хотя обе нарушали заявленное правило. Теперь hover с pending click, middle-drag и primary-нажатие проверяются в трёх достижимых состояниях; обе мутации падают, а release после поворота доказывает, что старое нажатие уже не может выбрать пиксель нового кадра. Отдельно прежние «app-ворота» крутили отдельный `ViewportInput` рядом с `LiveScene`, поэтому мутация прямо в оконном arm могла снять `live.scene.selection` и оставить все 110 app-тестов зелёными. Семантический путь вынесен в `apply_viewport_input`, который получает только reducer, событие и два ответа интерфейса; окно и тесты вызывают именно его, и selection/visibility структурно отсутствуют в правиле. Сам `ApplicationHandler` по-прежнему нельзя выполнить без окна: произвольная дополнительная запись в его arm остаётся ненаблюдаемой автоматическими воротами и не считается пойманной мутацией.
   **Границы:** ни smart magnify и `DoubleTapGesture`, ни навигации с сенсорного экрана, ни инерции, ни анимации, ни закладок и именованных наклонённых видов, ни настроек и persistence. Смысл выбора, состояние по размещению, моделирование, схема, capability, STEP identity, `TopologyRef`, C++, FFI и мост OCCT не тронуты; `PickId` и `FacePickId` остаются транзиентными и несериализуемыми. Ручной smoke на трекпаде не проводился и не заявляется.
   **Срез 19K-5 сделан: обратимое умное увеличение по двойному касанию.** Дефект: у `WindowEvent::DoubleTapGesture` не было смыслового маршрута в приложение, и жест не делал ничего. Ворота написаны первыми и шли через тот же production-маршрут, которым пользуется окно; заглушка не содержала никакой арифметики камеры – она просто возвращала «ничего не произошло». Падение записано: «a double tap did not magnify anything».
   **Правило.** Первое касание кадрирует то, что выбрано, если у выбранного есть чем нарисоваться, и иначе – границы того, что сейчас видно, то есть `Visibility::bounds`, а не сырые границы снимка. Вид, из которого пришли, запоминается только если кадрирование действительно сдвинуло камеру. Второе касание возвращает ровно тот вид и расходует запись, поэтому третье увеличивает заново. Пустой экстент – полный no-op: ни камеры, ни записи, ни transient-состояния, ни кадра.
   **Почему именно так.** Двойное касание не несёт ни позиции, ни геометрии, поэтому оно не может значить «вот эту деталь под курсором». Оно значит «то, над чем я работаю», а над чем работают – это то, что выбрано; когда не выбрано ничего, остаётся картинка, и картинка – это то, что в ней видно. Никакого чтения глубины этот срез не добавляет, и привязка к поверхности под курсором не заявляется ни в README, ни здесь.
   **Владение.** Запись о том, куда возвращаться, – transient-состояние камеры и ввода: поле `magnified: Option<Camera>` в `ViewportInput`. Её нет ни в `RenderSnapshot`, ни в `Visibility`, ни в `SceneItem`, ни в каталоге, ни в persistence. Кадрирование одно на всё приложение: `magnify` вызывает `Camera::frame`, а что именно кадровать, решает `magnified_bounds` через уже существующие `Selection::bounds` и `Visibility::bounds`. Второй арифметики кадрирования и проекции ни в приложении, ни в редьюсере, ни в рендерере не появилось. winit остался в `ferritecad-app`.
   **Как обесценивается запись.** Каждое ручное движение камеры в редьюсере проходит через `by_hand`, который сравнивает камеру до и после и забывает запись ровно тогда, когда вид действительно сдвинулся. Поэтому orbit, pan, колесо, щипок, поворот, именованный вид, смена проекции, оба кадрирования и настоящий resize её обесценивают, а отказ камеры, шаг слишком малый для представления, забранное интерфейсом событие, нулевые orbit и pan, уже установленный именованный вид, уже кадрированный экстент, уже включённая проекция, resize в тот же размер и просто движение курсора – нет. Успешный Open её очищает явно; неудачный сохраняет вместе со сценой и камерой.
   **Маршрут и границы слоёв.** `magnify_gesture` – свободная функция, вызываемая из тестов без окна; картинка и выбор приходят по разделяемой ссылке, поэтому этот маршрут может их читать и не может менять. Признак «жест принадлежит интерфейсу» вынесен в `pointer_gesture_claimed`, которым пользуются и `claimed_by_interface`, и двойное касание, поэтому второй политики не появилось. Ограничение из ревью 19K-4 остаётся в силе и повторяется честно: сам `ApplicationHandler` без настоящего окна не проверяется, и какая из двух соседних функций вызывается в этой ветке, воротами не закрыто; закрыто то, что `translate` для двойного касания не выдаёт ни одного события камеры, поэтому две ветки не могут обработать его дважды.
   **Ворота:** синтетический `DoubleTapGesture` через production-маршрут увеличивает и возвращает; `consumed` и `wants_pointer` делают жест полностью инертным, включая ожидающий клик и запись; выбранная грань, выбранная definition и пустой выбор дают три разные цели, и скрытая геометрия из запасного варианта исключена; все восемь углов повёрнутой коробки попадают в clip volume в обеих проекциях, в альбомном и портретном вьюпорте; первое касание сохраняет направление взгляда, горизонт и проекцию; второе возвращает камеру точно и рисует побайтово ту же картинку с теми же picks и гранями; запись расходуется, и третье касание увеличивает заново; отсутствие экстента и уже кадрированный вид не записывают ничего; девять ручных операций обесценивают запись, одиннадцать холостых – сохраняют; resize обесценивает, а не возвращает потом устаревший размер окна; успешный Open очищает, неудачный сохраняет; выбор, `SelectedFace` со всеми durable-именами и маска видимости переживают оба направления; hover, клик и нажатие забываются только после настоящего движения камеры; глубина по-прежнему решает; сетка следует общей матрице и остаётся никем; повторные кадры детерминированы, `geometry_uploads()` не растёт; сравнение оконного и readback-путей расширено на плотно кадрированную камеру в обеих проекциях.
   **Мутации (семнадцать, все выполнены):** событие снова выбрасывается; забранный жест выполняется; кадрируется весь файл вместо видимого; кадрируется картинка вместо выбранного; выбранная грань подменяется деталью, на которой она лежит; запись не расходуется; запоминается новый вид вместо прежнего; возвращается только часть камеры; запись переживает настоящее ручное движение; запись теряется после холостой операции; resize сохраняет запись и возвращает старый размер окна; успешный Open сохраняет запись; неудачный Open её теряет; устаревшие hover, клик и нажатие сохраняются; смена камеры грузит геометрию; рендерер кадрирует сам. Все роняют ворота.
   **Одна мутация сначала выжила и починена по-настоящему.** «Успешный Open сохраняет запись» не ловилась: ворота проверяли лишь то, что камера отличается от той, которую дал Open, а этому условию удовлетворяет и восстановление устаревшего вида. Теперь ворота называют именно тот вид, который не должен вернуться, – вид старого документа, – и мутацию роняют.
   **Ревью закрыло повторённую щель в transient-gate.** Ворота увеличения создавали hover, а затем начинали middle-drag, чей press сам очищает hover; завершённый `click` проверял pending pick, но незавершённого primary-нажатия и `pressed_at` в состоянии не было. Поэтому две точные мутации только в `magnify` – восстановить прежний hover после `settle_view` и восстановить прежний `pressed_at` – оставляли профильный тест зелёным, хотя глобальная мутация того же `settle_view` ловилась старыми воротами 19K-4. Теперь pending click с настоящим idle-hover, middle-drag и primary-нажатие проверяются раздельно в обоих направлениях toggle; обе точные мутации падают, а release после увеличения доказывает, что нажатие из старого кадра не выбирает пиксель нового.
   **Ревью довело симметрию no-op до каждого ручного пути и нашло дефект.** Исходные семь холостых случаев не включали orbit, pan, именованный вид и обычное кадрирование, поэтому мутации, очищающие запись перед уже установленным именованным видом или уже кадрированным экстентом, оставляли все 79 UI-тестов зелёными. После добавления соответствующих случаев повтор позиции во время drag обнаружил настоящий дефект: `Camera::orbit(0, 0)` численно ортогонализовал сохранённый базис, а на повёрнутом горизонте ещё и выравнивал его, поэтому редьюсер принимал неизменившийся указатель за движение и выбрасывал запись. Равная предыдущей позиция теперь отсекается в редьюсере, а нулевые orbit и pan отказывают и на чистой границе `Camera`; одиннадцать холостых путей сохраняют запись, а точные мутации именованного вида и кадрирования падают.
   **Что структурно невозможно.** Изменить выбор или видимость из маршрута увеличения нельзя: аргументы приходят по разделяемой ссылке, и попытка даёт `E0594: cannot assign to 'scene.selection', which is behind a '&' reference` и `E0596: cannot borrow 'scene.visibility' as mutable`. Это не засчитано как пройденные ворота, а показано компилятором.
   **Границы:** ни навигации с сенсорного экрана, ни инерции, ни анимации, ни закладок камеры и именованных наклонённых видов, ни persistence, схемы, capability, моделирования и новых видов выбора; C++, FFI и мост OCCT не тронуты. Ручной smoke на трекпаде и в настоящем окне не проводился и не заявляется.
   **Срез 19L-1 сделан: видимые границы граней.** Дефект: закрашенное тело рисовалось без линий, поэтому граница между двумя соседними гранями не была нарисована намеренно, и на одинаково окрашенных или лежащих в одной плоскости гранях структура формы читалась только по силуэту. Пиксельные ворота написаны первыми и меряли это на зафиксированной пластине: из 483 пикселей, где картинка переходит с одной грани на другую, чернилами было нарисовано 0.
   **Что рисуется, честно.** Граница тесселяции грани, а не кривая B-Rep. Снимок не несёт идентичности ребра, поэтому ничто здесь на неё не претендует: у линии нет `PickId`, нет hover, нет выбора, и клик по-прежнему выбирает грань или деталь под ней. Внутренние швы триангуляции не рисуются.
   **Владение.** Индексы линий выводятся один раз при упаковке меша, из уже имеющегося разбиения `MeshFaceRange`. Внутри каждого диапазона считаются неориентированные рёбра: встреченное один раз – граница грани, встреченное дважды – внутренний шов и опускается, встреченное трижды – не поверхность, и такой меш отвергается с `E`-ошибкой, а не разбирается наугад. Счёт ведётся внутри каждой грани, а не по всему мешу: в этом вся разница между «где грани встречаются» и «контур тела». Ребро, оба конца которого называют одну вершину, пропускается; разные индексы в одной координате не свариваются, потому что tolerance этому слою не принадлежит. Линии индексируют те же вершины, что и треугольники, и загружаются один раз рядом с мешем; ни на кадр, ни на размещение ничего не пересчитывается. C++, FFI и мост OCCT не понадобились: существующего представления хватило.
   **Идентичность.** Версия алгоритма не поднималась, и это осознанно: линии – чистая функция от `indices` и `face_index_counts`, которые уже входят в хеш, поэтому ничего нового не хешируется и ничего хешируемого не изменилось. Декоративный bump сделал бы недействительными все существующие идентичности без единого изменения смысла.
   **Рисование.** Порядок: очистка, сетка, закрашенная модель, затем границы с проверкой глубины. Тот же `Camera::view_projection`, та же арифметика размещения, тот же вершинный этап и те же буферы вершин, что и у модели; отдельной арифметики камеры нет. Линии проигрывают всему, что ближе, следуют за orbit, pan, зумом, поворотом, кадрированием и обеими проекциями, уважают видимость во всех четырёх операциях и рисуются для каждого размещения. В pick- и face-цели конвейер линий не пишет вообще: маска записи пуста, поэтому пиксель под линией по-прежнему отвечает за себя.
   **Чем рисуются.** Цвет чернил берётся от затенённого цвета этого же пикселя и уводится в противоположный конец диапазона. Отсюда три следствия, и все три нужны: линия видна и на чёрной детали, и на белой; она видна на грани, отвёрнутой от света, потому что меряется от её собственного затенения; и она не пропадает в заливке, которая только что сдвинулась в её сторону.
   **Найденный при этом настоящий дефект оснастки, и он важнее самого среза.** Первая версия конвейера линий просила depth bias, а wgpu запрещает его на линейной топологии. Конвейер отвергался, `push_error_scope` превращал отказ в `Unsupported`, и макрос `renderer_or_skip!` молча пропускал **каждый** GPU-тест: все они «проходили», ничего не проверяя, включая ворота о самом дефекте. Обнаружено это только потому, что для диагностики был запущен тест с `--nocapture` и в выводе оказалась строка `skipped: unsupported: ... Depth bias is not compatible with non-triangle topology LineList`. Bias убран, ворота стали настоящими, и после этого выяснилось, что часть уже существующих ворот линиями действительно нарушена.
   **Ревью закрыло причину ложнозелёного прогона, а не только один её симптом.** Validation error при сборке offscreen- или оконного pipeline теперь `Rendering`, поэтому `renderer_or_skip!` не может принять ошибочный WGSL, несовместимое состояние primitive или неверную attachment-схему за отсутствие GPU. Только настоящий отказ запроса адаптера и internal driver failure остаются `Unsupported`; текст драйвера сохраняется в обоих классах. Чистый gate без GPU доказывает классификацию, включая приоритет validation, если одна серия сборок сообщила оба отказа. Точная мутация, возвращающая validation в `Unsupported`, роняет этот gate.
   **Что пришлось поправить в существующих воротах, и почему это не ослабление.** Ворота вида «выбор детали меняет каждый её пиксель» писались, когда каждый пиксель детали был заливкой. Теперь часть её пикселей – граница, а чернила уведены в конец диапазона, поэтому две заливки по одну сторону диапазона окрашиваются одинаково, и граница о выборе ничего не сообщает. Эти ворота теперь говорят «каждый пиксель поверхности», исключая границу и объясняя почему; утверждение о том, что деталь видно выбранной, сохранено полностью. Отдельно исправлено скрытое переполнение в тестовом помощнике `is_grid`: `b > r + 40` в `u8` переполнялось на белом пикселе, чего до появления белых чернил не случалось.
   **Ворота упаковки:** квадрат из двух треугольников даёт четыре стороны и не даёт диагонали; две отдельно тесселированные грани в одной плоскости сохраняют обе границы, включая шов между ними; несколько граней и разрозненные куски дают один и тот же результат при повторной упаковке; порядок и обход треугольников не меняют множество границ; не-поверхность, рваное разбиение и индекс вне меша отвергаются; пустой меш не выдумывает линий; идентичность по-прежнему различает две разные триангуляции одного квадрата и признаёт одну и ту же картинку той же самой.
   **Ворота GPU:** на зафиксированной пластине граница между гранями нарисована; на светлых плитах чернила лежат по краю грани и не пересекают её середину, где была бы диагональ; граница детали, целиком закрытой другой, не проступает сквозь неё, и появляется, как только закрывавшее убрано; скрытие и изоляция убирают и заливку, и линии, а возврат рисует ровно ту же картинку побайтово; оба размещения одной definition получают одинаковое количество линий; линии следуют за поворотом камеры в обеих проекциях; выбор и вопрос по-прежнему различимы, а выбранная грань сохраняет свою границу; под чернилами по-прежнему та же грань; фон, где ничего не нарисовано, остаётся никем; повторные кадры совпадают побайтово; `geometry_uploads()` не растёт; сравнение оконного и readback-путей теперь явно проверяет, что сравниваемая картинка содержит линии.
   **Ещё два раза ворота проходили не по той причине, и оба найдены мутациями.** Первое: `ink_pixels` считал чернилами и чёрный фон, прилегающий к силуэту плиты, поэтому размещение вообще без линий выглядело так, будто линии у него есть; проверено вручную – мутация «линии только у первого размещения» проходила собственные ворота. Теперь чернилами считается только то, что нарисовано поверх пикселя, принадлежащего модели. Второе: ворота о скрытии не видели своей мутации, потому что у светлой детали чернила чёрные, а фон тоже чёрный; ворота переведены на тёмный материал, где такие линии белые, и исключают окрестность детали, которая законно открывается под скрытой. Отдельно: прогон мутаций, убитый таймаутом, не восстанавливает файлы, и следующий прогон сохранил мутанта как эталон – в дереве какое-то время отсутствовал `seen.clear()`. Обнаружено по несовпавшему якорю; в harness добавлен отказ делать backup поверх существующего `.bak`.
   **Ограничения, названные прямо:** «чернила» отличаются от заливки по цвету только в тех фикстурах, где материал не является чистым белым или чёрным; там, где является, ворота выбирают пиксель внутри грани, а не по цвету. Тусклая линия сетки и тёмные чернила по цвету неразличимы, поэтому ворота о фоне утверждают то, что проверить можно: при скрытом всём не нарисовано ничего. Ручной осмотр окна не проводился и не заявляется.
   **Срез 19L-2a сделан: точная ассоциация топологических рёбер от OCCT до снимка.** Дефект: снимок нёс только границу тесселяции, поэтому у ребра модели не было идентичности вообще, и адаптер OCCT сообщал пустую ассоциацию. Ворота написаны первыми и оба падали: `every_edge_of_the_plate_is_named_and_drawn_from_both_of_its_faces` – «Open CASCADE knows which topological edge each segment draws», и `a_foreign_edge_cannot_hide_behind_a_correct_first_one` – «an edge of another shape is not part of this mesh», потому что проверка владения сравнивала только первое ребро с первой гранью.
   **Измерение до проектирования, и оно решило вопрос.** `BRep_Tool::PolygonOnTriangulation` измерен на OCCT 7.9.3 при тех же параметрах, что и мост: linear 0.01, angular 0.5, relative off, InParallel off, с `BRepTools::Clean` до сетки. Двенадцать форм: пластина 60x40x10 тем же маршрутом `BRepPrimAPI_MakePrism`, полуцилиндр из дуги и хорды, цилиндр, сфера, тор, скруглённая пластина r=2, оболочка t=2 и пять STEP-фикстур корпуса. Итог: 205 топологических рёбер, 403 стороны ребро-грань, **ни одной стороны без полигона, ни одного узла вне триангуляции, ни одной непокрытой грани**. Поэтому ассоциация читается, а не выводится, и отсутствие полигона – отказ, а не заплатка.
   **Что измерение изменило в проекте.** `TopLoc_Location` оказался обязательным, а не оптимизацией: если подставить единичную локацию, на двух STEP-сборках теряются все 125 сторон из 125, а на самой пластине – 4 из 24, потому что верхняя крышка призмы лежит под локацией. Ориентация не является частью идентичности: грани приходят FORWARD и REVERSED вперемешку, ребро в одной грани FORWARD, в соседней REVERSED, и обе стороны обязаны попасть под один идентификатор. Шов несёт два представления на одной грани; измерено, что списки узлов у них совпадают, поэтому берётся по одному полигону на сторону и шов рисуется один раз. Вырожденные рёбра существуют (два полюса сферы, восемь углов скругления) и полигон у них есть – они включаются, потому что фильтрация по вырожденности была бы решением о рисовании, а не фактом об ассоциации.
   **Контракт ядра говорит о доступности прямо.** `Mesh::edges` теперь `Option<MeshEdges>`, а не два независимых поля рядом с `Mesh`: `None` – производитель не сопоставил ничего; `Some` пустого `MeshEdges` – производитель посмотрел и рёбер нет. Данные ассоциации сгруппированы с фактом их доступности и не могут существовать при `edges: None`. Поля DTO остаются открытыми, поэтому неправильное сочетание сегментов и диапазонов внутри `Some` представимо, но явно отвергается валидацией. Она проверяет: массив сегментов состоит из пар; все индексы в пределах вершин; каждый диапазон непустой; диапазоны непрерывны, упорядочены, без переполнения, разрывов и перебора; покрытие полное; handle имеет вид Edge; дубликатов рёбер нет; **shape каждого ребра сверяется с shape граней на каждой итерации, а не только на первой**. Координатного равенства и tolerance в идентичности нет нигде.
   **Мост и FFI.** `fc_occt_tessellate` получил один аргумент – `FcOcctEdgeBuffers`, структуру буферов, а не шесть позиционных: функция уже дошла до длины, на которой перестановка двух однотипных указателей даёт молча неверный каркас вместо ошибки компилятора. Узлы полигона переводятся в те же упакованные вершины, которыми пользуются треугольники: `base + node - 1`, где `base` – та же величина, что уже считается в цикле граней. Консолидация идёт через `IsSame` – и в ключах `TopExp::MapShapesAndAncestors`, и в `ShapeRecord::remember`, – поэтому общее ребро двух граней остаётся одним. Порядок сегментов: грань за гранью в порядке упаковки, цепочка внутри полигона сохраняется. Ребро без сетчатой смежной грани – свободный провод в компаунде – ассоциации не даёт и в список не попадает; ребро со смежной сетчатой гранью, но без полигона, роняет вызов. Handle OCCT через границу ядра не проходит.
   **Упаковка и `EdgePickId`.** Идентичность ребра нумеруется один раз на definition в `add_mesh`, никогда в `place`. `PackedEdges` хранит только сегменты и число сегментов на ребро – ровно так же, как `face_index_counts` хранит разбиение граней; ни `SubShapeHandle`, ни `ShapeHandle`, ни `SessionId` в снимок не попадают, и ворота проверяют это в том числе по `Debug`-выводу. `edge_owner` – один вектор, поэтому противоречивая пара «ребро и не та definition» невыразима: definition выводится из идентичности, а не лежит рядом с ней. Чужая, устаревшая и `NOTHING` отвечают ничем, включая случай, когда сырое число попадает в диапазон другой картинки.
   **Версия алгоритма поднята с 4 до 5, и это заявление, а не починка.** Хеш снимка теперь покрывает второе разбиение той же геометрии, у которого есть собственные идентичности. Ворота доказывают то, ради чего это сделано: две картинки с одними и теми же вершинами, треугольниками и границами, но с разным делением сегментов по рёбрам, не принимают идентичности друг друга. Handle не хешируются – по той же причине, по которой не хешируются handle граней. Ничто долговременное этим ключом не адресуется, поэтому смена абсолютного значения ничего не стоит.
   **Мутации (семнадцать, все выполнены и все роняют ворота):** принять чужое ребро после правильного первого; прочитать отсутствующую ассоциацию как доказанную пустую; сваривать вершины по координатной близости; сделать ориентацию частью идентичности и раздвоить общее ребро; потерять `TopLoc_Location`; взять одну произвольную сторону грани; принять нечётный массив сегментов; принять нарушение непрерывности; принять неполное покрытие; принять диапазон нулевой длины; принять не-Edge handle; принять дубликат ребра; принять сегмент вне вершин; принять `EdgePickId` другой картинки; не включить разбиение рёбер в идентичность снимка; сохранить kernel-handle в упакованной картинке; нумеровать рёбра на каждое размещение.
   **Две мутации сначала не ловились, и обе – настоящие находки.** Первая: harness сообщил «выжили» сразу о восьми мутациях, потому что `cargo test --exact` требует имя с модулем, а у unit-тестов ядра оно `result::tests::...`; запускалось ноль тестов, и cargo возвращал успех. Теперь harness отказывается засчитывать прогон, в котором не выполнился ни один тест. Вторая, найденная уже после починки: мутация, убирающая проверку непрерывности, выживала, потому что и «разрыв», и «перекрытие» ловились правилом о полноте покрытия, а не правилом о непрерывности. Ворота о перекрытии переписаны так, что суммы совпадают точно – три сегмента и три заявленных, – и отличить их может только непрерывность.
   **Границы:** GPU-цель для рёбер, `Frame::edge_at`, hover, приоритет грань/ребро/деталь, выбор рёбер, UI и app-wiring не добавлялись – это §19L-2b. Схема, persistence и capability не менялись. Границы граней из 19L-1 рисуются ровно как раньше и остаются свойством треугольников, а не B-Rep. Ручной осмотр окна не проводился и не заявляется.
   **Срез 19L-2b1 сделан: GPU-цель идентичности рёбер и чтение через `Frame`.** Дефект: `EdgePickId` из 19L-2a существовал только в снимке, до GPU не доходил и по пикселю не спрашивался. Ворота написаны первыми и падали: `one_topological_edge_answers_with_one_identity_from_both_of_its_faces` – в точке (46, 145) левого размещения ожидался `EdgePickId { raw: 1 }` этого снимка, а `Frame::edge_at` отвечал `raw: 0` с нулевым `ContentHash`. Временная заглушка `edge_at -> NOTHING` была именно заглушкой: никакой арифметики в ней не было.
   **Представление на GPU, и почему дублирование обязательно.** Отдельный expanded edge stream: каждая пара endpoints сегмента становится двумя вершинами по 16 байт – позиция и сырое значение `EdgePickId`. Обычный indexed vertex buffer этого выразить не может: одна геометрическая вершина принадлежит нескольким topological edges – угол коробки является концом трёх, – поэтому одно значение на позицию не может сказать, какому из них принадлежит сегмент. Позиции берутся из уже упакованного меша по тем самым индексам, которые дал kernel; ни одна координата ни с чем не сравнивается. Нумерацию спрашивают у снимка через `edge_of`, а не считают заново. `primitive_index` не используется: он был исключён настоящим Windows backend ещё в 19I-2, и сюда не возвращается. Буфер собирается один раз в `prepare` рядом с треугольниками; на кадр и на размещение не пересчитывается ничего, а рисуется один вызов на размещение, а не на ребро.
   **Порядок проходов и правило глубины.** Проход рёбер идёт вторым, после того как картинка нарисована целиком, и имеет ровно одно вложение – `R32Uint`, очищаемое в ноль. Цвета, definition и face у этого прохода нет вообще, поэтому испортить их он не может не по политике, а структурно; grid и фон в нём не рисуются и остаются нулём по той же причине. Глубина модели теперь сохраняется первым проходом (`StoreOp::Store` вместо `Discard`) и загружается вторым: сравнение `LessEqual` без bias, запись глубины выключена. `LessEqual` – потому что ребро лежит ровно на поверхности, которую ограничивает, и иначе проигрывало бы ей каждую ничью; bias запрещён wgpu на линейной топологии, и он не нужен, поскольку ребро и поверхность проецируются одними и теми же матрицами. Оконный путь не изменился: у окна нет identity-вложений и не обязано быть.
   **`Frame` и `Hit`.** `Frame::edge_at(x, y)` возвращает содержимое цели, декодированное только через `EdgePickId::from_raw` против снимка этого кадра; вне кадра, на фоне, на сетке и внутри грани – `NOTHING`. `Hit::edge()` требует согласованности: ребро сохраняется, только если принадлежит той же definition, что и пиксель. Противоречие даёт ребру `NOTHING` и не трогает ни definition, ни face. `Frame::pick_at` не изменён, и наличие ребра не убирает грань: клик по-прежнему находит грань под линией.
   **Что названо честно.** Внешний силуэт – единственное место, где линия законно попадает на пиксель, которого не достигла заливка. Ворота меряют это: ни один пиксель с идентичностью ребра не отстоит от модели дальше чем на один пиксель, и там, где definition пустая, `hit_at` ребро отвергает. Это не обходной путь, а то самое правило согласованности, ради которого оно написано. Цель хранит один `u32`, поэтому в sample, который покрыли несколько рёбер – общий конец или их проекционное пересечение, – остаётся одно из них по детерминированному порядку рисования; это ответ raster sample, а не утверждение, что в геометрии там существует только одно ребро. Разрешение нескольких кандидатов и выбор вершины в этот срез не входят.
   **Ворота:** обе стороны общего ребра отвечают одной идентичностью – и это утверждение с содержанием, потому что синтетический меш строит две грани с разной частотой разбиения одной кривой, так что хорда одной стороны отстоит от ломаной другой примерно на девять пикселей; каждое размещение отвечает той же идентичностью; четыре соседних ребра отвечают своими; внутренность грани, фон и всё дальше пикселя от модели – ничем; ребро за более близкой деталью не отвечает сквозь неё и возвращается, когда её скрыли; скрытая definition не оставляет ни одной идентичности, а Show возвращает ровно те же; Isolate детали без ассоциации оставляет цель пустой; цвет побайтово совпадает с картинкой без прохода рёбер, а definition и face совпадают попиксельно; `None` и `Some(empty)` не создают геометрии; повторные кадры совпадают по всем четырём чтениям; `geometry_uploads` не растёт; орбита, панорама, поворот горизонта и обе проекции находят ребро там, где говорит общая матрица; `edge_at` вне кадра и число, которого нет в картинке, отвечают ничем; `PreparedSnapshot` другого рендерера по-прежнему отвергается.
   **Мутации (восемнадцать, все выполнены, все восемнадцать роняют ворота):** цель всегда ноль; писать definition вместо ребра; сдвиг нумерации на единицу; слить все рёбра definition в одно; рисовать только первый сегмент; рисовать только представление первой грани; рисовать только первое размещение; не применять Visibility; глубина `Always`; проход рёбер пишет в цветовую цель; он же в definition-цель; он же в face-цель; фон остаётся с идентичностью; принять противоречивое ребро в `Hit`; декодировать сырое значение без проверки снимка; грузить геометрию каждый кадр; считать проекцию отдельно; хранить одну идентичность на исходную вершину без дублирования.
   **Три мутации сначала не ловились, и все три – настоящие находки.** Первые две: harness сообщил «gate did not run at all» о двух мутациях, потому что `cargo test --exact` требует имя с модулем, а у unit-тестов рендерера оно `renderer::tests::...`; правило harness, добавленное в 19L-2a, отработало и не засчитало эти прогоны как выживание. Третья: мутация «считать проекцию отдельно», масштабирующая мир на два процента, выживала, потому что ворота о камере искали ребро с допуском в два пикселя, а сдвиг в точке пробы был примерно таким же. Ворота усилены: при каждой камере и в обеих проекциях теперь проверяется, что ни один пиксель с идентичностью ребра не отстоит от модели дальше чем на пиксель, – и мутация падает.
   **Чем именно поймана мутация «проход пишет цвет», честно.** Не пиксельным утверждением, а отказом устройства: `Render pipeline targets are incompatible with render pass ... the RenderPass uses textures with formats [Some(Rgba8Unorm)] but the RenderPipeline with 'ferritecad viewport edge identity pipeline' label uses attachments with formats [Some(R32Uint)]`. Ворота падают, но падают на валидации wgpu, и это записано именно так.
   **Что показал компилятор, а не ворота.** Выбор ребра структурно невозможен: у `Marked` нет варианта `Edge`, и попытка даёт `E0599: no variant, associated function, or constant named 'Edge' found for enum 'Marked'`. Это не засчитано как пройденные ворота, а показано компилятором; `Marked` в этом срезе остался ровно тем же состоянием выбора и видимости.
   **Границы:** ни `Hovered`, ни hover-состояния приложения, ни визуальной подсветки ребра, ни изменений reducer, UI, inspector и Selection; ни durable-имён рёбер и связи с TopologyRef; ни изменений `Visibility` API, схемы, persistence и capability; C++, FFI и мост OCCT не тронуты, поэтому pin не запускался. Хеш и версия снимка не менялись: новой семантики в них не появилось. Этот срез не заявляет hover – он доказывает, что GPU и `Frame` умеют точно ответить, какое топологическое ребро лежит под пикселем.
   **Срез 19L-2b2 сделан: точная подсветка топологического ребра под указателем.** Дефект: `EdgePickId` доходил до `Frame`, но приложение его выбрасывало и отвечало гранью. Ворота написаны первыми, шли через настоящий маршрут – зафиксированная пластина, loader, OCCT-ассоциация рёбер, GPU, `Hit`, решение приложения, второй кадр, пиксели, – и падали на настоящем runtime failure: «the pointer over an exact topological edge did not mark the edge; left: `Face(FacePickId { raw: 1 })`, right: `Edge(EdgePickId { raw: 1 })`», оба с одним и тем же `ContentHash` картинки. Заглушка `hovered_at` возвращала грань и не содержала ни арифметики precedence, ни шейдера.
   **Владение: отдельный `Hovered`, а не вариант в `Marked`.** `Marked` остался тем, что выбрано: Nothing, Definition, Face. `Hovered` – это Nothing, Definition, Face, Edge, с собственным `known_to` и `definition`. Разделение не косметическое: общий тип сделал бы `Selection::Edge` состоянием, в которое программу можно привести. Попытка показана компилятором: `E0599: no variant, associated function, or constant named 'Edge' found for enum 'Marked'` и то же самое для `ferritecad_scene::Selection`. Это не засчитано как пройденные ворота. `LiveScene.hovered` теперь `Hovered`; редьюсеру по-прежнему передаётся только `&mut Hovered`, поэтому указатель ничего не выбирает; `Selection` и `Visibility` принимают только `Marked`.
   **Точный порядок для пикселя.** Согласованный `Hit::edge()` → Edge; иначе `Hit::face()` → Face; иначе `Hit::definition()` → Definition; иначе Nothing. Самое частное первым, и всё из одного `Hit` одного кадра, поэтому ответ не может описывать одно, а разрешаться против другого. Внешний силуэт сюда не попадает: `Hit::edge()` уже отвергает пиксель, где цель рёбер и цель definition расходятся, и такой пиксель отвечает гранью или ничем. Строка списка всегда отвечает Definition и пикселей не читает.
   **Порядок проходов.** Картинка (сетка, заливка, границы граней) → отметка ребра → цели идентичности. Отметка – отдельный проход только с цветом и глубиной: цели pick, face и edge к нему не прикреплены, поэтому изменить их он не может структурно, а не по маске записи. Глубина тестируется `LessEqual` и не пишется, bias нет. Если отмечать нечего, проход не создаётся вовсе, и кадр рисуется ровно теми проходами, что и раньше. Оконный проход уже состоит только из цвета, поэтому там отметка рисуется в нём же, тем же конвейером и тем же вызовом: одно утверждение о том, что значит отметить ребро, а не оконное и закадровое по отдельности. Геометрия – тот же expanded stream из 19L-2b1; второго буфера нет, и наведение ничего не загружает.
   **Layout uniform, явно.** `Globals` получил `hovered_edge` и три скаляра выравнивания. Пять `u32` после матрицы – это 84 байта в Rust и 96 в WGSL, потому что `mat4x4` даёт структуре выравнивание в шестнадцать байт; такое расхождение один backend прощает, другой нет. Обе стороны дополнены до 96, и в Rust стоит `const _: () = assert!(size_of::<GlobalsUniform>() == 96)` плюс ворота, называющие число.
   **Выбор сильнее вопроса, и правило одно.** Отмечается ребро, если выбрана не та definition, которой оно принадлежит, и если оно не ограничивает выбранную грань. Смежность спрашивается у картинки: `RenderSnapshot::edge_bounds_face` читает её из уже упакованного разбиения – сегменты ребра называют вершины, каждая вершина принадлежит ровно одной грани. Это свойство ребра, а не одной его стороны, поэтому ответ не зависит от того, какая из двух совпадающих face-side линий нарисована последней; ни координат, ни kernel handle здесь нет. Следствия: выбранная деталь не перекрашивается вопросом о её ребре; выбранная грань тоже; ребро той же детали, не ограничивающее выбранную грань, отмечается; выбор в другой детали ничего не подавляет.
   **Как выглядит.** База – противоположный конец диапазона от материала детали, что гарантирует видимость и на почти белом, и на почти чёрном; затем половина пути к фиксированному тёплому акценту, что делает отметку другой вещью, а не более ярким вариантом уже существующей. Все прочие линии картинки ахроматичны по построению, а вопрос и выбор о грани или детали двигают заливку, а не линию, поэтому это единственное место, где линия имеет цветовой тон. Честное упрощение: цвет меряется от материала, а не от затенения в этом пикселе, потому что expanded stream не несёт нормалей, а поток с нормалями был бы второй копией той же геометрии.
   **Ограничение, названное прямо.** Цель идентичности рёбер хранит одно значение на sample. Там, где два ребра сходятся в общей вершине или пересекаются в проекции, sample сообщает то из них, которое нарисовано последним, тогда как отметка, рисующая одно ребро, законно закрывает этот пиксель. Роль там не упоминается, поэтому новая роль, разрешающаяся в ребро, проходит тем же путём, что и крышечная. `EdgeNames`, `SelectedEdge`, `Marked::Edge`, кадрирование, Hide/Isolate и поведение при успешном и неудачном Open – всё generic, и ворота этого среза спрашивают их именно у sweep-ребра, чтобы ветка по роли, если бы она появилась, была видна.
   **Единственное изменение production-кода – одна ветка `describe_role`:** «Sweep edge at the joint of profile segments A and B», оба идентификатора и в том порядке, в котором их держит канонический `ProfileJoint`. Назвать один из двух значило бы описать угол половиной того, чем он является, а вторая половина – ровно то, что отличает его от соседнего угла.
   **Смежный дефект найден и намеренно не тронут.** В том же `describe_role` нет ветки и для `ExtrudeCapEdge`, поэтому выбранное крышечное ребро inspector тоже печатает через Debug. Это тот же класс дефекта в той же функции, но он за пределами названного среза, поэтому он назван, а не исправлен молча.
   **Ворота.** Сцена: четыре точные `ExtrudeSweepEdge` достигают ровно четырёх продольных рёбер; вместе с восемью крышечными они покрывают все двенадцать рёбер пластины и не пересекаются по смыслу; картинка без sweep-ссылок не выдумывает ни одного такого имени и оставляет ровно четыре ребра безымянными; все точные ссылки одного угла сохраняются в порядке документа, проверенном против самого документа; имена другой картинки и `EdgePickId::NOTHING` не называют ничего, а число, которого картинка не выдавала, вовсе не становится её ребром. Приложение: после орбиты находится согласованный пиксель продольного ребра, клик даёт `Selection::Edge` с `ExtrudeSweepEdge`, а не грань и не definition; следующий кадр меняет цвет только на этом ребре и оставляет pick- и edge-чтения каждого пикселя прежними; кадрирование идёт по самому ребру, Hide действует на владеющую definition, строка списка по-прежнему выбирает Definition. Inspector: Kind = Edge, оба durable-идентификатора, по одному предложению на каждое хранимое имя в порядке документа, и ни `EdgePickId`, ни `ProfileJoint`, ни `ExtrudeSweepEdge`, ни `SubShapeHandle`, ни `SessionId`, ни путь к файлу ни в одной строке.
   **Смежность взята одна на всех.** Ворота строят углы через `ProfileLoop::joints` – ту же арифметику, которой пользуются мост, адаптер и `TopologyMap`. Пары соседних кривых эскиза в тесте были бы второй арифметикой смежности, свободной разойтись с первой, поэтому `ferritecad-eval` добавлен в dev-dependencies приложения именно ради этого и только для тестов.
   **Мутации (одиннадцать, применены и выполнены; все одиннадцать роняют ворота).** Отбросить `ExtrudeSweepEdge` при связывании сцены; связать по позиции вместо равенства handle; сохранить только первое имя угла; провалить клик к грани под ребром; потерять имена рёбер в `prepare_load`; оставить inspector на Debug fallback; назвать только один из двух сегментов; напечатать transient-идентичность рядом с durable-словами; отметить всю деталь вместо ребра; позволить строке списка выбрать ребро; отдать углу имя соседнего угла. Ни один прогон, в котором не выполнился ни один тест, не засчитан: харнесс требует «running 1 test» и отказывается писать поверх существующего `.bak`.
   **Одна мутация выжила и вскрыла настоящую дыру в воротах.** «Отдать углу имя соседнего угла» сдвигает весь список имён на одну позицию, и ворота о покрытии этого не видели: четыре и восемь остаются четырьмя и восемью, множества остаются непересекающимися, объединение остаётся двенадцатью. Ворота проверяли, сколько имён и куда они не попали, но не то, на какое именно ребро попало каждое. Добавлено утверждение, которое это и пиннит: имя угла из сегментов A и B должно лежать на ребре, касающемся обеих граней, поднятых из A и из B, – прочитано через `edge_bounds_face` и `ExtrudeSide`, без координат и без порядковых номеров. На усиленных воротах мутация падает. Одна мутация сначала не применилась вовсе (ANCHOR MISSED, неверно списанный текст ветки `marked()`); это ошибка харнесса, а не результат, она исправлена и мутация выполнена по-настоящему.

   **Границы:** ни нового GPU-таргета, прохода, edge stream или renderer-side identity; ни отдельного `SweepEdgeNames` рядом с `EdgeNames`; ни нового типа выбора или наведения; схема, payload, capability и версия алгоритма снимка не менялись; C++, header, FFI и мост OCCT не менялись, поэтому pin не запускался; ни выбора вершин, ни привязок, ни выбора вхождений, ни UI моделирования. README не менялся: пользовательское обещание про выбор ребра было дано в 19L-3b2, и этот срез его не расширяет, а лишь распространяет на второй класс имён.

   **Исправление после независимого review.** Сквозные ворота говорили «выбранное продольное ребро и больше ничего», но проверяли только изменение целевого пикселя и неизменность identity-целей; пиксели, ошибочно перекрашенные вне ребра, могли пройти. Теперь каждый изменившийся пиксель обязан быть sample этого `EdgePickId` или касаться его в пределах одного пикселя, ровно в пределах уже документированного ограничения одноэлементной identity-цели на пересечениях. Тот же кадр доказывает, что hover уже выбранного ребра нигде не побеждает selection. Ещё одно утверждение сравнивало `Selection::at` само с собой и потому было пустым; вместо него пиксель с той же гранью и `EdgePickId::NOTHING` обязан дать `Selection::Face`, отличную от выбранного ребра. Два теста также больше не полагаются на совпадение ordinal первой грани и выбранного ребра: связанную грань они находят только через `edge_bounds_face`.

   **Срез 19L-3c1 сделан: документное имя для продольных рёбер extrusion.** Дефект: у пластины двенадцать топологических рёбер, восемь из них крышечные и уже названы, а четыре вдоль sweep документ назвать не мог вовсе – `EdgePickId` видит их в картинке, но после rebuild сослаться на них нечем. Ворота написаны первыми и шли по настоящему маршруту: временная копия зафиксированной пластины, дописанная точная ссылка, настоящий OCCT-rebuild, `TopologyMap`, `resolve`. Зафиксированное падение: «the joint of segments 019fe39c-...-908ab8eb3619 and 019fe39c-...-909aaed4f042 names no edge: unsupported: topology reference 01a01a93-... names the joint of segments ... and ..., and this build does not record which edge a profile joint swept». Заглушка содержала только проверку вида ссылки и отказ, никакой арифметики ассоциации.
   **Измерение до проектирования.** `BRepPrimAPI_MakePrism::Generated(vertex)` измерен на OCCT 7.9.3 тем же маршрутом, которым строит мост, и на тех самых угловых вершинах, которые соседние входные рёбра уже разделяют, а не на перестроенных точках. Восемь конфигураций: прямоугольная пластина вслепую, в обратную сторону, симметрично и обратно-симметрично; профиль из трёх сегментов с дугой вслепую и симметрично; треугольник как другая cardinality; и профиль из двух сегментов. Двадцать семь joints, и по каждому одно и то же: ровно одна форма, и это `TopoDS_EDGE`; она принадлежит готовому solid по `IsSame`; она ограничивает ровно две грани, и это ровно те две, что подняты сегментами, встречающимися в этом углу; она никогда не совпадает с cap-edge; её же достигает обход тесселяции; два разных joints ни разу не получили одно ребро; `history.Generated` для той же вершины отвечает тем же. Ответ не зависит ни от порядка обхода – профиль, перестроенный с другого стартового сегмента, не сдвинул ни одной ассоциации, – ни от ориентации: всё вернулось `FORWARD`. Ни одного случая wrong-type, not-in-solid или not-reachable. Поэтому ассоциация читается, а не выводится.
   **Единственная найденная неоднозначность названа, а не обойдена.** Она не в ядре, а в самом имени: на петле из двух сегментов оба угла – это место встречи одной и той же пары, поэтому пара перестаёт быть ключом. OCCT при этом честно отдаёт два разных ребра. Сказать, какое из них имелось в виду, нечем, и координата или порядок обхода были бы именно тем, что этот срез запрещает. Поэтому пара, встречающаяся более чем в одном углу, не называет ни одного из них: оба остаются безымянными, как остаётся безымянным сегмент, для которого ядро ничего не вернуло. Ворота проверяют это на полудиске и заодно требуют, чтобы cap-edges той же формы остались названными – отказ про эту пару, а не про фигуру.
   **Portable meaning.** Роль `SemanticRole::ExtrudeSweepEdge { joint }`, где `joint` – `ProfileJoint`: неупорядоченная пара `StableEntityId` двух соседних сегментов и больше ничего. Пара сортируется при построении, и несортированную удержать нельзя; `ProfileJoint::new` отказывает паре, называющей один сегмент дважды. Хранимая пара либо уже канонична, либо отвергается: `from_canonical` – одно правило, которым пользуются и serde, и codec кэша, поэтому у одного угла не может появиться второе написание ни в файле, ни в кэше. Ни координат, ни позиций сегментов, ни индексов обхода, ни ориентаций, ни handle: угол – это его два сегмента, поэтому вставка или удаление несвязанного сегмента оставляет уцелевший угол с тем именем, которое у него было.
   **Владение.** Мост записывает всё, что алгоритм породил в углу, включая количество, отличное от одного, – обрезать до одного значило бы скрыть ядро, ответившее иначе. Kernel-neutral `ExtrudeResult` несёт `sweep_edges` отдельной картой `BTreeMap<ProfileJoint, SubShapeHandle>`, рядом с face-history, а не внутри неё. `validate` отказывает чужой форме, не-ребру, одному физическому ребру под двумя joints и ребру, названному одновременно cap-edge и sweep-edge. Адаптер отказывается выбирать, если ядро вернуло больше одного. `TopologyMap` хранит множество на joint – именно там ядро, сообщившее больше одного, записано честно, – и отвергает joint, чей сегмент не входит в свёрнутый профиль. Resolver принимает только `Exact` и только `EntityKind::Edge` и отдаёт ровно одно ребро или отказывает. Archive хранит имя как слот, restore в новой сессии даёт новые handle с тем же смыслом, и ни `ShapeHandle`, ни `SubShapeHandle`, ни `SessionId`, ни номер обхода в документ или архив не попадают.
   **Capability и cache, решённые явно.** Новая capability `topology.extrude-sweep-edge.v1`, своя, а не расширение cap-edge: читатель, понимающий, где крышка встречает свёрнутую грань, не понимает тем самым угол, и сказать ему обратное значило бы дать право переписывать документ со ссылками, которые он не воспроизведёт. Версия payload `topology_ref` не поднята: раскладка байт та же, вырос словарь ролей, а это ровно то, для чего capability и существует. В codec кэша добавлен тег 6, а не новая версия формата, и старый читатель на нём не ошибается молча: неизвестный тег отвергает всю запись как malformed, поэтому частичный набор имён не может быть восстановлен и принят за полный, а отвергнутая запись пересобирается, потому что это кэш.
   **Ворота.** Четыре joints пластины дают четыре различных ребра, вместе с восемью cap-edges они покрывают ровно все двенадцать топологических рёбер и не пересекаются. Каждый joint ограничен ровно теми двумя свёрнутыми гранями, которые подняты его сегментами – прочитано из меша по принадлежности вершин граням и равенству handle, без координат. Вслепую, обратно, симметрично и обратно-симметрично называют один и тот же набор joints. Угол между двумя прямыми не путается с углом против дуги, и проверено это по тому, какие грани ребро ограничивает, а не по длине. Пара, названная наоборот, – тот же joint, тот же `meaning_hash`, а хранимая пара не в каноническом порядке отвергается и через CBOR, и через `from_canonical`. Несоседняя пара, чужой producer, чужая feature, неверный вид, семейное правило, отсутствующий joint, ноль совпадений и несколько совпадений дают разные отказы, и ворота требуют, чтобы тексты действительно различались. Две одинаковые по геометрии пластины именами не делятся. Удаление сегмента, не касающегося угла, оставляет его имя, а угол, половина которого исчезла, честно не разрешается. Названное ребро – то самое, которое рисует тесселяция, по равенству handle. Имена переживают файл и новую сессию, а handle – нет, и в `Debug` архива нет ни `SessionId`, ни `ShapeHandle`, ни `SubShapeHandle`; в сохранённой роли – только два идентификатора сегментов. Роль без своей capability отвергается до получения write access. Отменённая extrusion не оставляет ни одной живой формы, и сессия после неё по-прежнему пригодна.
   **Мутации (двадцать четыре, применены и выполнены; двадцать три роняют ворота).** Спросить `Generated` про входное ребро вместо угловой вершины; перестроить угловую точку вместо того, чтобы взять разделяемую; назвать угол не той парой; положить ребро под следующий угол; под предыдущий; выбрать первое из нескольких; принять пару, встречающуюся в двух углах; не канонизировать пару вовсе; отсортировать хранимую пару вместо отказа; позволить сегменту соединиться с самим собой; принять sweep-edge чужой формы; принять грань под именем ребра; позволить одному ребру отвечать двум углам; выдать cap-edge за sweep-edge; принять joint с сегментом вне свёрнутого профиля; разрешить семейное правило; принять ссылку, ожидающую грань; выбросить sweep-edges при архивировании; восстановить sweep-edge как cap-edge; перестать требовать capability; убрать второй сегмент из значения имени; назвать handle, соседний с сообщённым; позволить восстановленному ребру быть и углом, и крышкой; потерять имена на обратном sweep. Ни один прогон, в котором не выполнился ни один тест, не засчитан: харнесс требует «running 1 test» и отказывается писать поверх существующего `.bak`.
   **Пять мутаций сначала выжили. Четыре – мои ошибки прицела и две настоящие дыры в воротах.** «Назвать угол не той парой» целилась в ворота о правке профиля, а те требовали лишь, чтобы уцелевший угол по-прежнему разрешался, не проверяя, во что именно; ворота усилены – теперь у найденного ребра сверяются обе ограничивающие грани с гранями его собственных двух сегментов, и мутация падает. «Позволить сегменту соединиться с самим собой» целилась в ворота о перестановке пары, где самосоединения нет вовсе; перенацелена на ворота, которые это и проверяют. «Принять joint с сегментом вне профиля» была ненаблюдаема, потому что ни одни ворота не звали `record_extrude` с рукотворным результатом – проверка стоит на публичной границе, и туда ядро такой joint не приносит; добавлены ворота, которые именно это и делают, и мутация падает. «Достичь нарисованное ребро по позиции, а не по handle» была сформулирована неверно: она правила само утверждение ворот, а не реализацию, поэтому не проверяла ничего; заменена на настоящую мутацию реализации – назвать handle, соседний с сообщённым ядром, – и она падает на воротах о тесселяции.
   **Одна мутация названа ненаблюдаемой, а не переименованной в пройденную.** «Выбрать первое из нескольких» правит отказ адаптера, но чтобы его увидеть, ядро должно вернуть для одного угла больше одного ребра, а измерение по двадцати семи joints восьми конфигураций такого не дало ни разу. Ветка остаётся защитой от ядра, ведущего себя иначе, чем измеренное. Само правило «отказать, а не выбрать» воротами закрыто – на границе восстановления, где несколько имён под одним углом действительно представимы, и там соответствующая мутация падает.

   **Исправление после независимого review.** Отчёт был сильнее публичной границы: `TopologyMap` проверял только, что обе метки принадлежат внешнему профилю, поэтому рукотворный результат мог назвать sweep-edge несоседней парой или единственной неупорядоченной парой двухсегментной петли, которая встречается в двух углах. Два gate сначала воспроизвели оба принятия. Теперь `ProfileLoop::joints` является одной арифметикой смежности для адаптера OCCT и `TopologyMap`; карта принимает только пару, встречающуюся ровно в одном углу. Мост также больше не отбрасывает молча `null`, не-ребро или ребро вне готового solid из `Generated(vertex)`: каждый такой ответ явно отказывает операцию. Последние три отказы защитные и не выдаются за воспроизведённые мутации, потому что измеренные 27 joints ни одного такого ответа не дали.

C++, header и FFI изменились, поэтому pin запускался.

   **Срез 19L-3b2 сделан: выбор точного именованного топологического ребра.** Дефект: обе половины уже существовали – документ хранил и разрешал точные `ExtrudeCapEdge`, картинка знала, какое ребро под пикселем, а §19L-3b1 их связал, – но клик по ребру по-прежнему выбирал грань под ним. Ворота написаны на весь маршрут: временная копия зафиксированной пластины, дописанные точные ссылки, настоящий loader на OCCT, кадр, `Hit`, решение приложения, второй кадр, пиксели и inspector. Зафиксированное падение: «clicking a named edge chose `Face(SelectedFace { face: FacePickId { raw: 4 }, ..., output_role: ExtrudeSide { .. } })` instead of the edge». Честно: арифметика `Selection::at` была написана в том же проходе, что и тип, поэтому падение снято возвратом ветки к заглушке, а не прогоном до реализации; это записано так, а не выдано за иное.
   **Правило клика.** Самое частное первым и только там, где документ может сказать, что это: согласованное ребро с непустым `EdgeNames` бьёт названную грань, потому что человек, целившийся в линию, имел в виду линию. Ребро, которое никто не назвал, – не худшее ребро, а не выбор вовсе: клик проваливается к названной грани, если она есть, иначе к детали. Ребро импортированной definition всегда выбирает definition. Строка списка всегда выбирает Definition. Устаревшая, чужая и `NOTHING`-идентичность, как и противоречивая тройка definition/face/edge, `SelectedEdge` не собирают. Все точные ссылки одного ребра сохраняются в порядке документа. Проверка после среза нашла, что последняя фраза была сильнее ворот: именованное ребро и несмежная грань той же definition проходили проверку владельца. Теперь `Hit` отбрасывает такой edge sample, `Selection::at` независимо требует `edge_bounds_face`, а отдельные GPU- и scene-ворота держат обе границы.
   **Владение.** `Selection::Edge(SelectedEdge)` с приватными `edge`, `definition` и `meanings`: снаружи крейта непротиворечивую тройку собрать нельзя, её решает только `Selection::at`. `Marked` получил `Edge`; `Hovered` остался отдельным типом, вопрос и решение не слиты. `EdgeNames` проходит через `prepare_load`, `commit_scene` и `LiveScene` рядом с `FaceNames`: успешный Open заменяет снимок, каталог, оба набора имён, выбор, видимость и камеру атомарно, неудачный не меняет ничего. `owning_definition`, `Visibility` и `bounds` понимают `Edge` честно: скрывается и изолируется владеющая definition, кадрируется само ребро. В portable meaning не попадает ни `ShapeHandle`, ни `SubShapeHandle`, ни `SessionId`, ни `EdgePickId`, ни `FacePickId`.
   **Отрисовка.** Используется тот же expanded edge stream и тот же проход отметки: ни второй копии геометрии, ни новой identity-цели, ни GPU-side маски, ни загрузки на кадр, ни второй арифметики камеры. Выбранное ребро добавлено в `Globals` за счёт уже имеющегося padding: структура осталась ровно 96 байт, и это по-прежнему проверяет `const _: () = assert!(size_of::<GlobalsUniform>() == 96)` на стороне Rust плюс явные скаляры в WGSL, а не готовность backend прощать. Вопрос уводится на половину пути к тёплому акценту, решение – на 0.85 к холодному, поэтому они различаются и по тону, и по силе, и ни одно нельзя прочесть как более яркую версию другого. Выбор побеждает вопрос о том же ребре; вопрос о другом ребре по-прежнему виден. Проход отметки не меняет ни цвет вне выбранного ребра, ни pick-, face- и edge-чтения.
   **Inspector.** Один текстовый `TopologyName` с псевдонимами `FaceName` и `EdgeName`, и один цикл, печатающий шесть терминов: два формата разошлись бы. Для ребра показываются Kind = Edge, имя тела, его durable object id и все Reference / Owner / Feature / Entity / Role / Rule в порядке документа. Ни `EdgePickId`, ни raw, ни хеш снимка, ни индекс меша, ни ordinal, ни handle, ни сессия, ни путь в файловой системе туда не попадают, и ворота проверяют это по напечатанным строкам.
   **Ограничение, повторённое честно.** Цель идентичности рёбер хранит одно значение на sample, поэтому там, где два ребра сходятся в общей вершине или пересекаются в проекции, raw sample сообщает то из них, которое нарисовано последним; `Hit` сообщает его только если независимо прочитанная грань действительно им ограничена, иначе проваливается к грани. Ничего о разрешении нескольких кандидатов и о выборе вершины не заявляется. Отдельно измерено и записано: какие рёбра вообще имеют согласованный пиксель, зависит от вида – на пластине при кадрировании по умолчанию согласованы только два продольных ребра, а названные рёбра крышек лежат на внешнем силуэте, где `Hit` их отвергает; сквозные ворота поэтому поворачивают камеру с оси, и это сказано в них прямо.
   **Мутации (двадцать, применены и выполнены; девятнадцать роняют ворота).** Отбросить ребро при клике; отдать победу названной грани; принять ребро, которого никто не назвал; принять ребро чужой картинки; сохранить только первое имя; потерять имена рёбер при подготовке загрузки; сохранить прежний выбор после успешного Open; потерять имена рёбер при неудачном Open; нарисовать выбранное ребро цветом вопроса; отметить выбранными все рёбра детали; отметить только первое размещение; писать identity-цель из прохода отметки; загружать геометрию, когда что-то выбрано; отметить ребро скрытой детали; кадрировать ребро как всю деталь; кадрировать только первое размещение; скрывать через ребро, не спросив его definition; напечатать transient-идентичность в inspector; выбрать ребро строкой списка. Ни один прогон, в котором не выполнился ни один тест, не засчитан: харнесс требует «running 1 test» и отказывается писать поверх существующего `.bak`.
   **Одна мутация выжила и вскрыла настоящую дыру в воротах.** «Потерять имена рёбер при подготовке загрузки» переживала сквозные ворота, потому что те собирают `LoadedScene` через `snapshot_of` напрямую и в `prepare_load` не заходят, а ворота про Open зовут `commit_scene`. Добавлены ворота, которые ведут настоящие имена рёбер через `prepare_load` и требуют их на выходе; на них мутация падает.
   **Одна мутация названа ненаблюдаемой, а не переименована в пройденную.** «Пусть вопрос победит решение о том же ребре» правит WGSL, но комбинацию, на которой ветка различима, CPU не выпускает: `hovered_edge` пишется из `marked_edge`, а тот возвращает `None` ровно тогда, когда спрашиваемое ребро и есть выбранное, поэтому `selected_edge == hovered_edge` в шейдер не попадает никогда. Само правило приоритета воротами закрыто, но на стороне Rust, а не этой веткой.
   **Границы:** ни выбора вершин, ни выбора вхождений, ни выбора на размещение, ни моделирования, ни привязок, ни рабочих плоскостей, ни сохранения состояния интерфейса; схема, payload и capability не менялись; C++, FFI и мост OCCT не менялись, поэтому pin не запускался. `EdgePickId` остаётся transient, привязанным к снимку, несериализуемым и никогда не показывается. Границы граней из 19L-1 и семантика hover из 19L-2b2 не менялись сверх того, что потребовал приоритет выбора.
   **Срез 19L-3a сделан: документное имя для ограниченного класса рёбер extrusion.** Дефект: у ребра готового solid не было портируемого имени вообще – `EdgePickId` живёт только в снимке, а resolver умел называть лишь грани. Ворота написаны первыми, шли по настоящему маршруту – зафиксированная пластина, OCCT, `TopologyMap`, `resolve` – и падали: «the Start cap edge of segment ... is not named: unresolved topology reference: ... and this rebuild produced none».
   **Измерение до проектирования.** Прежде чем что-либо добавлять, `BRepPrimAPI_MakePrism::FirstShape(edge)` и `LastShape(edge)` измерены на OCCT 7.9.3 тем же маршрутом, которым строит мост: общие вершины углов, wire, грань на плоскости эскиза, призма. Пять конфигураций: пластина вслепую, пластина в обратную сторону, пластина симметрично, полудиск с дугой вслепую и симметрично. Итог во всех пяти: каждый сегмент дал `TopoDS_EDGE`, принадлежащий телу по `IsSame`; каждое ребро ограничивает именно ту крышку, которой должно; множества start и end не пересекаются ни разу; и каждое названное ребро встречается в том же обходе, которым пользуется тесселяция, поэтому имя и нарисованная линия – одна и та же под-форма. Ни одного случая wrong-type, not-in-solid или not-on-its-cap. Поэтому ассоциация читается, а не выводится, и сегмент, для которого её нет, остаётся безымянным.
   **Семантика, названная узко.** Новая роль `SemanticRole::ExtrudeCapEdge { side, profile_segment }`. Тройка: producer feature приходит из самой ссылки, side говорит, какой конец, segment – какое из рёбер этого конца. Двух из трёх не хватает: без сегмента это четыре ребра пластины, без стороны – два. Продольные рёбра, вершины, рёбра скруглений и импортированные рёбра имён не получают: у них нет имени, которое этот срез мог бы сохранить, а роль, притворяющаяся обратным, была бы ссылкой на то, что следующая перестройка положит в ту же позицию.
   **Владение.** Мост записывает по одному ребру на сегмент на сторону и отдаёт их через `fc_occt_extrude_cap_edges`, консолидируя через тот же `IsSame`, что и всё остальное. Kernel-neutral `ExtrudeResult` несёт `start_cap_edges` и `end_cap_edges` как `BTreeMap<StableEntityId, SubShapeHandle>`: заявленная кардинальность – одно ребро на сегмент – это само представление, а не правило, применяемое после. `ExtrudeResult::validate` проверяет владеющую форму, вид Edge и отсутствие любого противоречия, при котором одно физическое ребро получает два имени, включая имена на разных концах sweep; `TopologyMap` повторяет эту проверку на публичной границе и отказывается записывать ребро под меткой сегмента, которого нет во внешнем профиле. `TopologyMap` хранит множество на сегмент, потому что именно там ядро, сообщившее больше одного, было бы записано честно, и `resolve` смог бы отказать вместо выбора. Resolver принимает только `Exact` и только `EntityKind::Edge`, и отдаёт ровно одно ребро или отказывает. В документное значение не попадает ни `ShapeHandle`, ни `SubShapeHandle`, ни `SessionId`, ни индекс обхода, ни `EdgePickId`, ни порядковый номер тесселяции: хранится роль, сторона и метка сегмента.
   **Policy для persistence, решённая явно.** Ссылка с новой ролью объявляет дополнительную capability `topology.extrude-cap-edge.v1`; версия payload `topology_ref` осталась 1. Причина названа: байты лежат ровно так же – роль, правило, необязательная сигнатура, – а версия говорит, что изменилась раскладка. Изменился словарь ролей, и это ровно то, для чего capability и существует: читатель, не знающий роли, по-прежнему читает все остальные ссылки документа, а конверт называет ему причину по имени вместо того, чтобы не разобрать незнакомый тег. При чтении проверяются обе стороны контракта: всё объявленное должно поддерживаться, а известная роль должна объявлять все capability, которые ей нужны. Та же проверка действует при `determine_access`, поэтому повреждённый payload не может скрыть новую роль под одним `core.part.v1` и получить право записи. Документ, не называющий ни одного такого ребра, объявляет ровно то же, что объявлял раньше, и остаётся записываемым для более старого читателя; ворота это проверяют в обе стороны. Архив кэша получил два новых тега вместо новой версии формата: старый читатель отвергает запись как malformed, а это кэш, и отвергнутая запись пересобирается.
   **Ворота.** Пластина: четыре сегмента дают четыре start и четыре end, все восемь различны и все встречаются в тесселяции. Start и End не путаются ни для одного сегмента; один handle под именами обоих концов отвергается и в свежем результате, и после restore, а метка вне внешнего профиля не записывается. Вслепую, обратно, симметрично и обратно-симметрично – во всех четырёх по восемь имён. Дуга связывается с кривым ребром: у него на порядок больше сегментов отрисовки, чем у хорды, поэтому их нельзя поменять местами незаметно. Двенадцать рёбер пластины: восемь названы, четыре продольных – нет. Две одинаковые по геометрии детали не делят имён: метка чужого сегмента не разрешается, ссылка на чужой producer тоже. Ссылка не того вида, с семейным правилом или на другую сторону отвергается с точной классификацией ошибки. Два ребра под `Exact` дают отказ со словами «refusing rather than choosing». Имена переживают файл и новую сессию: после archive/restore восемь рёбер разрешаются на восстановленной форме, приходят как Edge, и в `Debug` архива нет ни `session#`, ни `shape#`, ни `edge#`, ни `face#`. Значение имени различает и сторону, и сегмент, и не совпадает со значением грани-крышки. Отдельные document-ворота повреждают envelope вместе с его integrity hash и доказывают, что роль `ExtrudeCapEdge` без своей capability отвергается до получения write access.
   **Границы:** ни `Selection::Edge`, ни `Marked::Edge`, ни `SelectedEdge`, ни inspector ребра, ни стиля выбранного ребра, ни кадрирования по ребру, ни видимости через ребро, ни идентичностей вершин, ни UI. Edge hover и четыре GPU identity target не тронуты. README не менялся: пользовательского поведения этот срез не добавляет. Названо прямо: имя получает один класс рёбер – граница крышки против грани, поднятой сегментом; всё остальное остаётся безымянным намеренно.
20. **[сделано]** Провести первый benchmark review и утвердить следующий срез. Корпус fillet/shell – 20 процедурных деталей с provenance, проходами через предел, B-Rep validation, детерминизмом и честными отказами на OCCT 8.0.1 трёх ОС. **Главная находка: `IsDone()` лжёт:** плита 60x40x10 при r=5.1 и r=6 даёт невалидную форму большего объёма, поэтому адаптер проверяет каждый результат через `BRepCheck_Analyzer` и не выдаёт handle при отказе. Solver-review завершён отдельно: нейтральный корпус до 208 уравнений, persistent constraint graph на drag, три неразрешимых случая и mapping native tags обратно в caller constraint indices. Оба кандидата проходят correctness-gate; baseline – planegcs из пиннутого FreeCAD 1.0.1 за широту уже реализованных sketch-ограничений, а не за неустойчивую разницу локальных микротаймингов. Решение зафиксировано в [ADR 0001](decisions/0001-sketch-solver.md); LM остаётся reference. Открыты масштабирование/разреженность, hardware profile и package/CI planegcs на Linux и Windows.

## 15. Чего не делать до beta

- не писать собственное B-Rep-ядро;
- не считать STEP редактируемым исходным форматом;
- не хранить ссылки как индексы граней;
- не принимать DWG/JT/IFC в scope без конкретного пользователя и бюджета;
- не заменять UI-фреймворк во время построения MVP;
- не начинать сборки и чертежи, пока не стабилизированы детали и topological naming;
- не объявлять performance победой без воспроизводимого замера и исходных данных.

## 16. Решения, принятые перед первым коммитом

Три вопроса, которые этот план оставлял открытыми, закрыты:

| Вопрос | Решение |
| --- | --- |
| Название и расширение | FerriteCAD, репозиторий `ferrite-cad`, crate'ы `ferritecad-*`, документ `.fcad`, кэш `.fcad-cache` |
| Целевые платформы | Windows, Linux и macOS – все три продуктовые и равноправные в CI |
| Источник тестового корпуса | Собственные процедурно сгенерированные детали и открыто лицензированные датасеты; происхождение STEP-файлов в `fixtures/step/PROVENANCE.md` |

Дополнительно, по итогам разбора самого плана, изменены три решения RFC: кэш вынесен в отдельный файл-спутник (§4.1), граница FFI строится плоским `extern "C"` шимом вместо `cxx`, а «временный внешний solver» конкретизирован как planegcs. Обоснования – в [архитектурном RFC](architecture-decisions.md).

Минимальные версии ОС остаются открытыми и определяются тем, что реально соберётся на этапе 0: для macOS это следствие выбора между universal binary и `lipo`, для Windows – выбранного MSVC runtime. Все остальные крупные решения зафиксированы в RFC и должны меняться только по результатам измерений этапа 0.
